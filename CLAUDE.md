# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

"George" is a planned agent for technical analysis of financial markets (pattern detection on OHLCV data, per-basket "George Index" scoring, natural-language rationale for trade decisions). The build follows the 8-phase roadmap in `George_Prompts_Claude_Code.md`. So far: **Phase 0** (DB schema + Docker infra), **Phase 1** (pattern-detection engine + price ingestion), **Phase 2** (backtesting, learned XGBoost confidence score, baskets + George Index), **Phase 3** (FastAPI backend + `web/` wired to it via React Query), **Phase 4** (Mistral-backed LLM layer: decision explainer, `/chat`, pgvector-indexed reports, Jane's second opinion — `agents/`), **Phase 6** (risk management: exit-level calculation, the propose→confirm→monitor→confirm-exit decision lifecycle — `engine/exit_levels.py`, `engine/propose_decisions.py`, `engine/monitor_decisions.py`, this section), a **deliberately scoped-down MVP of Phase 7** (collection orchestrator + validation/quarantine module + 2 manually-triggered sub-agents — `agents/orchestrator/`, `agents/collectors/`, see the Phase 7 section below), and a **simple-access-portal slice of Phase 9** (Supabase-backed login gating mobile and web, no per-user data isolation — `api/auth.py`, see the Auth section below) are implemented. **Phase 5 (mobile app) was deliberately skipped in its original form** — built out of roadmap order, straight after Phase 4, because the user's immediate need was real buy/sell opportunities surfaced through the existing API/web stack, not a mobile client; nothing about Phase 6 depended on Phase 5 having been built first. A **Flutter V1 MVP** of the mobile app was built later (see "Mobile app (Flutter)" section below), deliberately deviating from the roadmap's own Phase 5 stack (React Native/Expo + FCM + Piper/Coqui TTS) at the user's explicit request for Flutter + Firebase — with Firebase itself deferred to a V2 that tackles push notifications, since V1's scope (3 read/action screens against the existing REST API, no auth, no push) doesn't actually need any Firebase product yet. The full Phase 7 (LangGraph/Celery/Redis/Airflow/Playwright, 4 activation modes, the scraping-based sub-agents, Jane's continuous methodology watch) remains unimplemented — see that section for exactly what was built instead and why.

## Quality conventions (standing instruction, applies to every change)

Before considering any non-trivial change finished (new endpoint, new detector, new mobile screen, anything touching auth/money/external services) — not for a one-line fix or a docs-only edit:

- Run `/code-review` on the diff. This project's own history includes real bugs caught this way (see e.g. the stale-`engine`-reference bug in `api/routers/baskets.py`/`agents/reports.py`, or the `ponderations` bug caught while adding MACD/Bollinger/Stochastic) — treat that as the expected value of this step, not an optional extra.
- Run `/security-review` on anything touching `api/auth.py`, Supabase/Mistral/Resend credentials, the OAuth flows (`login_screen.dart`), or financial calculations (`engine/exit_levels.py`, `engine/propose_decisions.py`, `api/routers/portfolios.py`) — this app proposes real buy/sell decisions and now holds real user accounts, so an auth or a money-math bug is not a cosmetic one.
- For `web/` changes touching a page real users see (not an internal/admin view): run `/accessibility-review`.

Skipping these is a deliberate choice to make under time pressure, not a silent default — if skipped, say so explicitly rather than letting "done" imply "reviewed."

## Python backend (`ingestion/`, `infra/`, `tests/`) — Phase 0

### Commands
Run from the repo root:
```
cd infra && docker compose up -d      # Postgres+TimescaleDB, Redis, MinIO, Adminer
python -m venv .venv && .venv\Scripts\activate
pip install -e ".[dev]"
alembic upgrade head                  # apply migrations (needs the db container running)
python -m ingestion.seed              # load the 40 CAC 40 securities (idempotent)
pytest                                # needs a local Docker daemon (testcontainers spins up its own Postgres)
```
`alembic upgrade head --sql` / `alembic downgrade base --sql` print the migration SQL without needing a DB connection — useful to sanity-check a new migration when Docker isn't available.

### Architecture
- **`ingestion/models.py`** is the single SQLAlchemy declarative source of truth for the schema (`Security`, `PriceOHLCV`, `PatternDetected`, `Decision`, `DecisionOutcome`) — the Alembic migration in `ingestion/migrations/versions/0001_initial_schema.py` was written by hand to match it (not autogenerated), including the `create_hypertable('prices_ohlcv', 'ts')` call that makes `prices_ohlcv` a TimescaleDB hypertable. If you change `models.py`, write the matching migration by hand rather than relying on `alembic revision --autogenerate` to get the hypertable call right.
- **`ingestion/db.py`** resolves the connection string from the `DATABASE_URL` env var at call time (`get_database_url()`), falling back to the default local Docker Compose credentials. `alembic.ini` (repo root) does not hardcode a real URL — `ingestion/migrations/env.py` overrides it via `get_database_url()` on every invocation, online or offline. `get_engine()` sets `connect_args={"connect_timeout": 5}` — without it, psycopg trying both the IPv6 and IPv4 loopback addresses against a port nothing is listening on can hang far longer than 5s; this bit the notebook's DB-or-fallback logic (below) before the timeout was added, so keep it if you touch this function.
- **`ingestion/cac40.py`** holds the seed list of 40 `(symbol, name, country, currency, sector)` tuples; `ingestion/cac_mid60.py` adds 62 more (CAC Mid 60 — the current index closest to the historical "second marché", abolished in 2005 and folded into Euronext Paris's single market; compiled from Euronext's own March 2026 factsheet cross-checked against a secondary composition list, so treat it with the same "needs refreshing periodically" caveat already documented in `cac40.py`). `ingestion/seed.py` loads both, tagging `securities.theme` with which universe each symbol came from, and raises loudly if a symbol appears in both lists rather than letting the last upsert silently win. One symbol from the initial compilation (Eurazeo) had the wrong ticker (`RAZ.PA`, corrected to the real `RF.PA`) — caught immediately by `ingestion/ohlcv.py`'s per-symbol soft-failure logging, not by silent bad data, which is the whole point of that design.
- **Tests** (`tests/test_migrations.py`, `tests/test_seed.py`) use `testcontainers.community.postgres.PostgresContainer` (image `timescale/timescaledb:latest-pg16`) to get a disposable database per test session — they require a working local Docker daemon and are independent of whatever is running via `infra/docker-compose.yml`. Each test upgrades to `head` and downgrades back to `base` itself, so tests don't depend on execution order.

## Quant engine (`engine/`) + price ingestion (`ingestion/ohlcv.py`) — Phase 1

### Commands
```
python -m ingestion.ohlcv             # download 2y daily OHLCV via yfinance for every security, upsert into prices_ohlcv (needs network + db)
python -m engine.run_detection        # run all 13 pattern detectors against prices_ohlcv, insert confirmed matches into patterns_detected (needs db)
pytest tests/test_patterns.py         # unit tests on synthetic price series — no DB, no Docker, no network needed
pip install -e ".[dev,notebook]"      # adds jupyter for engine/notebooks/pattern_validation.ipynb (mplfinance is now a base dependency, see the "Share by email" section)
```

### Architecture
- **`engine/patterns/common.py`** holds the shared geometry toolkit and the module-level tolerances every detector reads (`EXTREMA_ORDER`, `LEVEL_TOLERANCE`, `MIN_PATTERN_BARS`, `BREAKOUT_BUFFER`) plus `PatternMatch` (the dataclass every detector returns). Pattern-specific thresholds (e.g. `MIN_PEAK_PROMINENCE`, `MIN_CUP_DEPTH` in `reversal.py`; `MIN_TREND_SLOPE`, `MIN_CONVERGENCE` in `continuation.py`) are documented in each file's module docstring, not centralized — read the docstring before tuning a specific pattern.
- Detectors are split by shape: **`reversal.py`** (Double Top/Bottom, Head & Shoulders + inverse, Cup & Handle — scan the *whole* price history for the most recent qualifying formation, since these can form anywhere in the past and only need a breakout on the latest bar to confirm), **`continuation.py`** (Bull/Bear Flag, Ascending/Descending Triangle, Falling/Rising Wedge — only look at a recent tail window, since these are short-lived), **`breakout.py`** (Breakout/Breakdown — recent tail window, requires a pullback bar immediately before the break so a plain continuous grind doesn't trivially count as a "breakout"). All 13 are registered in `engine/patterns/__init__.py`'s `DETECTORS` dict and re-exported from there.
- **Every detector returns at most one match** (the most recent formation), not every historical occurrence — each one filters/iterates backward and returns on the first (i.e. most recent) qualifying formation. `engine/detect.py:detect_all` just concatenates one call per registered detector.
- **Trendlines are fit through the actual extrema points** (`common.fit_trendline`, `np.polyfit` on `(extrema_index, price)` pairs), not through the whole window — this matters for wedges/triangles/flags. A recurring trap already hit once while building this: computing "does the range narrow / is the channel tight" using the *raw high/low of a window that still includes the breakout bar* silently defeats the check, because the breakout bar's whole purpose is to exceed the channel. Wedge convergence is measured strictly between the first and last **extrema** (`continuation.py:_wedge`), and a flag's channel (`continuation.py:_flag`) is fit only over the consolidation bars, explicitly excluding the final (candidate breakout) bar — apply the same exclusion if you add another breakout-confirmed continuation pattern.
- **`engine/confidence.py`** turns a detector's own `geometry_quality` (0-1, pattern-specific) plus shared `volume_confirmation` and `trend_alignment` (both also 0-1) into the final 0-100 score via fixed weights (0.5/0.25/0.25). `trend_alignment` needs 200 bars of history to judge SMA50/SMA200 alignment and returns a neutral 0.5 below that — expect near-identical confidence scores across patterns when testing on short synthetic series.
- **`ingestion/ohlcv.py`** downloads per-symbol via `yf.Ticker(symbol).history(...)`, retries up to `MAX_RETRIES` with linear backoff, and treats an empty/missing result as a soft failure (logged, symbol skipped, rest of the universe continues) rather than raising.
- **`tests/test_patterns.py`** builds each pattern from hand-placed `ramp()`/`path()` segments (strictly monotonic pieces glued end-to-end so `scipy.signal.argrelextrema` finds extrema exactly where intended) rather than random walks — when adding a test for a new detector, follow that construction style and hand-verify the key indices/levels against the detector's own gates instead of guessing coordinates.
- **`engine/notebooks/pattern_validation.ipynb`** tries the real DB first (via `engine.run_detection.load_prices`) and falls back to a synthetic Double Bottom (same construction as the test above) if it's unreachable or empty — verified executable end-to-end with `jupyter nbconvert --to notebook --execute`. Its `plot_match` helper only sets `hlines=`/`addplot=` on the `mpf.plot(...)` call when those lists are non-empty — mplfinance's kwarg validator rejects `hlines=None` outright rather than treating it as "no lines", which crashed the first version of this cell.

## Learned scoring, baskets & George Index (`engine/`) — Phase 2

### Commands
```
python -m engine.build_training_set   # DB -> engine/data/training_set.parquet (patterns_detected + prices_ohlcv backtested at 5/10/20 sessions)
# then run engine/notebooks/train_confidence_model.ipynb (offline) to train + save engine/models/confidence_xgb_<date>.joblib (+ .meta.json)
python -m engine.compute_george_index # prints each basket's George Index (needs db + baskets/basket_securities populated)
python -m engine.reevaluate_decisions # updates decision_outcomes for existing decisions (needs db)
pytest tests/test_features.py tests/test_backtest.py tests/test_george_index.py tests/test_scoring.py   # no DB, no Docker
```
`engine/models/` and `engine/data/` are gitignored (regenerable binaries/derived data) — running the training notebook with no `engine/data/training_set.parquet` present falls back to a synthetic dataset with a small fabricated signal, so the whole pipeline (train → evaluate → save dated model + metadata → load in `engine.scoring` → override a detector's confidence) is exercisable and was verified end-to-end without Docker.

### Architecture
- **`engine/features.py`** is the single source of the feature contract shared between training and inference: `FEATURE_COLUMNS` (= `CATEGORICAL_FEATURE_COLUMNS` + `NUMERIC_FEATURE_COLUMNS`). Its functions (`relative_volume`, `atr_pct`, `position_vs_moving_averages`) return `None` on insufficient history rather than a placeholder value — that `None` is exactly the signal `engine/scoring.py` uses to trigger the Phase 1 heuristic fallback instead of the learned model.
- **`engine/backtest.py`** is pure (no DB) — `build_sample` turns one detected pattern into a training row (features + `return_{5,10,20}` + `success_{5,10,20}` labels), gated on the pattern being far enough in the past that the longest horizon is observable. `compute_market_trend` is a deliberate proxy for "reference index trend" (cross-sectional average return of whatever price series you hand it) because the schema has no dedicated market-index feed — same limitation called out in `engine/george_index.md`. `engine/build_training_set.py` is the DB-touching script that resolves each `patterns_detected.detected_at` to an integer bar position (`nearest` on the DatetimeIndex) and calls into `backtest.py`. **It skips writing `training_set.parquet` entirely when zero samples are backtestable** (real case: right after a fresh `engine.run_detection` run, every pattern's `detected_at` is today, so none has `TRAINING_HORIZON` sessions of hindsight yet) — writing an empty, columnless DataFrame there would satisfy the training notebook's `os.path.exists(...)` fallback check while still crashing it on `dataset[FEATURE_COLUMNS]` a few cells later; the notebook now also guards with `not dataset.empty` before trusting the file, and falls back to the synthetic dataset otherwise.
- **`engine/scoring.py`** loads the lexicographically-last `engine/models/confidence_xgb_*.joblib` (filenames are ISO dates, so sorted-last == most recent) plus its `.meta.json` (`feature_columns`), caches both for the process, and never raises — any missing model, insufficient per-symbol history, or prediction-time exception falls back to `match.confidence` (the Phase 1 heuristic, already computed by the detector). `predict_confidence`'s `price_frames` param is optional: passing it enables the `market_trend` feature, omitting it just leaves that one feature as `NaN` (imputed by the trained pipeline) rather than blocking inference — only the *other* features (volume/ATR/moving averages) are treated as hard requirements.
- **The saved model artifact is a full scikit-learn `Pipeline`** (`ColumnTransformer(SimpleImputer + OneHotEncoder) → XGBClassifier`), not a bare `XGBClassifier` — this is why `engine/scoring.py` can call `.predict_proba()` directly on a raw one-row DataFrame with string `pattern_type`/`sector` columns without re-implementing the encoding at inference time. If you retrain with a different feature set, update `engine/features.py:FEATURE_COLUMNS` (both training and inference read from there) rather than hardcoding column lists in the notebook or in `scoring.py`.
- **`engine/george_index.py`** implements the formula documented in `engine/george_index.md` — read that file first; the two must stay in sync. Key asymmetry: the confidence part of the score only counts securities with a pattern detected within `ACTIVE_WINDOW_SESSIONS` (5 sessions), but the momentum/volume multipliers are computed over *every* security in the basket with enough price history, active or not — a basket's price-action context isn't limited to its currently-alerted names. Returns `None` (not `0`) when no security in the basket has an active pattern — a silent basket isn't a bad one.
- **`engine/reevaluate_decisions.py`** and **`engine/compute_george_index.py`** are thin DB scripts — `baskets`/`decisions` stay empty unless you run `ingestion/seed_demo.py` (Phase 3) or wait for Phase 6 to generate real decisions; verified here only by import and by unit-testing their pure helper functions (`evaluate_decision`, `george_index.compute_george_index`) directly, not against a live DB.
- **`ingestion/models.py`** gained `Basket`, `BasketSecurity`, `PatternCandidate` in migration `0002` (chained after `0001` via `down_revision`). `pattern_candidates` mirrors `patterns_detected`'s columns exactly — it's a landing/backtesting table for whatever the future Phase 7 methodology-watch agent proposes, nothing promotes rows into it yet.

## API (`api/`) — Phase 3

### Commands
```
uvicorn api.main:app --reload     # dev server on :8000, needs db running (needs Docker)
python -m ingestion.seed_demo     # optional: seeds baskets (one per sector) + a few illustrative decisions/agent_events, so the API isn't just empty lists
pytest tests/test_api.py          # most need Docker (testcontainers); one doesn't (see below)
```
`GET /docs` (Swagger UI) and `/openapi.json` are generated automatically by FastAPI — `app.openapi()` builds successfully with zero DB access (verified by importing `api.main` with no DB running), since routes only touch the DB when actually called.

### Architecture
- **`api/deps.py`** builds the SQLAlchemy `engine`/`SessionLocal` once at import time (not per-request) and exposes both as module attributes — `api/routers/baskets.py` reuses the same engine directly (not the per-request ORM `Session`) to call into `engine.george_index`/`engine.run_detection`, which expect a raw Engine. Tests override `api.deps.engine`/`api.deps.SessionLocal` via `monkeypatch` (see `tests/test_api.py`) since they're bound at import time, before a test DB URL is known. **`baskets.py` does `from api import deps` and reads `deps.engine` at call time — not `from api.deps import engine`.** The latter copies the reference at import time into `baskets.py`'s own namespace; a later `monkeypatch.setattr(deps, "engine", ...)` then silently misses it, and the route keeps querying whatever DB was live at process startup. Caught by running the real Phase 0-3 stack end-to-end (Docker actually available): `test_george_index_for_basket_with_active_pattern` passed against the isolated test container's `SessionLocal`-backed queries but returned `george_index: null` because `load_patterns`/`load_prices` were silently hitting the stale pre-monkeypatch engine instead.
- **`api/schemas.py:Page[T]`** is the one pagination envelope used by every list endpoint (`{"items": [...], "total", "limit", "offset"}`). Routers return a *bare* `Page(items=rows, ...)` (not the parameterized `Page[SecurityOut](...)`) with `rows` being raw ORM objects — this works because FastAPI re-validates the returned object against the route's declared `response_model=Page[SecurityOut]` regardless of how it was constructed, and that re-validation is what triggers `SecurityOut`'s `from_attributes` conversion. Verified with an isolated repro against this exact FastAPI/pydantic version pair before relying on it.
- **`GET /securities/{symbol}/prices`** exists beyond the roadmap prompt's minimum endpoint list — the candlestick chart (task 6 of the Phase 3 prompt) needs real OHLCV, and no endpoint for it was specified. It returns the `limit` most recent bars in chronological order; the frontend must reconstruct each bar's *absolute* index (`total - len(items)` from the same `Page` envelope) to translate a pattern's `context` indices (absolute positions in the full series the detector saw) into positions within this truncated window — see `CandlestickChart.jsx` below.
- **`GET /securities/{symbol}/patterns` orders by `detected_at.desc(), confidence.desc()`, not `detected_at.desc()` alone.** `engine/run_detection.py` typically confirms several pattern types for the same symbol with the exact same `detected_at` (all resolve off the same latest bar) — against a real populated DB, `limit=1` with only `detected_at` ordering returned an effectively arbitrary tied row (observed: consistently the *lowest*-confidence one, e.g. a 19% Double Bottom shown in the watchlist for a symbol that also had a 48% Inverse Head & Shoulders). The confidence tiebreaker makes "the pattern for this symbol" deterministic and picks the most convincing one instead. `tests/test_api.py::test_list_security_patterns_prefers_higher_confidence_on_tie` is the regression test.
- **`api/main.py:database_exception_handler`** is registered for `SQLAlchemyError`, deliberately *not* the bare `Exception` class — Starlette special-cases handlers registered for `Exception` (or status 500) and routes them to `ServerErrorMiddleware`, which sits *above* `CORSMiddleware` in the stack, so its response never gets CORS headers added (the browser then reports a misleading CORS error instead of surfacing the real 503, since with no DB running every list endpoint fails this way). Registering the handler on a specific subclass instead keeps it inside `ExceptionMiddleware`, *below* `CORSMiddleware`, so headers get added correctly. `tests/test_api.py::test_db_unreachable_returns_503_with_cors_headers` is the regression test — it needs no Docker (it points `api.deps.engine` at a deliberately-closed port) and will fail if this handler regresses to catching bare `Exception` again.
- **`ingestion/db.py`'s default `DATABASE_URL` host is `127.0.0.1`, not `localhost`** — `localhost` also resolves to `::1`, and psycopg tries both addresses in sequence on failure, doubling the time before a connection error surfaces (relevant because the API, the notebooks, and every script share this default). Combined with React Query's `retry: 0` (`web/src/main.jsx` — a second client-side attempt would double the already-multi-second server-side failure again), a cold "DB is down" page load now settles in roughly one `CONNECT_TIMEOUT_SECONDS` instead of stacking multiple retries at multiple layers.
- **`ingestion/seed_demo.py`** groups the existing `securities` by their `sector` column into one basket per sector — it doesn't invent a separate taxonomy. Decisions are only inserted for symbols that already have `prices_ohlcv` history (real `entry_price`, computed `take_profit`/`stop_loss` off it); a symbol with no price history is silently skipped rather than seeded with a fabricated entry price. Both the basket-seeding and decision-seeding steps check what already exists before inserting, so the script is safe to re-run.
- **`ingestion/models.py`** gained `AgentEvent` in migration `0003` (chained after `0002`). It backs `GET /agents/activity`; nothing populates it yet outside `seed_demo.py`'s illustrative rows, pending the Phase 7 sub-agents.

## LLM layer (`agents/`) — Phase 4

### Commands
```
alembic upgrade head            # migration 0004: CREATE EXTENSION vector + reports table
export MISTRAL_API_KEY=...      # required at call time, not import time — see below
uvicorn api.main:app --reload   # POST /decisions/{id}/explanation, POST /chat, POST /reports, GET /reports, GET /reports/search
pytest tests/test_agents.py     # pure context-builder tests, no DB, no network
pytest tests/test_api.py        # includes the Phase 4 endpoints, Mistral client monkeypatched — needs Docker (testcontainers), no real API key
```

### Architecture
- **Scoped per the roadmap's own text** (`George_Prompts_Claude_Code.md`, Phase 4 + the Jane paragraph under pilier 7): built here are the explainer, `/chat`, pgvector report indexing, and Jane's **synchronous second opinion** only. Jane's **continuous methodology-watch** role (scraping Investopedia/TradingView/etc. for new pattern candidates) explicitly "ne fonctionne que sur le mode veille continue autonome, en tâche de fond à faible priorité (queue/worker séparé)" — that infrastructure (Celery/Redis worker, Airflow) doesn't exist yet, so it stays deferred to Phase 7 rather than being half-built on top of a synchronous FastAPI request/response cycle.
- **`agents/mistral_client.py`** generalizes the roadmap's reference `mistral_client.py` (repo root) into one client shared by every sub-agent (explainer, Jane, chat, reports) instead of duplicating the retry/backoff logic per module. Deliberate deviation from that reference: the client is instantiated lazily on first real call (`_get_client()`), not at module import — the reference raises `RuntimeError` at import if `MISTRAL_API_KEY` is unset, which would make `agents.*` unimportable (and untestable) in any environment without a key configured, same reasoning as `ingestion/db.py:get_database_url()` resolving at call time rather than import time.
- **`MistralUnavailableError`** (raised for a missing key or after retry exhaustion) is a dedicated subclass of `RuntimeError`, deliberately *not* bare `Exception` — same Starlette trap as `SQLAlchemyError` (see Phase 3 section above): a handler on `Exception` gets pulled into `ServerErrorMiddleware`, *above* `CORSMiddleware`, so the browser sees a misleading CORS error instead of the real 503. `api/main.py:mistral_exception_handler` targets the specific subclass to stay under `CORSMiddleware`. Verified against the real dev DB with no `MISTRAL_API_KEY` set: `POST /chat` returns a clean `503` with the actual missing-key message, not a crash.
- **Every agent module calls `mistral_client.complete(...)`/`.embed(...)` via `from agents import mistral_client` then `mistral_client.xxx(...)`, never `from agents.mistral_client import complete`** — same reasoning as `baskets.py`'s `deps.engine` pattern in Phase 3: it lets tests `monkeypatch.setattr(mistral_client, "complete", fake)` and have every caller see the fake, regardless of which module imported it first.
- **`agents/context.py`** is pure (no DB, no LLM call) — same split as `engine/backtest.py` vs `engine/build_training_set.py`: it takes already-fetched ORM objects and returns a JSON-serializable dict, converting `Numeric` columns (`decimal.Decimal`) to `float` explicitly. This dict is the *entire* user message sent to the LLM; every system prompt in `agents/prompts/` instructs the model to never cite a number absent from it. `tests/test_agents.py` checks these builders directly; `tests/test_api.py` additionally monkeypatches `mistral_client.complete` to echo the received context back verbatim and asserts the real DB values (not fabricated ones) survive into the "response" — the two halves of the anti-hallucination guarantee required by the roadmap's task 6, without a real network call or API key.
- **`agents/explainer.py:find_pattern_for_decision`** prefers `decision.pattern_id` (Phase 6, a real foreign key filled in by `engine.propose_decisions`) when present. Older/illustrative decisions (`ingestion/seed_demo.py`) have no `pattern_id`, so it falls back to the pre-Phase-6 heuristic: the most recent `patterns_detected` row for the same symbol at or before the decision's `created_at` (same confidence-tiebreak rule as `api/routers/securities.py`'s pattern listing, Phase 3). `agents/jane.py` and `agents/chat.py` reuse it (or its `_latest_pattern` sibling in `chat.py` for symbols with no decision yet).
- **`agents/jane.py:second_opinion`** is a genuinely separate LLM call (`mistral-large-latest`, `agents/prompts/jane_second_opinion_system.txt`) from `agents/explainer.py:explain_decision` (`mistral-small-latest`) — not a parameter tweak on the same call. `POST /decisions/{id}/explanation` with `include_second_opinion: true` calls Jane first, then threads her note through `decision_context(..., jane_note=...)` into George's own explanation, which is told to arbitrate rather than defer to her. This implements the roadmap's "Jane relit le dossier complet ... juste avant la génération de l'explication finale par George" — originally wired to a manually-triggerable endpoint rather than an automatic publishing pipeline, and still is: Phase 6 built the propose→confirm decision lifecycle but nothing in it auto-calls Jane or the explainer, by design (an investor might want the explanation before *or* after confirming, not forced into one order).
- **`agents/chat.py:find_relevant_securities`** does plain substring matching (symbol root or lowercased name) against the ~40-security universe — the roadmap explicitly calls for "RAG simple sur les tables SQL, pas besoin de recherche vectorielle complexe à ce stade" for `/chat`; pgvector is reserved for `agents/reports.py` (task 4 is specifically about indexing long reports/notes, not routing chat questions).
- **`agents/reports.py`** reuses `engine.george_index.compute_george_index`/`engine.compute_george_index.load_patterns` directly (Phase 2), taking the SQLAlchemy `Engine` as a parameter rather than importing one — `api/routers/reports.py` passes `deps.engine` read dynamically at call time, avoiding the exact stale-reference bug already hit once in `baskets.py` (Phase 3). A portfolio-wide report (`basket_id=None`) leaves `george_index` as `None` rather than averaging per-basket indices: the George Index is a defined-only-per-basket metric (`engine/george_index.md`), and no methodology for a portfolio-wide aggregate exists yet.
- **`Report.embedding`** is `pgvector.sqlalchemy.Vector(1024)` — `mistral-embed`'s documented output dimension (verified from the installed `mistralai` SDK's own README, not yet against a real embedding call, since no `MISTRAL_API_KEY` has been configured in this environment). If Mistral ever changes that dimension, both `ingestion/models.py:EMBEDDING_DIM` and migration `0004`'s literal `1024` need updating together (a fixed dimension is required for the column type, not just a soft convention).
- **`mistralai` SDK note**: the installed version (2.7.2) imports as `from mistralai.client import Mistral`, *not* `from mistralai import Mistral` as shown in the roadmap's own reference `mistral_client.py` — that top-level shortcut doesn't exist in this version (confirmed by inspecting the installed package: `mistralai/__init__.py` doesn't exist, only `mistralai/client/`, `azure/`, `gcp/`, `extra/` subpackages). Follow `agents/mistral_client.py`'s import if extending this layer, not the root-level reference file's.
- **pgvector is already available in `timescale/timescaledb:latest-pg16`** (the image already in use since Phase 0) — confirmed with `SELECT * FROM pg_available_extensions WHERE name='vector'` against the real container before writing migration `0004`, so no base-image change was needed.

### Architecture
- **Not literally what the roadmap's Phase 6 prompt describes**, and deliberately so: the prompt's own "Contexte" line says decisions "sont créées avec entry_price, take_profit, stop_loss déjà en colonnes... mais la logique de calcul... n'existe pas encore" — it assumes decisions already exist and only specifies the *levels* calculation (task 1) and a `propose-levels`/`confirm` pair (tasks 2-3) for an *existing* decision. In reality, before this phase, only `ingestion/seed_demo.py` ever created a `Decision` row, explicitly as illustrative demo data (Phase 3). The user's actual ask ("peux-tu me proposer des opportunités d'achat") needed decisions to be created from real detected patterns in the first place — so `engine/propose_decisions.py` closes that gap: it's the module that turns a real `patterns_detected` row into a real `status="proposee"` Decision, which `propose-levels`/`confirm` then operate on exactly as specified.
- **`decisions.status` lifecycle**: `"proposee"` (created by `propose_decisions`, levels not yet validated) → `"confirmee"` (investor validated, possibly with adjusted levels) → `"sortie_proposee"` (the monitor job detected a TP/SL breach and filled in `exit_scenario`/`exit_volume_confirmed`/`exit_justification`) → `"cloturee"` (exit confirmed, `decision_outcomes` row written). The 3 pre-existing illustrative decisions (`seed_demo.py`) were backfilled to `"confirmee"` by migration `0005`'s `server_default` — they were already presented as definitive before this lifecycle existed, and `status` has no Python-side default (every code path sets it explicitly), so the server default only ever fires for that one historical backfill.
- **`engine/exit_levels.py:propose_levels`** implements task 1 for all 13 pattern types, not just the two the roadmap gives as examples (flag mast, double-bottom amplitude). Reversal patterns (Double/Top/Bottom, Head & Shoulders + inverse, Cup & Handle) compute take-profit/stop-loss entirely from the geometry already stored in `patterns_detected.context`. Continuation patterns (triangles, wedges) and Breakout/Breakdown don't store enough absolute-price geometry in `context` for this (only a slope or a percentage — see `engine/patterns/continuation.py`'s own docstring) — their functions take the already-loaded price `df` as a second input and recompute a recent high/low over the same `WINDOW` the detector itself used (imported directly from `engine/patterns/breakout.py`/`continuation.py`, not redefined), rather than duplicating that geometry into `context` solely for this purpose. Bull/Bear Flag needed one small, additive change to `continuation.py:_flag`'s `context` (added `pole_amplitude`, `flag_low`, `flag_high` — all computed values that already existed as local variables there, just not previously returned) to avoid an approximation; confirmed safe via `tests/test_patterns.py`, which doesn't assert on exact `context` contents for flags.
- **`engine/propose_decisions.py:select_candidates`** picks at most one proposal per symbol — the most confident active pattern (`ACTIVE_WINDOW_SESSIONS`, same 5-session/1.5x-day-margin window as `engine/george_index.py`) above `MIN_PROPOSAL_CONFIDENCE` (50.0) — and skips any symbol that already has an open decision (`status` in `proposee`/`confirmee`/`sortie_proposee`), so re-running it is safe and never stacks contradictory signals on the same title. Real run against the populated dev DB produced 16 proposals from 109 detected patterns; a few (e.g. a Double Bottom on MT.AS with bottoms far below the current price) show intentionally wide levels because the measured-move formula is faithful to whatever geometry the pattern actually has — proposals are meant to be reviewed/adjusted via `propose-levels`/`confirm`, not auto-executed, so this is accepted rather than artificially capped.
- **`engine/exit_scenarios.py:classify_exit`** implements the volume-confirmed-vs-noise distinction the roadmap asks for "dans ce dernier cas" (i.e. only for a stop-loss breach, not a take-profit hit) — reuses `engine.confidence.volume_confirmation` (same metric Phase 1 already uses for detection confidence) rather than a new one, thresholded at `VOLUME_CONFIRMED_THRESHOLD` (0.5, i.e. breach-day volume ≥ 1.25× the 20-session average) to choose `"sortie_totale"` vs `"sortie_partielle"`.
- **`engine/reevaluate_decisions.py:evaluate_decision`** (Phase 2) gained a third return value (`hit_at`, the breach session's timestamp) — its one existing caller (`run()` in the same file) was updated to unpack 3 values; needed so `engine/monitor_decisions.py` can locate the exact session to check volume on.
- **`engine/monitor_decisions.py`** never writes to `decision_outcomes` and never sets `status="cloturee"` itself — it only reaches `"sortie_proposee"` with the scenario/justification already filled in, honoring the roadmap's explicit constraint ("le job de suivi ne doit jamais clôturer une position automatiquement"). Only `POST /decisions/{id}/confirm-exit` writes the `decision_outcomes` row (task 5) and closes the decision — and it *recomputes* the outcome via `evaluate_decision` rather than trusting `exit_scenario` directly, because `"sortie_totale"` is ambiguous on its own (it's produced both by a take-profit hit *and* by a volume-confirmed stop-loss breach) and the real cause (`take_profit_hit`/`stop_loss_hit`) needs to be unambiguous in `decision_outcomes` for any future retraining use.
- **`GET /decisions`'s query param `status` used to mean `decision_type`** ("Achat"/"Renforcer"/"Surveiller"/"Alléger") — confusingly, since Phase 6 needed a *real* lifecycle `status` field on the same table. Renamed the existing param to `decision_type` and gave `status` its new lifecycle meaning; safe because no shipped `web/` code was actually passing a `status` value yet (`useDecisions({status, ...})` in `web/src/api/queries.js` existed but was never called with one) — updated to `useDecisions({decisionType, status, ...})` and the one test that exercised the old param (`tests/test_api.py`) accordingly.
- **`agents/prompts/exit_scenario_system.txt`** + `agents/context.py:exit_scenario_context` + `agents/explainer.py:explain_exit_scenario` are a third George-voice prompt (alongside the decision explainer and `/chat`), reusing the exact same anti-hallucination contract: the scenario/volume-confirmed verdict is already decided by `engine.exit_scenarios` before the LLM ever sees it, the LLM only puts it into words and is told to always restate that nothing is closed without investor confirmation.

### Scope decision
The roadmap's own text calls Phase 7 "l'étape la plus complexe du projet" — an orchestrator (LangGraph/CrewAI), Celery+Redis, Playwright/Scrapy, Airflow, 6 sub-agents, 4 activation modes, and a multi-source validation/quarantine module. Built here, with explicit user sign-off (plan mode) on scaling down to an MVP rather than attempting the full spec in one pass: the orchestrator and validation/quarantine module (tasks 1 and 4 of the roadmap's Phase 7 prompt) for real, plus **2 of the 6 specified sub-agents**, all triggered manually — same precedent as `POST /prices/refresh` — rather than via any scheduler/queue. No Celery, Redis (already provisioned in `infra/docker-compose.yml` but still unused by any Python code), Airflow, Playwright, or LangGraph exist in this codebase. Deferred entirely: regulatory-filing scraping, earnings-calendar scraping, sector-press/sentiment scraping, Jane's continuous methodology watch (the roadmap explicitly restricts that role to a low-priority background queue that doesn't exist yet — see the LLM layer section above for Jane's *synchronous* second-opinion role, which was already built in Phase 4), and 3 of the 4 activation modes (continuous background watch, nightly Airflow batch, reactive-to-a-missing-info-queue).

- **Sub-agent swap, discovered and confirmed with the user mid-implementation**: the roadmap's "fondamentaux d'entreprise" sub-agent (SEC EDGAR) has a real coverage gap for this universe — EDGAR only indexes companies that file with the US SEC. Checked directly against SEC's own `company_tickers.json`: only ~5-6 of the 102 tracked CAC 40/Mid 60 securities have a real CIK (TotalEnergies, Sanofi, Crédit Agricole, Orange, Saint-Gobain, via their ADRs) — `edgar_client.py` (root, still unintegrated, unchanged) would have been accurate but nearly useless at this universe's scale. Replaced with **"synthèse de document"** — one of the roadmap's own 7 listed collection task types (task 1) — which summarizes an existing `Report` (Phase 4, `agents/reports.py`) instead: zero coverage gap, zero new external dependency, reuses data already produced by the anti-hallucination-verified LLM pipeline.
- **`agents/orchestrator/types.py:CollectedItem`** is the one shared shape every collector returns (label, value, unit, source name/URL, observed-at, optional symbol) — pure dataclass, no DB, no network, same tier as `agents/context.py`.
- **`agents/orchestrator/validation.py:validate`** implements the roadmap's task 4 (multi-source cross-referencing, a reliability score, quarantine on unresolved contradiction) as a pure function: 1 source → `validated` at a moderate fixed reliability (`SINGLE_SOURCE_RELIABILITY = 0.6`, no fabricated second source); ≥2 sources → compares numeric values, `validated` (reliability scaling with agreement) if the relative spread is within `tolerance_pct` (1% default), else `quarantine` with both values in `reason`. This is the function the roadmap's task 7 test targets directly (`tests/test_orchestrator.py`) — no DB/network needed to prove contradictory sources never get integrated.
- **`agents/orchestrator/run.py:run_collection_task(db, engine, task_type, collector, scope)`** is the actual orchestrator (task 1): calls the already-resolved `collector` (passed in by the caller, not imported here — see next point), validates each returned group, writes an `AgentEvent` (validated) or `CollectedInfoQuarantine` (quarantined) row, commits, returns both. `engine` is a parameter, never imported at module level — same anti-stale-reference precaution as `agents/reports.py`/`api/routers/portfolios.py`. **`collector` is passed in rather than resolved from a `task_type` string inside this module** specifically to avoid a real circular import hit during development: `agents/collectors/*.py` import `agents.orchestrator.types.CollectedItem`, so having `agents/orchestrator/run.py` import back `from agents.collectors import COLLECTORS` created an import cycle the moment both packages' `__init__.py` files existed. `api/routers/agents.py` (the one caller) resolves `COLLECTORS[task_type]` and passes the callable in.
- **Dedicated table for numeric indicators, added later (ad hoc, not a roadmap task)**: `donnees_macro`/`donnees_eurostat`/`donnees_tic`/`donnees_worldbank` produce real numeric readings (a rate, an index, an amount) that used to live only inside `AgentEvent.context` — queryable as activity, not as a time series. `run_collection_task` now also upserts each validated group's items into `ingestion/models.py:MacroIndicatorSnapshot` (one row per source, not per indicator — e.g. EUR/USD's 3 sources each keep their own value, unique on `(indicator, source_name, observed_at)`), via the module-level `NUMERIC_INDICATOR_TASK_TYPES` allowlist. `synthese_document` is deliberately excluded: its `CollectedItem.value` is an LLM summary (`str`), not a number. Only **validated** groups are written here — a quarantined (contradictory) reading never enters this table, same principle as `AgentEvent`/`CollectedInfoQuarantine`. The `indicator` column uses the group's own `label` (the one passed to `validate()`), not `item.label` — a real bug caught while testing: a hand-built `CollectedItem` (in a test) can set its own `.label` independently of the group label it was collected under, so trusting `item.label` would have silently mislabeled a snapshot.
- **`agents/collectors/__init__.py:COLLECTORS`** is the registry (`{"donnees_macro": ..., "synthese_document": ..., "donnees_eurostat": ..., "donnees_tic": ..., "donnees_worldbank": ...}`), same pattern as `engine/patterns/__init__.py:DETECTORS`.
- **`agents/collectors/macro.py`** — FRED (`fredgraph.csv`), the ECB's Statistical Data Warehouse (`data-api.ecb.europa.eu`), and Frankfurter (`api.frankfurter.dev` — the `frankfurter.app` domain now 301-redirects there, called directly to skip the hop), all genuinely keyless public APIs (verified live before writing any code). EUR/USD is fetched from **all three** specifically to exercise `validate()`'s real multi-source path — the values are close but not identical in practice (e.g. 1.1385/1.138/1.138 on a live run), a genuine independent-source agreement, not a fabricated demo. The OAT-10-year indicator (`IRLTLT01FRM156N`) stays single-source — no independent keyless alternative was found, so it's `validated` at the single-source reliability rather than pretending a second source exists; EUR/GBP and EUR/CHF are also single-source (Frankfurter only). **A real bug caught by live validation, not by the test suite**: FRED's CSV header names the value column after the exact series ID (e.g. `observation_date,IRLTLT01FRM156N`), not a generic `DATE`/`VALUE` pair — the first implementation assumed the latter, which parsed successfully in unit tests (whose canned CSV fixtures happened to share the same wrong assumption) but silently found zero observations against the real endpoint. Fixed in `fetch_fred_series`, and the test fixtures corrected to match the real header shape. The dispatch dict inside `collect_donnees_macro` is built freshly on every call (not once at module import) specifically so tests can `monkeypatch.setattr(macro, "fetch_ecb_series", ...)` and have it actually take effect — a module-level dict built once at import time would have captured the original function reference before any monkeypatch could apply.
- **`agents/collectors/eurostat.py`** (`donnees_eurostat`) — chômage zone euro (`une_rt_m`) et inflation HICP (`prc_hicp_manr`) via l'API Eurostat, format **JSON-stat 2.0**, pas un CSV plat comme FRED/BCE : `fetch_eurostat_series` fixe toutes les dimensions sauf `geo`/`time` à une seule catégorie, puis décode l'offset plat de `value` à partir de `dimension.*.category.index` et `size` (le calcul se réduit à `geo_index * time_size + time_index`, vérifié valable tant que `geo` précède `time` dans `id` — vérification défensive à l'exécution, pas supposée). **Piège réel trouvé en vérifiant en direct** : le code géo "zone euro" diffère par dataset — `une_rt_m` veut `EA21`, `prc_hicp_manr` veut `EA20` ; les deux sont codés en dur par indicateur, pas un seul code partagé. Les deux indicateurs sont source unique (aucune alternative publique identifiée) → toujours `validated` à réputation 0.6.
- **`agents/collectors/tic.py`** (`donnees_tic`) — détention de Treasuries US par la France, système TIC du Trésor américain. **Deux vraies découvertes faites en testant contre le serveur réel, pas supposées** : (1) l'URL initialement prévue (`slt-table5.html`, une table HTML) renvoie un vrai 404 — la source réellement servie est `slt_table5.txt` (underscore, texte tabulé, sans BeautifulSoup) ; (2) **la première colonne de données est le mois le plus récent**, pas la dernière comme pour FRED/Eurostat — l'inverse de l'hypothèse initiale, corrigée après une capture réelle (`Country\t2026-05\t2026-04\t...`). Le serveur `ticdata.treasury.gov` s'est montré flaky pendant le développement (mélange de réponses 200 rapides et de timeouts sur des appels par ailleurs identiques) — traité comme n'importe quel échec transitoire (`None` + log), jamais fatal. Source unique → toujours `validated` à réputation 0.6.
- **`agents/collectors/worldbank.py`** (`donnees_worldbank`) — 5 indicateurs France-spécifiques via l'API World Bank (recettes fiscales, chômage, inflation, budget défense, production industrielle, tous `% PIB` sauf inflation/chômage) : ported from a sibling project of the user's (Wchecks, `clients/worldbank_client.py`), which queries this same free/keyless API for ~217 countries — only the response-parsing shape was reused, not that multi-country scope, since `MacroIndicatorSnapshot` has no country column (a single global/France instant per indicator, like `macro.py`'s OAT rate, not a per-country table like Wchecks' own `country_debt`). Country debt itself deliberately excluded: Wchecks' own comments note it switched that one indicator from World Bank to the IMF, no reason to pick back up a source the origin project itself moved away from. Single source per indicator → always `validated` at 0.6, same as `eurostat.py`/`tic.py`. **Two real issues caught by `/code-review`, not by manual testing** (no live network access to `api.worldbank.org` from the sandbox this was built in — verified instead by inspecting the ported client's own production-proven parsing code, and by mocking the documented `[metadata, data]` response shape in tests): a hardcoded `"date": "2015:2025"` window would have silently stopped seeing new publications past 2025 (fixed: computed fresh every call from `YEARS_OF_HISTORY=10` relative to the current year, with a regression test asserting the exact parameter sent); and a 30s timeout (copied from Wchecks, which has no equivalent constraint) × 5 indicators × `MAX_RETRIES=2` gave a 300s worst case inside `POST /agents/collect`'s **sync** route handler — reduced to 10s (matching `macro.py`/`eurostat.py`), bringing the worst case to 100s, in line with `macro.py`'s own already-accepted 120s (6 fetches × 2 retries × 10s).
- **`agents/collectors/finnhub.py` (`donnees_finnhub`) was decommissioned entirely, later in this project's history** (file, registry entry, `tests/test_finnhub.py`, `FINNHUB_API_KEY` in `render.yaml`, and the `symbol`-scope handling in `api/routers/agents.py`/`CollectionTaskRequest` all removed together) — not migrated to a dedicated table like its siblings above. Reasoning kept here rather than silently dropped, same discipline as the TimescaleDB removal documented elsewhere in this file: verified live with a real key that Finnhub's free tier covers **no** Euronext Paris ticker at all (every `.PA` symbol tested — `TTE.PA`, `MC.PA`, `OR.PA`, `SAN.PA`, `AIR.PA`, `AI.PA`, `BNP.PA` — returned a real `403 Forbidden`, not a `200` with `c: 0`), so it could never complement/replace yfinance for the CAC 40/Mid 60 universe this project actually tracks; it was also never wired into any web/mobile trigger (only reachable via curl/API, unlike `donnees_macro`'s "🌍 Collecte macro" button). A dead collector for a universe it can't cover added nothing worth keeping.
- **`agents/collectors/synthesis.py`** — `collect_synthese_document(db, engine, scope)` requires `scope["report_id"]` (`ValueError` otherwise, translated to 400/404 by the router); loads the `Report`, calls `mistral_client.complete` with a new `agents/prompts/synthesis_system.txt` (same shape as the other 5 prompts: French, narrow role, anti-hallucination rule 1, explicit empty-input clause) via `mistral-small-latest`. Always a single item from a single source (the report itself) — always `validated` by construction, unless the Mistral call itself fails, in which case `MistralUnavailableError` propagates unchanged and is already handled by `api/main.py`'s existing handler (Phase 4) — nothing new needed there. Verified end-to-end against a real `Report` and a real Mistral call in this environment (a key is in fact configured here): the summary faithfully cited the report's real confidence figures (e.g. "FR.PA... 87,1") without inventing anything, and the test/demo rows created during that check were deleted afterward.
- **`api/routers/agents.py`** gained `POST /collect` (`CollectionTaskRequest{task_type, report_id}` → `CollectionTaskResponse{validated, quarantined_count}`) alongside the pre-existing `GET /activity`. Unknown `task_type` → 400; `synthese_document` without `report_id` → 400 (checked before calling the collector, so it never reaches the collector's own `ValueError`-for-missing-scope path); unknown `report_id` → 404. `scope` is `{"report_id": ...}` when provided, else `None` (the `symbol`-scope branch, only ever used by the now-decommissioned `donnees_finnhub`, was removed along with it). Sync `def` route (like `api/routers/prices.py`), since a call is at most a few seconds (2 short HTTP GETs, or one Mistral call), no threadpool concern.
- **`ingestion/models.py:CollectedInfoQuarantine`** (migration `0008`) is deliberately not paired with a new `produced_by_agent` column — `AgentEvent.agent_name` already identifies the producing sub-agent for validated info, and adding a second column with the same meaning would be redundant.
- **`web/`**: one manual trigger only — "🌍 Collecte macro" in `Univers.jsx`'s sidebar (next to "🔄 Mise à jour des prix"), calling `useTriggerCollection()` (`web/src/api/queries.js`). No trigger for `synthese_document`: it needs a `report_id`, and no screen in `web/` lists `Report` rows yet — building one was out of scope for this pass; the endpoint remains callable via API/curl.
- **Verified live against the real Supabase database** (migration `0011` applied, then `run_collection_task` called directly for `donnees_macro`/`donnees_eurostat`/`donnees_tic`): 7/7 indicators validated, 0 quarantined, 9 real rows landed in `macro_indicator_snapshots` — EUR/USD's 3 sources (FRED 1.1385, BCE 1.1485, Frankfurter 1.1485) each kept as a separate row at `reliability_score` 0.99 (high agreement), every other indicator (OAT, EUR/GBP, EUR/CHF, chômage, inflation HICP, Treasuries TIC) single-source at 0.6 — no fabricated values, no silent overwrite between sources.

### Scope decision
Requested directly by the user as a **simple access portal**, explicitly *not* the multi-tenant data isolation the roadmap's own Phase 9 might otherwise imply: `decisions`/`baskets`/`portfolios` stay exactly as global/shared as they were before this phase (see the "Named portfolios" section above — that "single shared list across all API clients" statement is still accurate post-Phase-9; auth gates *access*, not *data*). Chosen and designed by comparing two sibling projects of the user's: `MeteoIA` (Supabase Auth, email/password + Google OAuth **proven working in production**) and `JADE` (PocketBase, whose Google OAuth is **broken** — an unresolved SDK/server version mismatch). Supabase was picked for George specifically because its OAuth path is the one already proven to work, and it's used here purely as an external identity provider — no new table exists in George's own Postgres/TimescaleDB for this, and no `service_role` key is ever needed (unlike `MeteoIA`, which also uses Supabase as its application database for `messages`/`profils`).

- **`api/auth.py`** follows the exact same shape as `agents/mistral_client.py`: `SUPABASE_URL`/`SUPABASE_ANON_KEY` are read inside `verify_supabase_token` at call time, never at import — same reasoning as `_get_client()` there, so `api.auth` (and anything importing it) stays importable/testable with no keys configured. **Never decodes the Supabase JWT locally** — `verify_supabase_token` always makes a real `GET {SUPABASE_URL}/auth/v1/user` call with the token as a Bearer header plus an `apikey` header, a direct port of a mechanism already validated in production in `MeteoIA/db.py:obtenir_utilisateur`. Returns `None` for a non-200 response (an expired/invalid token — an expected, normal outcome) and reserves `SupabaseUnavailableError` (a dedicated `RuntimeError` subclass, not bare `Exception`) for actual service failure: missing config, or Supabase itself unreachable (`httpx.HTTPError`).
- **`require_user`** (the dependency actually wired to routers) uses `fastapi.security.HTTPBearer(auto_error=False)` rather than a raw header read — `auto_error=False` is deliberate: the default `True` behavior raises a `403` for a missing header, a well-known FastAPI surprise that's wrong for a bearer-token API; a manually-raised `HTTPException(401, ...)` is used instead for both the missing-header and invalid-token cases. Declaring it as an `HTTPBearer` security scheme (rather than `Header(...)`) is also what makes FastAPI register an OpenAPI `securitySchemes` entry — confirmed live via `/openapi.json`, which shows `HTTPBearer` on every protected route — so `/docs` gets a real "Authorize" button, the fastest way to manually exercise a protected route without curl.
- **`SupabaseUnavailableError` gets a dedicated `api/main.py` exception handler (503)**, same Starlette trap already documented for `SQLAlchemyError`/`MistralUnavailableError`: a handler registered on bare `Exception` gets routed to `ServerErrorMiddleware`, *above* `CORSMiddleware`, so its response never gets CORS headers. **`HTTPException(401)` needs no such handler** — it already has a default handler inside Starlette's `ExceptionMiddleware`, the same layer as the other dedicated handlers, so it stays under `CORSMiddleware` for free. Verified live via curl against a running dev server with no `SUPABASE_URL` set: `GET /baskets` with no token → `401` ("Authentification requise."); the same request with a garbage Bearer token → `503` ("Variables d'environnement SUPABASE_URL/SUPABASE_ANON_KEY manquantes."), confirming the two error paths are distinguished correctly.
- **`api/main.py`** adds `dependencies=[Depends(require_user)]` to all `app.include_router(...)` calls (securities, baskets, decisions, agents, chat, reports, portfolios, prices, and later additions — see other sections below) — this protects every route in each router *without* the route function needing to declare or consume the dependency's return value, consistent with the "portal, not per-user filtering" scope decision above (the returned Supabase user id is available for future use but nothing reads it today). `/health` and FastAPI's own auto-generated `/docs`/`/redoc`/`/openapi.json` are deliberately outside every one of these routers, so they stay reachable with no token — verified live via curl.
- **`httpx`** moved from `[project.optional-dependencies].dev` to `[project].dependencies` in `pyproject.toml` — it was previously only a `TestClient`-driving dev tool; `api.auth.verify_supabase_token`'s real runtime HTTP call to Supabase makes it a genuine runtime dependency now.
- **`tests/test_api.py`**'s existing `client` fixture and the standalone `TestClient(app)` inside `test_db_unreachable_returns_503_with_cors_headers` both add `monkeypatch.setitem(app.dependency_overrides, auth.require_user, lambda: "test-user-id")` before constructing their `TestClient` — FastAPI's own `dependency_overrides` mechanism, chosen over monkeypatching the httpx call itself since it's the standard built-in way to bypass one dependency without touching the module it lives in; `monkeypatch.setitem` self-reverts at teardown, matching the existing `monkeypatch.setattr(deps, ...)` style already used in these same fixtures. All ~193 pre-existing tests pass unchanged through this bypass — none of them needed to be touched individually.
- **`tests/test_auth.py`** is a new, separate, pure test file (no DB, no Docker, no network) rather than folding auth tests into `test_api.py` — same tiering principle as `test_agents.py` vs `test_api.py`: `require_user` is a plain `async` function with zero DB dependency, so it's called directly via `asyncio.run(...)` (not through a `TestClient`) to avoid adding `pytest-asyncio` as a dependency for 3-4 tests. Covers: missing credentials → 401, invalid/expired token (mocked `verify_supabase_token` → `None`) → 401, valid token (mocked → a fake user dict) → returns the user id, and missing `SUPABASE_URL`/`SUPABASE_ANON_KEY` → `SupabaseUnavailableError`.

### Mobile (`mobile/`)
- **`supabase_flutter` (2.16.0)** added via `flutter pub add supabase_flutter` (not hand-typed — lets pub resolve the actual current compatible version rather than guessing one). Its default local session storage is plain `shared_preferences` (confirmed from the resolved dependency tree) — **not encrypted at rest**, unlike `JADE`'s explicit `flutter_secure_storage` choice for the same problem. Accepted as-is for this simple-portal pass (a stolen/rooted-device session token is a real but lower-severity risk than the auth gate simply not existing at all); `supabase_flutter` does accept a custom `LocalStorage` implementation if this needs hardening later.
- **Two real API mismatches caught by `flutter analyze`, not assumed from the package's docs**: (1) `Supabase.initialize(...)` has no `authFlowType` parameter directly — it must be nested inside `authOptions: FlutterAuthClientOptions(authFlowType: AuthFlowType.pkce)` (`core/auth/supabase_init.dart`); (2) `anonKey` is deprecated in favor of `publishableKey` in this version (kept the env var itself named `SUPABASE_ANON_KEY` for consistency with the backend/web convention, only the Dart-side parameter name changed).
- **`GoRouterRefreshStream` does not exist in `go_router` 17.3.0** — checked directly against the installed package source after the initial plan assumed it was an importable export (it's long been a *community recipe* shown in go_router's own docs/examples, never actually shipped inside the package). A hand-written `ChangeNotifier` subscribing directly to the raw Supabase stream was tried first, but that shape itself turned out to be the source of a second, more serious bug — see the next point.
- **`core/auth/auth_providers.dart`**: `authChangeStreamProvider` (`Provider<Stream<AuthState>>`) wraps `Supabase.instance.client.auth.onAuthStateChange`, and `authStateProvider` (`StreamProvider<AuthState>`, app-lifetime, deliberately not `.autoDispose` unlike every provider in `data/`) reads it via `ref.watch`. **This split exists because of a real bug caught by `flutter test`**: an early version of `app.dart`'s `_goRouterProvider` called `Supabase.instance.client.auth.onAuthStateChange` directly (not through a provider) to build its `refreshListenable` — this touches the real Supabase singleton (never initialized in a widget test, which doesn't go through `main()`) even when `isLoggedInProvider` is overridden, crashing `test/widget_test.dart`. Routing the raw stream through `authChangeStreamProvider` makes it overridable (`authChangeStreamProvider.overrideWithValue(const Stream.empty())`) exactly like any other Riverpod dependency, fixing the test without any special-casing.
- **`core/auth/go_router_refresh_stream.dart` — a second, more serious real bug, caught only on a physical device, not by any test**: the first working version of this file was a `ChangeNotifier` subscribing directly to the raw stream from `authChangeStreamProvider` (`stream.listen((_) => notifyListeners())`), independently of `authStateProvider`'s own subscription to that same stream. Symptom, confirmed live via temporary diagnostic `SnackBar`s added to `_login()` (no USB/logcat access was available on the test device): `Supabase.instance.client.auth.signInWithPassword(...)` completed successfully every time, but the app never navigated away from `/login`. Root cause: two independent `.listen()` calls on the same broadcast stream fire in the order they were *registered*, not in any order tied to their logical dependency — the router's own listener (registered first, at `_goRouterProvider`'s construction) fired `notifyListeners()` and triggered `redirect:` to re-run *before* `authStateProvider`'s own internal listener (registered later, only on first read of `isLoggedInProvider`) had finished updating its cached value — so `redirect:`'s `ref.read(isLoggedInProvider)` observed the stale "logged out" state on every single login, by construction, not intermittently. Fixed by replacing the raw-stream subscription with `AuthRouterRefreshNotifier`, which calls `ref.listen(authStateProvider, (_, __) => notifyListeners())` instead — Riverpod's own contract guarantees a `ref.listen` callback only fires *after* the watched provider's state has already been updated, which removes the race by construction rather than by timing luck.
- **`app.dart`**: `_router` is now `Provider<GoRouter>((ref) => ...)` instead of a top-level `final` — `redirect:` reads `ref.read(isLoggedInProvider)` to bounce to `/login` when logged out (and away from `/login` when already logged in), `refreshListenable: AuthRouterRefreshNotifier(ref)` re-runs `redirect:` on every auth change (see the race-condition bug above for why this isn't built off the raw stream directly). `GeorgeApp` became a `ConsumerWidget` reading this provider. `_AppShell` gained a shared `AppBar` (it previously had none — just `body: navigationShell` + `bottomNavigationBar`) with a `person_outline` icon that pushes `ProfileScreen` — decided with the user directly (asked via options: shared AppBar vs. a 4th "Profil" tab vs. a floating button on one screen only) in favor of the shared-AppBar option, one place to code, visible from all 3 tabs.
- **`features/profile/profile_screen.dart`** mirrors `JADE/mobile/lib/features/memory/profile_screen.dart`'s shape (an `AppBar` with a logout `IconButton` in `actions:`, plus a full-width "Se déconnecter" button in the body) but with George's much narrower scope: just the connected account's email and sign-out, no bio/preferences editor (nothing in George has an equivalent). A **pushed screen via `Navigator.push`, not a `go_router` route** — same precedent already established for `features/decision_detail/` (see that section above): a single non-deep-linked destination doesn't need a nested route.
- **`core/auth/auth_interceptor.dart`**: a Dio `QueuedInterceptor` reading `Supabase.instance.client.auth.currentSession?.accessToken` directly (the singleton, not a Riverpod read) and attaching it as `Authorization` — added to `core/api_client.dart`'s constructor. Deliberately keeps `ApiClient` itself free of any Riverpod import, same as before this phase.
- **`android/app/src/main/AndroidManifest.xml`** gained an additional `<intent-filter>` (VIEW/DEFAULT/BROWSABLE, `android:scheme="io.supabase.george"`) for the OAuth deep-link return, additive to the pre-existing MAIN/LAUNCHER filter. The iOS `Info.plist`/`CFBundleURLTypes` equivalent is documented in `mobile/README.md` but **not verified** — no iOS build is possible from this Windows machine (see "iOS cannot be built or run from Windows" above).
- **Real bug, only reproducible in a release build on a physical device — missing `<uses-permission android:name="android.permission.INTERNET" />`.** The manifest never declared it (true since `flutter create`, long before this phase). `flutter run` in debug mode silently masked this the entire time this app existed: Flutter's tooling auto-injects the INTERNET permission (plus a few others needed for the VM service) into debug builds regardless of the manifest's own content — but `flutter build apk --release` (the only way to produce the APKs actually distributed via Firebase App Distribution) does **not** get that injection, so without the explicit permission, Android blocks all socket access at the OS level for the app's process. Symptom on a real phone: every network call (Supabase email/password login, and by extension the OAuth deep-link flow too) failed with `ClientException with SocketException: Failed host lookup: '<host>' (OS Error: No address associated with hostname, errno = 7)` — a DNS-shaped error that has nothing to do with DNS. Diagnosed by process of elimination, not assumption: the same phone logged into `JADE` successfully (ruling out a general connectivity problem), and opening the exact Supabase URL directly in the phone's own browser returned a real Supabase JSON response (ruling out DNS/domain-level blocking) — leaving "something specific to this app's own network stack" as the only remaining explanation, which pointed straight at the manifest. Fixed by adding the permission; `pubspec.yaml`'s version bumped (`1.1.2+4`) to mark the fix in the distributed build. **A second, unrelated XML pitfall was hit fixing the first one**: the initial fix's explanatory comment happened to contain the literal substring `--release` — XML forbids a bare `--` inside a comment body, which broke `AndroidManifest.xml` parsing entirely (`ManifestMerger2$MergeFailureException`) until the comment was reworded to avoid any double-hyphen.

The screen also gained a password-visibility toggle (`suffixIcon` eye icon) and — like `ProfileScreen` — a version label (`PackageInfo.fromPlatform()`, same pattern as `JADE`'s own login screen) so a build under test is always identifiable without needing to log in first.
- **Third real bug, found immediately after the first successful login**: once past `/login`, `UniversScreen`/`PaniersScreen` showed nothing but spinners, and `PaniersScreen`'s own "API unreachable" message appeared — yet `curl` from the dev machine against `http://192.168.1.162:8000/health` worked fine, and the backend's own access log showed exactly one request ever received, from `192.168.1.162` itself (the dev machine's own curl check, not the phone — a real request from the phone was never actually reaching the server). Cause: **Android 9+ (API 28+) blocks cleartext (plain `http://`) traffic by default**, and `AndroidManifest.xml` had no `android:networkSecurityConfig` at all — Supabase calls were unaffected (always `https://`), but every call to George's own dev backend (necessarily `http://`, since it's a local dev server, no TLS cert) was silently blocked at the OS level before ever leaving the phone. Already anticipated in `mobile/README.md`'s own text ("Android 9+ bloque le trafic HTTP en clair par défaut... à ajouter si un vrai appareil Android refuse la connexion") but never actually implemented until a real device surfaced it. Fixed with a new `android/app/src/main/res/xml/network_security_config.xml` (`<base-config cleartextTrafficPermitted="true">`, referenced via `android:networkSecurityConfig` on `<application>`) — cleartext allowed globally rather than scoped to one IP, since the dev backend's address changes per network (emulator/simulator/physical device all use different values, see `mobile/README.md`) and this app isn't distributed beyond internal testing yet.

Manually verified against the real Supabase project (`george-auth`) end-to-end at the backend/API layer (curl: 401 without a token, 401 with an invalid one, 200 with a real password-grant access token). ## Hosting (Supabase Postgres + Render) — ad hoc, not a roadmap phase

### Commands
```
export DATABASE_URL=postgresql+psycopg://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
alembic upgrade head                  # applies the full migration history against Supabase's Postgres
```

### Scope decision
Requested directly by the user, who wanted the mobile app reachable over the real internet rather than the local LAN (the LAN path needed a Windows Firewall rule and only worked on the same Wi-Fi as the dev machine — see the Mobile section above). The obvious first instinct — deploy George's own Postgres via Render or Railway — hit a real wall: **George's schema depends on the `timescaledb` extension** (`create_hypertable` on `prices_ohlcv`/`fx_prices_ohlcv`, since Phase 0), and neither Render's nor Railway's managed Postgres includes it; getting it would have meant a Docker-based private service with a persistent disk, which needs a paid plan (confirmed live: Render blocks deploying `plan: starter` pserv services without payment info on file).

- **TimescaleDB was dropped entirely, in favor of plain Postgres.** Verified live, not assumed, that Supabase (already in use for the auth portal, Phase 9 above) does *not* offer `timescaledb` on Postgres 17 projects — `CREATE EXTENSION IF NOT EXISTS timescaledb;` in the SQL Editor against the real `george-auth` project failed with `extension "timescaledb" is not available`, matching Supabase's own docs ("deprecated in projects using Postgres 17"). Given George tracks ~100 securities total, TimescaleDB's actual value-add (chunk partitioning, compression) was never load-bearing at this scale — dropping it unblocks a genuinely free, already-owned Postgres host with zero functional loss. `ingestion/migrations/versions/0001_initial_schema.py` and `0009_carry_trade.py` had their `CREATE EXTENSION timescaledb`/`create_hypertable(...)` calls removed directly (editing already-applied migrations rather than writing a new one to reverse them — justified here since this is a single-developer project with no other environment depending on migration history, and the local dev DB is trivially resettable/re-ingestable). `infra/docker-compose.yml` and `tests/conftest.py`'s testcontainers image both moved from `timescale/timescaledb:latest-pg16` to **`pgvector/pgvector:pg17`** (plain Postgres 17 + pgvector, matching Supabase's exact version) — pgvector (migration `0004`, `Report.embedding`) still needs to come from somewhere now that the TimescaleDB image no longer provides it for free; `tests/test_migrations.py`'s hypertable-existence assertion was removed accordingly.
- **George's own Postgres (via `george-auth`, the same Supabase project already used for auth) hosts the actual application data** — a deliberate expansion of that project's role beyond "identity provider only" (the original Auth-phase design explicitly kept these separate). Connection uses Supabase's **Session pooler** (`aws-0-<region>.pooler.supabase.com:5432`), not the direct connection — Supabase's own guidance reserves direct connections for IPv6-capable hosts and recommends the session pooler as "the alternative... when connecting via an IPv4 network," which better matches an external host like Render.
- **Render (`render.yaml`, repo root)** hosts only `george-api` (`env: python`, **`plan: free`** — no database service needed anymore, since Supabase already hosts the data, which is what makes the free plan viable here). `buildCommand: pip install -e .`; `DATABASE_URL`/`MISTRAL_API_KEY`/`FINNHUB_API_KEY`/`SUPABASE_URL`/`SUPABASE_ANON_KEY` are all `sync: false` (filled in manually via the Render dashboard once the service exists, same convention as Jaz's own `render.yaml` in `MeteoIA`). Migrations/seeding are run manually (via Render's Shell tab or, as done here, directly from a local machine with `DATABASE_URL` pointed at the Supabase connection string) — no CI/CD migration step exists yet.
- **Two real, previously-undiscovered data bugs surfaced only by running the full pipeline against fresh data ingested mid-trading-day** (local dev had never done this — prior ingestion runs happened to land after market close): `engine/run_detection.py:load_prices` and (now-removed, see the Carry Trade removal note below) `engine/compute_carry_index.py:load_fx_prices` both cast the whole price history to `float`/`int64` without ever dropping a trailing row whose `close` is `NaN` — yfinance can return a most-recent bar with real `open`/`high`/`low`/`volume` but a `null` `close` for a session still in progress (the *same* bug class already fixed once in `api/routers/portfolios.py:_current_price_and_pnl`, now hit a second and third time in different modules). Concretely, this produced: (1) `engine/scoring.py:predict_confidence` computing features (`relative_volume`, `atr_pct`, `position_vs_moving_averages`) off a NaN close, writing a `NaN` confidence into `patterns_detected` for every Breakout/Breakdown pattern whose most recent bar was incomplete (160 of 603 rows on the first real run); (2) `engine/propose_decisions.py` then reading `df["close"].iloc[-1]` directly for `entry_price`, producing NaN there too; (3) `engine.propose_decisions` crashing outright with `decimal.InvalidOperation` the moment it tried to compare a `Decimal('NaN')` confidence against `min_confidence` in Postgres. Fixed at the source in both loader functions (`return df[df["close"].notna()]`, filtering the incomplete trailing bar before *any* downstream consumer — detectors, `engine/confidence.py`, `engine/scoring.py` — ever sees it) rather than patching each consumer separately; `engine/confidence.py:volume_confirmation` also gained a defensive `pd.isna` guard on the same principle. Re-running the full pipeline after the fix against the same live Supabase data confirmed zero `NaN` confidences and zero `NaN` entry prices (down from 603 to 263 genuine pattern detections — the drop itself confirms some of the original 603 were spurious "breakouts" against a bad trailing bar, not just NaN-tainted).
- **Verified**: full test suite (197 tests) green after every change above; `alembic upgrade head` applied cleanly against the real Supabase database; `ingestion.seed`/`ingestion.ohlcv`/`engine.run_detection`/`engine.propose_decisions` all run successfully end-to-end against it; the local FastAPI app, pointed at `DATABASE_URL=<supabase connection string>`, served real data (`/securities`, real decisions) through the full Supabase-auth-protected request path. ## Named portfolios (`api/routers/portfolios.py`, web `Mon Portefeuille`) — ad hoc, not a roadmap phase

- **`web/src/views/Paniers.jsx`**: checking a row's checkbox only stages it in local component state (`checkedIds`) — nothing is sent to the API until "Créer un portefeuille" is confirmed with a name in the popup (❌ Annuler / ✅ Enregistrer, per the user's exact spec), calling `POST /portfolios` via `useCreatePortfolio`. The checkbox column sits between Confiance and Créée le, as requested.

- **The "Décisions" and "Alertes" nav tabs were removed** (they were `Placeholder` stubs since Phase 3, never implemented) at the user's request, alongside adding the new "Mon Portefeuille" tab.
- **`engine/portfolio_allocation.py`** (migration `0007` adds `portfolio_decisions.quantity`) computes a budget split across a portfolio's decisions — weight = confidence × (take-profit distance / stop-loss distance), i.e. more credible *and* better-rewarded-for-risk decisions get a bigger share, truncated to whole shares (no fractional-share trading on these markets). Deliberately **not** an LLM call: the same "small model can't reliably enumerate/compute over many structured entries" lesson from `agents/chat.py`'s opportunities case applies here even more directly, since this one has to be numerically correct (real money math), not just faithfully worded — `format_allocation_summary` builds the human-readable explanation in Python from the already-computed allocations, and `POST /portfolios/{id}/allocate` is a plain deterministic endpoint, no `agents.mistral_client` involved at all.
- **`PortfolioDecisionOut.current_price`/`pnl_pct` and `PortfolioOut.total_pnl_amount`/`total_invested`** are computed on every request (`api/routers/portfolios.py:_current_price_and_pnl`/`_portfolio_out`), not stored columns — `engine.run_detection.load_prices` for the latest close, and the same direction-aware sign convention as `engine.reevaluate_decisions.evaluate_decision` (bullish `{"Achat","Renforcer"}` vs bearish, imported as `BULLISH_DECISIONS` rather than redefined). **Deliberately not a call to `evaluate_decision` itself**: that function's `since = df[df.index >= decision.created_at]` filter exists to bound the history it scans for a TP/SL breach (Phase 6's exit-monitoring use case), and returns `None` whenever no price bar is dated on/after the decision's creation — for a decision proposed off today's close, that left this screen's PnL blank until tomorrow's bar existed, even though today's return (zero) was already knowable from `current_price == entry_price`. `_current_price_and_pnl` instead computes `(current_price - entry) / entry * 100 * direction` directly off the latest close, so `pnl_pct` is only `None` when there's no price history at all. `total_pnl_amount`/`total_invested` only sum over decisions with both a `quantity` (set via "Demander à George" or a future manual edit) and a non-null `pnl_pct` — a portfolio with no quantities yet shows `total_pnl_amount: null`, which `MonPortefeuille.jsx` renders as a "Renseignez des quantités..." prompt instead of a fake `0`. `_current_price_and_pnl` also returns `price_updated_at` (`df.index[-1]`, the last ingested price bar's timestamp) — `PortfolioDecisionOut`'s "Date"/"Heure" columns show *this*, not `DecisionOut.created_at` (when the decision itself was proposed): the two are genuinely different events (a decision from last week vs. this morning's price refresh) and conflating them was a bug caught by the user directly, not something derivable from the code. The portfolio's own `created_at` is shown separately, next to the "🎙 Demander à George" button ("Créé le …"). **Real bug caught by testing against the web UI, not by the test suite**: `.iloc[-1]` on the raw price DataFrame isn't enough — yfinance can ingest a most-recent bar with a real `open`/`high`/`low`/`volume` but a `null` `close` (observed live: a session still in progress at ingestion time), which silently turned `current_price`/`pnl_pct` into `NaN` → serialized as JSON `null` by FastAPI, with no error anywhere. Fixed by dropping `NaN` closes (`df["close"].dropna()`) before taking the latest one, same "skip missing, use latest present" idiom already used in `agents/collectors/`'s fetchers. `_current_price_and_pnl` also returns `day_change_pct` (added later, mobile-only column so far — `mobile/lib/features/portefeuille/portefeuille_screen.dart`'s "Delta veille" column): the raw day-over-day move `(last_close - previous_close) / previous_close`, deliberately *not* direction-adjusted like `pnl_pct` — it answers "how did the market move yesterday", not "how is this position doing", so it's `None` only when fewer than 2 closes exist, never flipped in sign for a bearish decision.
- **`POST /prices/refresh`** (`api/routers/prices.py`) wraps `ingestion.price_history.run` behind a manually-triggered HTTP endpoint — the "🔄 Mise à jour des prix" button under "Univers" in `Univers.jsx`'s sidebar. **Asynchronous**: the endpoint returns immediately with a `PriceRefreshStatus` (`idle`/`running`/`done`/`failed`), running the actual download (10 years of history for the full CAC 40 + Mid 60 universe, including yfinance retries) in a `BackgroundTasks` job tracked by an in-memory `_state`/`threading.Lock` (single uvicorn worker, no Redis/Celery needed for one job at a time) — clients poll `GET /prices/refresh` until a terminal status, each bounded by their own max-wait/max-consecutive-errors guards rather than a single fixed HTTP timeout, since `_state` doesn't survive a Render restart mid-job. `useRefreshPrices()` (`web/src/api/queries.js`) invalidates the *entire* React Query cache on success (not just `["securities"]`) since a price refresh can change patterns, decisions, the George Index, and portfolio PnL, all downstream of `price_history_long`. `SIDEBAR_NAV` in `Univers.jsx` used to list "Paniers"/"Décisions"/"George Index"/"Historique" as static, unclickable decoration (leftover from the original design prototype, never wired to real navigation — the actual view-switching nav is `App.jsx`'s top-level tabs) — trimmed to just "Univers" at the user's request, since those labels duplicated/contradicted the real top nav and the already-removed "Décisions"/"Alertes" tabs. `ResponsePopup.jsx`'s "loading" status text is now overridable via `popup.loadingText` (defaulting to "George réfléchit…") — needed here since this popup isn't an LLM call and "George réfléchit…" would be a misleading label for a price download.
- **"Demander à George" (web, per-portfolio mic button)** reuses the browser speech-to-text already built for Univers.jsx's voice command, extracted into `web/src/hooks/useVoiceCapture.js` (generic: caller supplies `onListening`/`onInterim`/`onError`/`onFinal`, the hook owns only the `SpeechRecognition` plumbing and error messages). `MonPortefeuille.jsx`'s `onFinal` runs a regex (`parseBudgetFromText`) over the transcript to pull out a euro amount ("répartis un budget de 100 000 euros..." → `100000`) and calls the deterministic `/allocate` endpoint — no LLM in this parsing step either, consistent with the point above. Which portfolio triggered the mic (several buttons, one per portfolio) is tracked in a ref set synchronously on click, not a state — a state update from the same click handler wouldn't be visible yet when `voice.start()` reads it in the same tick.

Two scope points confirmed directly with the user (via plan mode): RSI becomes a 4th confidence factor for **all 13 pre-existing detectors**, not just reversal patterns; and the ~12 candlestick detectors are built **in the same pass**, not deferred to a later one.

- **`engine/patterns/common.py:rsi(series, window=RSI_WINDOW)`** — Wilder's smoothing (`.ewm(alpha=1/window, adjust=False)`, not a plain rolling mean), `RSI_WINDOW=14`, `RSI_NEUTRAL_ZONE=50.0`. Handles the two degenerate cases explicitly rather than letting them fall out of the raw formula as `inf`/`NaN`: an uninterrupted rally (zero losses) → RSI pinned to `100.0`; a perfectly flat series (zero gains and zero losses) → RSI at the neutral `50.0`. Shared by every one of the now-25 detectors and by `engine/features.py:rsi_at` (the learned-model feature), not duplicated per module.
- **`engine/confidence.py`** rebalanced from the Phase 1 weights (`GEOMETRY 0.5 / VOLUME 0.25 / TREND 0.25`) to `GEOMETRY 0.4 / VOLUME 0.2 / TREND 0.2 / RSI 0.2` — `confidence_score` gained a 4th required parameter (`rsi_conf`), a breaking signature change accepted deliberately (every one of the 13 pre-existing call sites was updated in the same pass, not left on a default). `rsi_confirmation(close, at_idx, bullish)` returns `1.0` when the RSI sits on the expected side of its neutral zone for the pattern's direction, `0.0` when it contradicts it, `0.5` (neutral, same "insufficient data" convention as `trend_alignment`) when history is too short. Directly implements the synthesis's own worked counter-example (CAC 40, April 1997: a confirmed Head & Shoulders breakout that failed specifically because RSI never confirmed) — a geometrically perfect pattern with a contradicting RSI now scores meaningfully lower rather than being scored on geometry/volume/trend alone.
- **All 13 pre-existing detectors** (`reversal.py`, `continuation.py`, `breakout.py`) now compute `rsi_conf` at their confirmation bar and pass it to `confidence_score`, and store the raw value in `context["rsi_14"]` — not just used for scoring, but preserved so `agents/context.py` (below) can cite the actual number rather than recomputing or approximating it.
- **`engine/exit_levels.py:fibonacci_retracement_levels(swing_low, swing_high)`** — the 4 standard retracement ratios (38.2%/50%/61.8%/76.4%) between a swing low/high. **Deliberately informational-only**: it does not touch `propose_levels`'s existing take-profit/stop-loss formulas for any of the 13 chartist patterns — those were already validated (Phase 6) against real worked examples in the synthesis, and the synthesis's own recommendation (§7.5) was explicitly "no change needed to the existing formulas." Fibonacci levels are computed separately, only for the 5 reversal patterns whose `context` already stores an absolute swing low/high (Double Top/Bottom, Head & Shoulders + inverse, Cup & Handle — `agents/context.py`'s `_FIBONACCI_SWING_EXTRACTORS` maps each pattern type to the right two `context` keys), and surfaced to the LLM as supporting context, never as a new exit level.
- **`engine/patterns/candlestick.py`** (new, 12 detectors across 6 geometric pairs: Doji, Hammer/Hanging Man, Inverted Hammer/Shooting Star, Bullish/Bearish Engulfing, Morning/Evening Star, Piercing Line/Dark Cloud Cover) — implements the synthesis's explicit "never alone" rule (§2.1/§6: a candlestick shape by itself is not an actionable signal) as a **hard pre-filter**, separate from and in addition to the soft-scored geometry/volume/trend/RSI factors every other detector uses: each function checks the OHLC shape (body/range and shadow/body ratios, thresholds documented in the synthesis) *and* the preceding trend direction (`_preceding_trend`, a short lookback slope check), returning `[]` outright if either fails — a textbook Hammer shape after an uptrend is not a Hammer, it's discarded. This is why geometrically-identical pairs (a Hammer and a Hanging Man are the same candle shape) need two separate detector functions with two separate `pattern_type` names, rather than one function that names its output conditionally: `engine/exit_levels.py:is_bullish()`/`_LEVEL_FUNCTIONS` (Phase 6) hard-codes exactly one direction per `pattern_type` string, and preserving that existing contract was simpler and safer than changing it to accommodate context-dependent naming.
- **`engine/exit_levels.py:_candlestick_levels`** — candlesticks have no "pattern height" the way chartist patterns do (no measured-move geometry), so take-profit/stop-loss use a different, equally book-sourced rule instead: stop-loss at the signal candle's own extreme wick (with `BREAKOUT_BUFFER`), take-profit derived from a minimum **risk/reward ratio of 3** (`CANDLESTICK_RISK_REWARD_RATIO`, §5 of the synthesis) applied to the resulting risk distance — a second, independent rule from the synthesis, not an approximation of the chartist formulas. All 12 candlestick pattern types were added to `BULLISH_PATTERNS`/`BEARISH_PATTERNS`/`_LEVEL_FUNCTIONS`; skipping this would have made `engine.propose_decisions` raise `KeyError` the first time a real candlestick pattern was proposed.
- **`engine/patterns/__init__.py:DETECTORS`** now has 25 entries (13 chartist + 12 candlestick), all still one dict, one registration point, same precedent as every other detector added since Phase 1.
- **`engine/features.py`/`engine/scoring.py`** — `rsi_14` added to `NUMERIC_FEATURE_COLUMNS` and computed via `rsi_at(df, at_idx)`, but treated as a **soft/non-gating** feature at inference time (like `market_trend`), not a hard-gating one (like `atr_pct`/`relative_volume`/the moving-average features): RSI only needs 14 bars of history, far less than the SMA200 gate, so a missing value is left as `NaN` for the trained pipeline's imputer rather than aborting inference. Because `engine/scoring.py` resolves its feature columns from the trained model's own `.meta.json`, not from `NUMERIC_FEATURE_COLUMNS` directly, adding this column doesn't change or break inference against the currently-deployed model — it only takes effect after a future retrain via the existing notebook.
- **`agents/context.py:decision_context`** — the one change that actually made any of the above reach an LLM explanation, found by tracing the full chain before writing any code: `decision_context` was already dropping `pattern.context` entirely (only `pattern_type`/`detected_at`/`confidence` were ever forwarded), so RSI/Fibonacci could be computed and stored correctly and still never appear in an explanation. Now `context["pattern"]` also carries `"rsi_14"` (straight from `pattern.context`, `None` if absent — e.g. patterns detected before this change) and `"niveaux_fibonacci"` (computed on demand via `_fibonacci_context`, `None` for any pattern type without an absolute swing in its `context`, i.e. continuation patterns and all 12 candlesticks) — never a raw, unfiltered `pattern.context` passthrough, keeping the same "explicitly control what's citable" discipline as the rest of this anti-hallucination architecture. `agents/prompts/explainer_system.txt` and `agents/prompts/jane_second_opinion_system.txt` had their "éléments de confirmation" rule extended to name RSI and Fibonacci explicitly (citing the same CAC 40 1997 example for Jane's prompt) — rule 1 (never cite a number absent from context) already covers these new fields with no change needed.
- **`.github/workflows/daily_yfinance_import.yml`** gained two more steps (`engine.run_detection` then `engine.propose_decisions`) after the existing price/fundamentals ingestion steps — closing a real gap surfaced mid-planning when the user asked for the ability to "submit a price history and get an analysis": clarified via AskUserQuestion that the actual need wasn't a new submission endpoint (the 102 tracked securities' history is already in the database), but daily automation of the analysis that already exists and, until this change, only ever ran manually. No new endpoint or UI was built as a result — every existing screen (Univers/Paniers) now shows freshly-detected patterns and freshly-proposed decisions each morning without any manual trigger.
- **Out of scope for this pass** (documented rather than silently dropped, same discipline as every other ad hoc feature above): no arbitrary/off-universe curve submission endpoint; Elliott wave detection (the synthesis itself flags wave identification as too interpretation-dependent for a reliable automatic detector); pair trading; a Livermore-style pyramiding/reinforcement mechanic (George never reinforces an existing decision — a bigger philosophy change than this pass); actually retraining the XGBoost model with the new `rsi_14` feature (the feature is wired and ready, retraining stays the existing manual notebook step).
- **Verified**: `pytest -q` — 254 passed, 13 skipped (skips are the risk/reward-ratio test correctly skipping the 13 non-candlestick pattern types). Verified live against the real production Supabase database: `engine.run_detection` ran cleanly across the full ~102-security universe with no crashes, produced 275 real pattern detections including genuine candlestick matches; `engine.propose_decisions` produced 17 real proposals with no `KeyError` on any candlestick-sourced decision; a direct `decision_context()` call against a real VIRI.PA Double Bottom detection confirmed real RSI and Fibonacci values were correctly surfaced.

## Confidence sub-scores in George's explanation — ad hoc, not a roadmap phase

Requested directly by the user after seeing a real "George explique" popup for ABVX.PA (Double Bottom, 53.7% confidence) and asking for a walkthrough of how that number was reached — then asking to add that same breakdown (Detection / Confidence scoring / Fibonacci levels) into George's actual generated explanation, not just an ad hoc answer in conversation.

- **All 25 detectors now store their 4 real confidence components in `context`**, alongside the already-existing `rsi_14`: `geometry_quality`, `volume_confirmation`, `trend_alignment`, `rsi_confirmation` (all 0-1, rounded to 3 decimals). Every detector already computed these locally right before calling `engine.confidence.confidence_score(...)` — they were just discarded after producing the final blended 0-100 score. For the 12 candlestick detectors this is a single change (`engine/patterns/candlestick.py:_score_and_match`, the shared constructor every one of them calls); the 13 chartist detectors (`reversal.py`/`continuation.py`/`breakout.py`) each have their own literal `context={...}` dict, so each needed its own edit.
- **`agents/context.py:decision_context`** forwards these as `context["pattern"]["scores"]` (`geometrie`/`volume`/`tendance`/`rsi`, `None` for any component absent from an older pattern's `context` — same "never fabricate, show unavailable" discipline as `rsi_14`) plus `context["pattern"]["ponderations"]`, the fixed weights (`GEOMETRY_WEIGHT`/`VOLUME_WEIGHT`/`TREND_WEIGHT`/`RSI_WEIGHT`, 0.4/0.2/0.2/0.2) imported directly from `engine.confidence` rather than hand-copied into the prompt or into `agents/context.py` as literals — so a future rebalance (this happened once already, 0.5/0.25/0.25 → 0.4/0.2/0.2/0.2) can never silently desync the explanation from the real weights.
- **A real, previously-latent circular import surfaced by this change, fixed at its source**: `agents/context.py` importing `GEOMETRY_WEIGHT` etc. from `engine.confidence` at module level triggered `ImportError: cannot import name 'confidence_score' from partially initialized module 'engine.confidence'` — reproducible from a completely fresh process with just `python -c "import engine.confidence"`, unrelated to anything else in this pass. Root cause: `engine/confidence.py` imported `from engine.patterns.common import RSI_NEUTRAL_ZONE, rsi, sma` at module level; reaching into `engine.patterns.common` forces Python to first execute `engine/patterns/__init__.py`, which imports all 25 detectors, every one of which does `from engine.confidence import confidence_score` — while `engine.confidence` is still mid-execution of that very same top-level import line, so `confidence_score` (defined further down the file) doesn't exist yet. This only ever worked by accident of import order: every existing entry point happened to import `engine.patterns` (or something that does) before anything imported `engine.confidence` on its own — `agents/context.py` was the first module to import `engine.confidence` first. Fixed by making the two imports lazy (inside `trend_alignment`/`rsi_confirmation`, the only two functions that use them) rather than at module level — by the time either is actually *called*, `engine.confidence`'s own module-level code has already finished running, so the cycle never closes. Verified via `python -c "import engine.confidence"` / `import agents.context` / `import engine.patterns"` each succeeding standalone, plus the full test suite.
- **`agents/prompts/explainer_system.txt`** restructured from 4 to 5 sections: **Detection** (figure + detection date), **Confidence scoring** (the final number plus its 4 real components and their weights — explicit `None`-handling instruction for older patterns without them), **Fibonacci levels** (its own section now, rather than folded into "éléments de confirmation" — explicit instruction to say so when a pattern type has none, e.g. continuation/breakout/candlesticks), **Éléments de confirmation additionnels** (anything else in context not already covered), **Risques identifiés** (unchanged). Rule 1 (never cite a number absent from context) already covered these new fields with no change needed — only the structural instruction changed. `agents/prompts/jane_second_opinion_system.txt` was deliberately left untouched: Jane's note is a concise 3-5 sentence contradictory read, not a structured breakdown report, and the user's request was specifically about George's own explanation.
- **A second real discrepancy caught during live verification, before shipping**: `patterns_detected.confidence` is very often NOT the weighted sum of the 4 sub-scores above — `engine/run_detection.py` overrides a detector's own heuristic `confidence_score(...)` result with `engine/scoring.py:predict_confidence`'s XGBoost prediction whenever a trained model is available and the title has enough history (true for effectively every pattern now, since `price_history_long` gives every symbol 200+ bars). Concretely: a real ALO.PA Breakout had sub-scores geometry=0.797/volume=0.0/trend=0.5/rsi=1.0 (heuristic weighted sum ≈ 61.9%) but a stored confidence of **22.4%** — the learned model, not the formula. Telling George to state "the final score is the weighted sum of these components" would have been false in this (the common) case. Fixed at the source: `engine/scoring.py:predict_confidence` now returns `(confidence, source)` where `source` is `"heuristique"` or `"modele_appris"` (its one real caller, `engine/run_detection.py:run`, was updated to unpack this and store `confidence_source` in `patterns_detected.context`), forwarded as `context["pattern"]["source_confiance"]`, and the prompt branches on it: cites the weighted-sum equivalence only when `"heuristique"`, otherwise presents the sub-scores as "the technical factors that informed the analysis" without claiming they reproduce the final number.

Live-verified against the real Supabase database: re-ran `engine.run_detection` (confirmed every fresh pattern now has `confidence_source`, all currently `"modele_appris"` in production — no title lacks a trained model or sufficient history anymore), then a real Mistral call for the ALO.PA Breakout above produced a correct, internally-consistent 5-section explanation that explicitly attributed 22.4% to "le modèle statistique entraîné de George" and presented the sub-scores as contributing factors rather than a false arithmetic equivalence.

## Auto-learn: automated confidence-model retraining (`engine/train_confidence_model.py`) — ad hoc, not a roadmap phase

Requested directly by the user ("create a process the LLM can auto learn") — clarified via `AskUserQuestion` into what it actually maps onto in this codebase: there is no fine-tunable LLM in George (Mistral is a stateless hosted API call), so the only real "learned" component is the XGBoost confidence model (Phase 2). Two scope points confirmed directly with the user: automate *this* model's retraining, and keep a human validation gate before a retrained model ever reaches production (a bad retrain would otherwise silently degrade real Achat/Alléger recommendations) — same "propose, never auto-execute" discipline already used for Achat/Alléger decisions themselves.

- **A real, significant discovery made before building anything, changing the whole plan**: the XGBoost model has likely *never actually run in the deployed/scheduled system*. `engine/models/*.joblib` was fully gitignored — it only ever existed on this local dev machine (leftover from earlier manual notebook runs), never in git, never on Render, and never in the GitHub Actions runner (fresh checkout every run). Since `engine.run_detection` only ever executes via that scheduled workflow (or manually), and the workflow had no model file to load, `engine.scoring.load_latest_model()` always returned `(None, None)` there — every *scheduled* production detection run has always silently fallen back to the plain heuristic score; the learned model only ever activated when someone (in this session, Claude) ran detection locally by hand. Confirmed via `AskUserQuestion`: fix by tracking the *promoted* model in git (not a new storage dependency) so the workflow's checkout actually has it.
- **Another real, concrete gap found while first trying to retrain**: `python -m engine.build_training_set` against production returned **0 backtestable samples** — every pattern in `patterns_detected` had been detected within the last 2-3 trading sessions (the RSI/candlestick/price_history_long work in this same session is only days old), nowhere near `TRAINING_HORIZON` (10 sessions) of hindsight needed to know a pattern's outcome. Not a bug — retraining today would just reproduce the same 800-sample synthetic placeholder the currently-deployed model was trained on (`dataset_source: "synthétique (démonstration)"`, accuracy 0.56 / ROC AUC 0.57 — barely above chance). Real training data becomes available only once enough patterns age past 10 sessions (~mid-August from the earliest current detections) — the automated pipeline below is built now so it's *ready* the moment that happens, not run manually today for a result with no real value yet.
- **`engine/train_confidence_model.py`** ports `engine/notebooks/train_confidence_model.ipynb`'s training logic (dataset loading with synthetic fallback, sklearn `ColumnTransformer`+`XGBClassifier` pipeline, train/test split, accuracy/ROC AUC) into an importable, automatable module — the notebook now imports `load_dataset`/`CANDIDATES_DIR` from here rather than duplicating the logic, so notebook and CI stay identical by construction. `train_candidate()` **always saves to `engine/models/candidates/`**, never directly to `engine/models/` (the live location `engine/scoring.py:latest_model_path` actually reads — its glob doesn't recurse into subdirectories, so a candidate is structurally invisible to production until explicitly promoted) — and returns a comparison report (candidate metrics vs. the currently-live model's, read from its `.meta.json`) rather than just the candidate's own numbers, so a promotion decision is never made on the candidate's score in isolation.
- **A second real bug caught by actually executing the (refactored) notebook end-to-end**, not assumed: `KeyError: "['rsi_14'] not in index"` — the synthetic-dataset generator predates `rsi_14` being added to `NUMERIC_FEATURE_COLUMNS` (Kabbaj synthesis pass) and was never updated, so `dataset[FEATURE_COLUMNS]` failed the moment RSI became a required feature column. This had been silently broken since that RSI pass — nobody had re-run the notebook since. Fixed by adding a plausible `rsi_14` column to `make_synthetic_dataset` (centered above/below the neutral zone by pattern direction, same convention as the other pre-biased synthetic features); verified by actually executing the notebook via `jupyter nbconvert --to notebook --execute` (not just importing the module) and confirming the new tests catch this class of regression directly (`test_make_synthetic_dataset_has_every_feature_column`, iterating `FEATURE_COLUMNS` rather than hardcoding column names, so a future feature addition can't silently repeat this).
- **`engine/promote_candidate_model.py`** is the human validation gate itself: `python -m engine.promote_candidate_model [stamp]` copies (never moves — the candidate stays available for audit) a candidate's `.joblib`+`.meta.json` from `candidates/` into `engine/models/`, making it live at the next `engine.run_detection`. Deliberately does **not** `git add`/commit/push itself — same "confirm before an irreversible-ish shared-state action" discipline as the rest of this project; the human runs it, reviews the result, then commits/pushes explicitly.
- **`engine/scoring.py:_latest_model_path` renamed to `latest_model_path`** (dropped the leading underscore) — it's now a genuinely shared utility between `engine/scoring.py` (production inference) and `engine/train_confidence_model.py` (the comparison report needs to know exactly which file inference would actually load), not a private implementation detail of one module. Deliberately not duplicated the way `ohlcv.py`'s tiny `_to_aware` is elsewhere in this codebase — this one carries real glob/sort logic worth keeping as one source of truth rather than risking drift between two copies.
- **`.gitignore`** changed from blanket-ignoring `engine/models/` to ignoring only `engine/models/candidates/` — the promoted model files directly under `engine/models/` are now tracked, which is precisely what makes them reach the GitHub Actions checkout. The current local models (previously never committed) were promoted and committed as this pass's starting point.

## MACD, Bollinger Bands & Stochastic (`engine/patterns/common.py`, `engine/confidence.py`, `engine/features.py`, `engine/exit_levels.py`, `agents/context.py`, `mobile/lib/core/indicators/`, `mobile/lib/features/univers/widgets/candlestick_chart.dart`) — ad hoc, not a roadmap phase

## `web/` — the front-end app

### Commands
Run from `web/`:

### Stack
Vite + React 19 + Tailwind CSS v4 (via `@tailwindcss/postcss`) + Recharts (donut chart in Paniers) + [`@tanstack/react-query`](https://tanstack.com/query) (all API calls/caching — task 9 of the Phase 3 prompt) + Vitest/React Testing Library/jsdom (dev-only, task 10). No router — view switching is plain `useState` in `App.jsx`. No `lucide-react` any more (dropped with the Paniers rewrite below — check before re-adding an icon library that nothing else needs it).

### Architecture
- **`src/api/client.js`** is a thin `fetch` wrapper (`apiFetch(path, params)`) — throws on any non-OK response so React Query's `isError` fires correctly. **`src/api/queries.js`** has one React Query hook per API endpoint (`useSecurities`, `useSecurityPatterns`, `useSecurityPrices`, `useBaskets`, `useGeorgeIndex`, `useDecisions`, `useAgentActivity`). There's no batch endpoint for "pattern + price history for N securities at once", so `WatchlistRow` and `GeorgeIndexTile` each call their own per-item hook — real N+1 request behavior, acceptable at CAC-40 scale, called out in `queries.js`'s docstring as something to revisit if the tracked universe grows a lot.
- **`src/components/CandlestickChart.jsx`** no longer generates synthetic candles from a seeded PRNG (that whole approach — and `src/lib/ohlc.js` — is gone). It now takes real `candles` (from `/securities/{symbol}/prices`) plus the real `context` dict from `patterns_detected`/`PatternOut.context`, and derives the overlay generically from that context's shape rather than regex-matching the pattern name: a `{index, price}` value becomes a marker (translated by the `indexOffset` prop — see the API section above for why that offset is needed), a `{points, price}` value (a neckline) becomes markers *and* a horizontal line, and a bare number under the key `resistance`/`support` becomes a line with no marker. No context at all (no active pattern) means no overlay at all — it no longer fabricates one from local extrema, unlike the Phase-3-prototype version. `takeProfit`/`stopLoss` are now absolute prices (from `Decision`), not the old `tpPct`/`slPct` percentages off a synthetic last close.
- **`src/views/Univers.jsx`** fetches `useSecurities`, `useDecisions` (built into a `symbol -> most-recent-decision` map client-side — there's no per-symbol decision filter on the endpoint, and the full list is small enough to fetch once), `useBaskets`, `useAgentActivity` at the top level; `WatchlistRow`/`GeorgeIndexTile` (in `src/components/`) own their own per-item queries. The George Index tile grid always renders exactly 2 slots (real tile, or an empty filler `<div>`) plus the macro tile — the grid's `gridTemplateColumns` is the fixed `"150px 150px 1fr"`, so a *variable* number of basket tiles (0, 1, vs. 2) shifts the macro tile into the wrong column; the empty-baskets message instead spans both slots via `col-span-2`. Distinguishes "API unreachable" (`isError`) from "DB reachable but empty" (`data.items.length === 0`) with two different messages — collapsing them into one generic empty state would hide a real connectivity problem.
- **`src/views/Paniers.jsx`** was rewritten from a fictive-portfolio simulator (invented capital, position weights, cash reserve — none of that has a backing table in the schema) into a real-data basket/decision browser: George Index per basket (bars, real), universe breakdown by `sector` (donut, real, computed client-side from the single `/securities` fetch rather than a per-basket count query), and a real `/decisions` table. Same "unreachable vs. empty" distinction as `Univers.jsx` (`apiUnreachable = basketsError || securitiesError || decisionsError`).
- **`src/data.js`** now only holds the `decisionColor`/`scoreColor` helpers shared by both views — the last fictive placeholder (`macro`, a rates/indices/FX tile with no backing table) was removed once the Energy Market feature (see its own section below) gave the equivalent "Repères macro" tile a real backing table (`GET /energy-prices`). Everything else that used to live here (`positions`, `georgeIndex`, `agentEvents`, `CAPITAL`) is gone now that real data is wired up.
- **Theming** is CSS custom properties defined once in `src/index.css` (`--bg`, `--panel`, `--positive`, `--negative`, etc.), consumed via inline `style={{ color: "var(--x)" }}` or Tailwind arbitrary values rather than a Tailwind theme extension. Keep new components consistent with this pattern instead of introducing hex literals or extending `tailwind.config`.
- **Tests** (`*.test.jsx` next to the files they cover) mock `../api/queries` wholesale with `vi.mock` rather than standing up a `QueryClientProvider` + mocking `fetch` — simpler, and sufficient since the hooks themselves are trivial wrappers with no logic of their own to test. `vi.mock` is keyed by resolved module path, so mocking `"../api/queries"` from e.g. `Univers.test.jsx` also mocks it for `WatchlistRow`/`GeorgeIndexTile` that `Univers` renders, even though those files import it via the same relative specifier resolving to the same file — no separate per-component mock wiring needed.

## Mobile app (Flutter) — ad hoc, not a roadmap phase

Requested directly by the user as "Flutter + Firebase" rather than the roadmap's own Phase 5 spec (React Native/Expo + Firebase Cloud Messaging + Piper/Coqui TTS, see `George_Prompts_Claude_Code.md`). Built as a deliberately scoped-down V1 MVP with explicit user sign-off (plan mode) — same precedent as the Phase 7 scale-down: 3 screens mirroring `web/`'s functionality against the existing FastAPI backend, no push notifications, no native TTS/STT, no offline cache, no daily digest, no authentication. `mobile/` was a one-line placeholder README before this; it's now a real `flutter create` scaffold (`--org com.george --project-name george_mobile --platforms=android,ios`).

- **No Firebase in V1, deliberately** — flagged directly to the user rather than added for its own sake: FCM (push) and Firebase Auth are the only two Firebase products that would organically fit this app, and both are explicitly out of scope for V1 (no push infra, no auth anywhere in the backend yet — Phase 9 of the roadmap, not built). Adding Crashlytics/Analytics just to "use Firebase" would be contrived scope with no backend equivalent to match (`web/` has no crash reporting either). Firebase gets wired in during a V2 that actually tackles push notifications.
- **No authentication in V1** — the app calls the API directly, no login screen, matching the backend's current reality: no auth exists anywhere (see the API section above, `api/main.py`'s "Pas d'authentification à ce stade" comment), portfolios are globally shared, not per-user.
- **State management: Riverpod** (`flutter_riverpod`), not BLoC/plain `Provider` — chosen as the closest analogue to `web/`'s React Query pattern: one `FutureProvider.family` per API resource (mirroring one `useX` hook per resource in `queries.js`), with mutations calling `ref.invalidate(...)` on success instead of `queryClient.invalidateQueries(...)`. `lib/data/invalidate_all.dart:invalidateAllData` is the direct analogue of `useRefreshPrices`'s "invalidate everything" comment — `ref.invalidate(provider)` on a `.family` provider invalidates every parameterized instance, not just one. **Riverpod 3.x API gotcha hit while building this**: `AsyncValue.valueOrNull` from Riverpod 2.x is gone — the plain `.value` getter is now nullable and fills that role (`AsyncValue<T>.value` returns `T?`, never throws). Also, `StateProvider` moved to `package:flutter_riverpod/legacy.dart` in 3.x; rather than pull in that import for a single screen-local filter chip (purely UI state, not server state), `UniversScreen` uses a plain `ConsumerStatefulWidget` with local `setState` instead — no Riverpod provider needed for state that isn't shared/server-derived.
- **API client: hand-written, not codegen'd from `/openapi.json`** — `lib/core/api_client.dart` mirrors `web/src/api/client.js`'s 3-verb wrapper (`get`/`post`/`delete`) exactly, and `lib/models/*.dart` are hand-transcribed from `api/schemas.py` field-by-field, same discipline as the web client's implicit JSON destructuring. Chosen over `openapi-generator`/chopper/retrofit because the API is small (~9 resources, one shared `Page[T]` envelope) and has free-form `dict` fields (`PatternOut.context`, `AgentEventOut.context`) that would generate poorly as strict Dart classes anyway. **Naming collision worth knowing about**: the hand-written generic pagination wrapper is named `Page<T>` (mirroring `api/schemas.py:Page[T]`) — this collides with Flutter's own `widgets.dart:Page` class (used by `Navigator`'s Pages API) the moment a file imports both `package:flutter/material.dart` and `models/page.dart` and references `Page<T>` by name (hit in `test/features/paniers_screen_test.dart`); fixed there with `import '.../models/page.dart' as model;` rather than renaming the model class, since no non-test file needs both imports together.
- **Long-running calls get an explicit per-call timeout override, not a longer global default** — `/agents/collect`, `/decisions/{id}/explanation`, and `/chat` pass `receiveTimeout: Duration(seconds: 90-120)` on the specific `ApiClient` call rather than raising the shared `Dio` instance's default (15s connect / 30s receive) — same "surface real errors fast" reasoning as `retry: 0` in `web/src/main.jsx` and `connect_timeout=5` in `ingestion/db.py`. `/prices/refresh` no longer needs this override: it was made asynchronous (see the "Named portfolios" section below) after its old synchronous, up-to-2-minute call routinely exceeded even this override once the backend was repointed at 10 years of price history — `PricesRefreshRepository.refresh()` now polls a status endpoint instead, bounded by its own `_maxWait`/`_maxConsecutiveErrors` guards rather than a single fixed HTTP timeout.
- **`lib/shared/widgets/response_dialog.dart:showResponseDialog`** is the mobile analogue of `web/src/components/ResponsePopup.jsx` — one dialog (loading/done/error, parameterized `loadingText`) reused for every LLM/long-running action (decision explanation, chat, price refresh, macro collection, budget allocation) instead of a bespoke dialog per screen.
- **`lib/features/univers/widgets/candlestick_chart.dart`** is a direct `CustomPainter` port of `web/src/components/CandlestickChart.jsx`'s hand-rolled SVG chart (there's no off-the-shelf Flutter candlestick chart in `fl_chart`) — same `buildOverlay` logic (markers from `{index/points, price}` context entries, horizontal lines for `resistance`/`support` keys), same generic "derive from `context`'s shape, not the pattern's name" principle called out in the original component's own comment.
- **`lib/features/decision_detail/`** is a pushed screen (`Navigator.push`, not a `go_router` route) rather than `web/`'s 3rd desktop column — mobile has no room for a persistent 3-column layout, and a plain imperative push was simpler than wiring a nested `go_router` route for a single non-deep-linked destination.
- **`DataTable` + horizontal `SingleChildScrollView`** renders each portfolio's decisions table in `lib/features/portefeuille/portefeuille_screen.dart` — same reasoning as `web/`'s `overflow-x-auto` on a `min-width: 840px` table (too many columns for a narrow viewport either way, scroll rather than cram).
- **Budget allocation uses a plain numeric `TextField`, not voice** — `web/`'s `MonPortefeuille.jsx` parses a spoken euro amount via `useVoiceCapture` + a regex (`parseBudgetFromText`); mobile's budget dialog still just takes a number directly, unrelated to the `speech_to_text` package added later for "Ask Jane" (see below) — porting the budget flow to voice too wasn't part of that change and remains unscoped.
- **Testing**: no dedicated hook tests (this codebase's `web/` doesn't unit-test its React Query hooks either — they're trivial wrappers) — widget tests per screen (`test/widget_test.dart`, `test/features/paniers_screen_test.dart`, `test/features/portefeuille_screen_test.dart`) override the relevant Riverpod providers with fake data instead of letting a real HTTP call fire, same principle as `web/`'s wholesale `vi.mock("../api/queries")`. A provider left un-overridden in a test (e.g. `georgeIndexProvider` in the Paniers test) still resolves safely to its `AsyncValue.error` branch — Flutter's test `HttpClient` returns a fake 400 for any real request rather than hanging, so an un-mocked provider degrades gracefully instead of timing out the test.
- **Networking for local dev**: `mobile/README.md` documents the `--dart-define=API_BASE_URL=...` mechanism (no `flutter_dotenv` — Flutter's native build-time define mechanism already solves this, no extra dependency needed) and the three environments that actually differ (Android emulator needs `10.0.2.2`, not `localhost`; iOS simulator can use `localhost` directly; a physical device needs the host machine's real LAN IP plus `uvicorn --host 0.0.0.0`). CORS (`api/main.py:allow_origins`) is a browser-only mechanism and doesn't apply to native Android/iOS builds at all — only relevant if a Flutter *web* target is ever added.
- **`android/gradle.properties`'s default `org.gradle.jvmargs=-Xmx8G ...`** (from the stock Flutter Android template) crashed the Gradle daemon with an out-of-memory native allocation failure on this dev machine (7 GB total RAM, well under 8 GB) — lowered to `-Xmx2048m -XX:MaxMetaspaceSize=1g -XX:ReservedCodeCacheSize=256m`, which built `flutter build apk --release` successfully. Worth checking first if a release/debug APK build mysteriously fails with "Gradle build daemon disappeared unexpectedly" plus a `hs_err_pid*.log` crash dump in `android/` — that log's own "Out of Memory Error" / "insufficient memory... to continue" message is the tell, not a code problem.
- **Distributing a build for manual testing (e.g. Firebase App Distribution)** needs no Firebase SDK/`google-services.json` in the app itself — the release APK (signed with the debug key by default, see `android/app/build.gradle.kts`'s `signingConfig = signingConfigs.getByName("debug")`, fine for internal testing, not for a Play Store release) is a self-contained artifact; the Firebase project only needs the app registered (package name `com.george.george_mobile`) to accept an upload via the console's drag-and-drop, no CLI/build integration required for a one-off test distribution.

## DeepSeek fallback (`agents/mistral_client.py`) — ad hoc, not a roadmap phase

Added directly in response to a real production incident (Sept. 2026): Mistral's free-tier rate limit (`429`, `code: 1300`) blocked `/chat`, `/jane/ask`, and `/decisions/{id}/explanation` for hours, confirmed via Render logs and a direct `curl` reproduction against the account's own key.

- **`complete()`/`complete_vision()` try Mistral first, unchanged** — DeepSeek is only called after Mistral's own `_complete_with_messages` exhausts `max_retries` and raises `MistralUnavailableError`. A single DeepSeek attempt, no retry loop of its own, to bound total latency on an already-failed call. `embed()` is untouched — DeepSeek has no embeddings endpoint, so pgvector indexing (`agents/reports.py`) stays exclusively on `mistral-embed`.
- **`DEEPSEEK_API_KEY` is optional** — same lazy-read-at-call-time convention as `MISTRAL_API_KEY`/`SUPABASE_URL`: unset, the fallback is silently skipped and the original `MistralUnavailableError` propagates exactly as it did before this change, so every existing test/environment without the new var is unaffected. Verified live with a real key (`platform.deepseek.com`, not the look-alike third-party site `mydeepseekapi.com` initially and mistakenly navigated to — flagged and avoided): `deepseek-chat` (aliases to `deepseek-v4-flash`), `deepseek-reasoner` (same model, chain-of-thought enabled — used for `MODEL_LARGE`/Jane, closer to a "second opinion" role than plain explanation), and the still-experimental `deepseek-v4-flash-vision-exp` (for `complete_vision`, used by `agents/jane_veille.py`) all confirmed reachable with this key.
- **`complete_vision`'s image content has to be reshaped for DeepSeek, not reused as-is**: Mistral accepts a bare string for `image_url` (`{"type": "image_url", "image_url": "data:..."}`), but DeepSeek's OpenAI-compatible endpoint expects a nested object (`{"image_url": {"url": "data:..."}}`) — confirmed by reading DeepSeek's own vision docs, not assumed; the fallback path builds its own `messages` from `user_text`/`image_data_uris` rather than reusing Mistral's already-built list.
- **No dedicated exception class added** — the fallback still raises `MistralUnavailableError` on total failure (both providers exhausted), deliberately reusing the existing class rather than introducing `DeepSeekUnavailableError`: `api/main.py`'s existing Starlette-CORS-safe 503 handler already targets `MistralUnavailableError` and needed no change.
- **`complete(..., allow_fallback=True)`** — real bug caught by `/code-review` before this shipped: the fallback's extra DeepSeek attempt (up to a 60s timeout) directly contradicted the explicit "must never block" contract of `agents/jane.py:reformulate_formal` and `agents/email_formatter.py:format_email_body`, both of which exist specifically to fail fast and return the raw, unformatted text rather than delay an already-complete result. Both call sites now pass `allow_fallback=False`, which makes `MistralUnavailableError` propagate immediately, exactly as before this change — every other caller (explainer, chat, Jane's second opinion/veille, reports, synthesis) keeps the default `True` and benefits from the fallback.
- **`tests/test_mistral_client.py`** (new) covers the fallback in isolation — `_complete_with_messages` and `httpx.post` both monkeypatched, no network/DB — including the "no `DEEPSEEK_API_KEY`" no-op path and the vision content-reshaping.

## Web search fallback for Ask Jane (`agents/web_search.py`) — ad hoc, not a roadmap phase

Requested directly by the user right after the DeepSeek fallback above: when `jane_knowledge` doesn't cover a question, Jane should search the web instead of just declining to answer.

- **Via Tavily** (tavily.com) — chosen for its free tier and because it's purpose-built for this exact use case (clean title/content/URL results meant for LLM context injection, no HTML scraping needed). `agents/web_search.py:search()` is a single HTTP call, same shape as `agents/collectors/macro.py`'s fetchers — deterministic, no LLM involved in deciding whether/what to search.
- **Both sources are always fetched, never a Python-side "if knowledge base found nothing" branch**: `jane_knowledge.search_jane_knowledge`'s `ORDER BY cosine_distance LIMIT N` always returns N rows if the table has that many, regardless of actual relevance — there is no distance/similarity threshold anywhere in that function. Counting matches in Python therefore can't reliably signal "nothing relevant." Instead, `agents/jane.py:ask` always sends both `connaissances_pertinentes` and `resultats_web` to the LLM, and the updated `agents/prompts/jane_ask_system.txt` instructs Jane to judge relevance herself: prefer the knowledge base when it's genuinely relevant, fall back to web results (citing the URL) when it isn't, and say honestly that she doesn't know when neither source actually answers the question.
- **`TAVILY_API_KEY` is optional**, same convention as `DEEPSEEK_API_KEY`/`MISTRAL_API_KEY`: unset, `search()` returns `[]` immediately with no network call, so every existing test/environment without the new var is unaffected.
- **A failed web search never fails the whole answer**: `agents/jane.py:ask` catches `WebSearchUnavailableError` and degrades to an empty `resultats_web` list — same "never let an enrichment step block or fail a request that would otherwise succeed" principle as the `allow_fallback` guard on `mistral_client.complete` above.
- **`tests/test_web_search.py`** (new) covers `search()` in isolation (`httpx.post` monkeypatched); `tests/test_api.py::test_ask_jane_falls_back_to_web_search_results` (new, needs Docker) verifies the web results reach the LLM's context alongside the existing knowledge-base tests.

## `/chat` web search fallback for securities outside the tracked universe (`agents/chat.py`) — ad hoc, not a roadmap phase

Requested directly by the user: "je veux pouvoir poser des questions sur des sociétés/entreprises en dehors de la liste actuelle (~120 CAC 40/Mid 60)." Same mechanism as the Ask Jane web-search fallback above, applied to George's own `/chat`.

- **`answer_question` calls `agents.web_search.search(question)` only when `find_relevant_securities` recognized nothing** in the tracked universe — unlike Ask Jane (which always fetches both sources, since `jane_knowledge` has no relevance threshold), `find_relevant_securities`'s word-boundary symbol/name match is a hard, reliable "found or not" signal, so there's no need to fetch web results when a tracked title was already recognized.
- **`chat_system.txt` keeps the two sources strictly separate**, and says so explicitly to the model: `titres_reconnus` is George's real quantitative analysis (pattern detection, confidence score, decision levels); `resultats_web` is generic web information for a company George's engine has never analyzed. The prompt requires George to say up front that an untracked company has no figure/score/decision from him before answering from web results, and never to blend a web fact into the same sentence as a `titres_reconnus` figure. Same "cite what's confirmed by multiple sources, flag single-source claims" discipline as `jane_veille_web_system.txt`.
- A failed web search (`WebSearchUnavailableError`, or `TAVILY_API_KEY` unset) degrades to `resultats_web: []`, same as everywhere else this session added a Tavily call — never blocks `/chat` from answering.
- **The live fallback's query is enriched with generic terms** (`f"{question} société entreprise"`, not the bare `question`) — found live, via the app: a short/ambiguous company name alone (e.g. "Haffner" instead of "Haffner Energy") gave Tavily too little context and came back with poor or zero results, surfacing as George saying he found nothing at all rather than surfacing a real summary.
- **Analysis broadened to economic outlook, sector, and contracts** — requested directly by the user after confirming the web fallback worked: `_fundamentals_summary` (`agents/chat.py`) adds a `fondamentaux` key (sector, industry, business summary, market cap) to every `titres_reconnus` entry, sourced from `company_fundamentals` (already populated daily by `ingestion/fundamentals.py` for the "Fondamentaux" feature — no new data pipeline needed, just a new read). The live web-search query and `agents/george_veille.py:collect_company_news`'s query both gained "perspectives économiques secteur contrats" (verified live against Tavily: still 5 relevant results, no degradation from the longer query). `chat_system.txt`/`george_veille_system.txt` instruct George to cover these angles only when the actual source data supports it — never inferred from a general sector label.
- **App-wide logging bug found while diagnosing the "Haffner" case above, fixed in `api/main.py`**: `logging.basicConfig(level=logging.INFO)` was never called anywhere in this project — Python's un-configured root logger defaults to `WARNING`, so every `logger.info(...)` call in the codebase (a new diagnostic line added to `agents/chat.py`'s web-search fallback, plus any other pre-existing one) was silently dropped from Render's logs, while `logger.warning`/`.error`/`.exception` (the pattern already used by the existing exception handlers) worked fine — which is exactly why this gap went unnoticed until an `.info()` call specifically needed to be seen. The enriched-query fix above was verified working via direct Tavily API calls, but the deployed `/chat` endpoint still returned zero web results for a real user question with no error surfacing anywhere — this logging gap is why nothing showed up to explain it. Fixed at the application level (`api/main.py`, once, at import time) rather than per-call-site.
- **The real root cause, found only after the logging fix made it possible to see that `agents.web_search`/Tavily was never even being called**: `find_relevant_securities`'s name-matching branch (`s.name.lower() in question_lower`) had no word-boundary protection — unlike its symbol-matching sibling, already fixed once for the exact same class of bug (`test_chat_does_not_false_positive_match_short_symbol_roots_inside_words`, "ac" inside "achat"). A tracked security is literally named **"SES"** (SESG.PA), a 3-letter substring of the ordinary French word "pen**ses**" — so any question containing "penses" (a very common verb form, "que **penses**-tu de X ?") falsely matched SES as a recognized title. With `titres_reconnus` non-empty, `answer_question`'s entire "nothing recognized" branch (biofuel lookup + live web search) was skipped outright — explaining why asking about "Haffner" via a "que penses-tu de..." phrasing never reached Tavily at all, silently and with a plausible-sounding wrong answer, not an error. Fixed by wrapping the name comparison in the same `\b...\b` word-boundary regex already used for symbols (verified to still match multi-word names like "Alpha SA" correctly). Regression test: `test_chat_does_not_false_positive_match_short_names_inside_words`.

- **Scheduling**: `.github/workflows/weekly_geopolitical_veille.yml`, Sunday 22:00 UTC — the first version used 21:00 UTC "to avoid stacking with other weekly jobs" but missed that `daily_george_veille.yml` also fires at 21:00 UTC *every* day including Sunday; caught by `/code-review`, moved to the one genuinely free Sunday slot (06:00 energy, 20:00 fundamentals+confidence-model already collide with each other pre-existing, 21:00 company veille).
- **`agents/chat.py:answer_question` integration**: new `actualites_geopolitiques` context key, semantic search like `connaissances_apprises` — no relevance threshold, always queried, degrades to an empty list on a Mistral outage. **Shares one embedding call with `connaissances_apprises`** rather than embedding the same question twice (`mistral_client.embed([question])` once, `query_embedding=` passed to both `search_jane_knowledge` and `search_geopolitical_knowledge`, both of which gained that optional parameter defaulting to `None`/computed-if-absent) — a first version called `embed` separately in each of two `try/except` blocks, caught as a real doubled-latency/cost issue by `/code-review`, not just a style nit. `chat_system.txt` updated accordingly (eight context parts now).
- **`agents/gdelt_client.py` (GDELT, added later, requested directly by the user)** — free/keyless systematic keyword search over GDELT's global news index, in complement to Tavily's handful of curated results. **Integrated into the SAME `collect_geopolitical_news` Mistral call as Tavily, not a separate table or a parallel flow** (explicit choice put to the user, given the real overlap with Tavily's own "tensions sociales, conflits" query terms): `tavily_results + gdelt_results` are concatenated before the single `sources_payload`, so both sources get cross-referenced by the same anti-hallucination rules in one synthesis rather than needing reconciliation elsewhere. Two structural differences from Wchecks' own `clients/gdelt_client.py`, both deliberate: (1) **no scraping** — Wchecks scrapes every article URL (`article_scraper.py`) because GDELT's Doc API returns no page text, but this project has never added that capability; here, `extrait` is always `""` and only the real article title is passed to Mistral (a poorer signal than Tavily's extracts, but a real headline is still usable, and the prompt's existing single-source-attribution rule already covers thin evidence) — (2) **country-scoped by construction, not resolved after the fact** — Wchecks searches globally by category then resolves each result's country from the publishing outlet's location (`sourcecountry`, via `mapping/country_mapping.py`, unported), which is both a whole module this project doesn't have and structurally the wrong signal (the outlet's country, not the event's); this client instead puts the country name directly in the GDELT query as a literal AND-ed term (`'"{country}" (kw1 OR kw2 OR ...)'`), searching FOR the country already chosen by `_pick_weekly_countries` rather than inferring one. No full translation layer (Wchecks uses Gemini's `translate_batch` on article content) — Mistral synthesizes directly from non-French titles, same as it already does for non-French Tavily extracts; only the query term itself is translated (see `/code-review` fix below), not the results. GDELT is free, so unlike Tavily it's queried unconditionally, no budget accounting needed; 429s retried with backoff (`MAX_RETRIES=3`), same tolerant "log + skip" ethic as every other collector in this project.

  `/code-review`'s first pass on this integration caught 3 real bugs, all fixed: (1) GDELT's Doc API is restricted to `sourcelang: english`, but `country` comes from `whitelist_journaux.json` in French ("Allemagne", "Chine (officiel)") — AND-ing a French term against English-only results returned almost nothing for most of the 77-country whitelist. Fixed with a `GDELT_COUNTRY_NAMES` French→English dict (all 77 whitelist entries, verified by exact key-set match) that `search_articles` resolves through before building the query (`GDELT_COUNTRY_NAMES.get(country, country)`, falling back to the raw name for anything outside the whitelist — same tolerant ethic as `mapping/country_mapping.py` at Wchecks, not ported wholesale since this client only ever needs the 77 whitelist countries). (2) `source_name` said "+ GDELT" unconditionally, even when `gdelt_results` came back empty — misrepresented provenance; now conditional on `gdelt_results` being non-empty. (3) The docstring claimed a source failure "never raises an exception", but `web_search.search()` can raise `WebSearchUnavailableError` uncaught from Tavily — `collect_geopolitical_news` now catches it and degrades to an empty Tavily list, actually matching what the docstring claims (GDELT results alone still produce a synthesis). Chasing (3) also surfaced a latent bug in `agents/web_search.py` itself, pre-existing and unrelated to this feature but now actually triggerable via this new call site: its result-parsing list comprehension sat *outside* the function's own try/except, so a 200-OK-but-malformed Tavily payload (e.g. `{"results": null}`) raised a bare `TypeError` instead of `WebSearchUnavailableError` — fixed by moving the parsing inside the try block so any malformed-response shape is caught and converted like every other Tavily failure mode.

  22 tests total across the touched files (`tests/test_gdelt_client.py`: 9, including the French→English translation and unmapped-country-fallback cases; `tests/test_geopolitical_veille.py`: 4 new cases — Tavily+GDELT merge, both-sources-empty, GDELT omitted from `source_name` when it found nothing, Tavily-unavailable-falls-back-to-GDELT — alongside the 7 pre-existing `_load_countries`/`_pick_weekly_countries` tests; `tests/test_web_search.py`: 1 new regression case for the malformed-payload fix), all genuinely run and passing — network entirely mocked, no live call to `api.gdeltproject.org`/`api.tavily.com` made from the sandbox this was built in.
- **`tests/test_geopolitical_veille.py`** (pure — `_load_countries`/`_pick_weekly_countries`, including a genuine circular-wraparound case with `datetime.now` mocked, same pattern as `tests/test_george_veille.py`) and **`tests/test_geopolitical_knowledge.py`** (Docker/testcontainers — roundtrip, same-country dedup, and a regression test that two different countries with identical content do NOT dedupe against each other) plus a `/chat` coverage addition in `tests/test_api.py`. Not verified against a real Postgres from the sandbox this was built in (no Docker daemon available there) — SQL compiled and inspected directly instead, and the pure test file was actually run.

## Live technical analysis for any company mentioned in `/chat` (`agents/external_analysis.py`) — ad hoc, not a roadmap phase

Requested directly by the user, explicit scope confirmed via a clarifying question ("n'importe quelle entreprise mentionnée dans le chat", not just the bounded biofuel list): a real technical-analysis figure, not just a web-search text summary, for any company George doesn't track.

- **Three independently-failable steps**, each degrading to `None` rather than blocking `/chat`: `extract_company_name` (LLM extraction of a company name from the free-form question — a short, bounded extraction task, not the "enumerate a long structured list" failure mode already documented for `mistral-small-latest` elsewhere in this file), `resolve_ticker` (`yfinance.Search`, already a project dependency — no new external service), `analyze_ticker` (downloads 10y history via `yfinance.Ticker(...).history()` and runs `engine.detect.detect_all` on it directly).
- **`extract_company_name` uses `allow_fallback=False`** — same "must degrade fast, never worth a 60s DeepSeek retry" contract as `agents/jane.py:reformulate_formal`/`agents/email_formatter.py:format_email_body`: a failed extraction should fall through to "no company found" quickly, not stall the whole `/chat` response.
- **`resolve_ticker` filters out warrants (BSA) and prefers a Paris listing when one exists** — verified live: searching "Haffner Energy" returns 5 candidates across 4 exchanges (Frankfurt, Düsseldorf, Stuttgart, Paris) plus one warrant ("HAFFNER ENERGY BSA"); the heuristic picks `ALHAF.PA`, the real common-stock Paris listing. This is a heuristic, not a guarantee — documented as such in the module docstring and in `chat_system.txt` (the ticker "was identified automatically", not confirmed).
- **`analyze_ticker` deliberately skips `engine.scoring.predict_confidence`** (the trained ML confidence model) — that model is trained on the tracked CAC 40/Mid 60 universe's own patterns/outcomes, and its applicability to an arbitrary company is unverified. Only the Phase 1 heuristic confidence (already built into `PatternMatch.confidence` by each detector, geometry/volume/trend-based, universally applicable by construction) is used — `detect_all` is a pure function with no DB dependency, already designed to run on any OHLCV DataFrame.
- **`chat_system.txt`'s new `analyse_technique_externe` context key** is kept explicitly distinct from `titres_reconnus`: George must name the ticker, note it has no decision/proposal/George Index attached, and never present it as equivalent to his regular tracked-universe analysis.
- **Test-suite gotcha found while wiring this in**: `mock_llm`'s `_fake_complete` test double didn't accept `allow_fallback`, and — since `mistral_client.complete` is globally monkeypatched for the whole test file — every existing "unrecognized security" test would otherwise have started making a real `mistral_client.complete` call through the fake, gotten back a nonsense "company name" (the echoed context string), and then hit a **real network call to `yfinance.Search`** for every single such test. Fixed by having `_fake_complete` recognize `external_analysis.EXTRACTION_SYSTEM_PROMPT` specifically and return `"AUCUNE"` by default; the one existing test using an exact biofuel-list name (`test_chat_finds_biofuel_company_knowledge_before_live_web_search`, "Neste" — which skips extraction entirely since the name is already known) needed an explicit `resolve_ticker` mock on top of that.

## "Teach George on the go" via `/chat` (`agents/chat.py:_extract_taught_knowledge`) — ad hoc, not a roadmap phase

Requested directly by the user: sending a message like "ajoute à tes skills cette information : <content>" through the normal `/chat` box should make George remember `<content>` and reuse it for future questions — a general learning mechanism, not a one-off seeding of the specific list the user provided as the example (financial-data sources per company type: Pappers.fr, Zonebourse.com, SEC EDGAR, INSEE.fr, etc.).

- **Reuses `agents/jane_knowledge.py` as-is** (`add_knowledge`/`search_jane_knowledge`, the same pgvector-backed store already used for Jane's methodological knowledge) rather than a new table — this is the same "general knowledge, not a backtested pattern candidate" concept the module's own docstring already describes, just written to from George's `/chat` instead of Jane's veille jobs. Cosine-distance dedup (`DEDUP_DISTANCE_THRESHOLD`) is inherited for free, so teaching the same fact twice doesn't grow the table.
- **Considered and rejected: restricting `agents.web_search`'s Tavily calls to the user's listed sites via `include_domains`.** Verified empirically with a direct `curl` call restricting a search for "Neste" (a Finnish company) to the user's French official/finance domain list: every result came back irrelevant (generic pages about unrelated companies) — confirming `include_domains` is a hard filter, not a ranking boost, and would have broken research for any company outside that French-centric site list. Simple knowledge storage was chosen instead, precisely because it doesn't touch how `web_search.search` itself queries Tavily.
- **Detection is a plain keyword/`:`-split heuristic (`_extract_taught_knowledge`), not an LLM call** — `TEACH_INTENT_KEYWORDS` (ajoute/retiens/mémorise/apprends/note ceci/note bien) matched only at the START of the text before the first `:` (`re.match`, not `re.search`), with everything after `:` stored verbatim as `content`. Unlike `external_analysis.extract_company_name` (which needs the LLM because company mentions are phrased too freely to keyword-match), a "please remember this" intent is unambiguous, and skipping the LLM here also avoids any risk of the model paraphrasing/losing part of what the user asked to memorize.
- **`/code-review` bug found and fixed: keyword matching anywhere in the sentence, not just at the start.** "ajoute"/"retiens" are also ordinary French verbs used mid-sentence in real financial questions ("un investisseur ajoute des actions Alpha SA à son portefeuille : quel est l'impact ?", "je retiens que le secteur est en croissance : qu'en penses-tu ?") — matching anywhere silently swallowed the real question as "taught content" instead of answering it. A word-boundary-only fix (`\b...\b`, same style as the two existing `find_relevant_securities` fixes) was tried first and found insufficient, since "ajoute" in that sentence already sits on its own word boundaries — the actual fix anchors the match to the *start* of the pre-`:` segment (`re.match`), since a genuine teach command is phrased as an imperative opening the message, never buried mid-sentence.
- **First check in `answer_question`, before security matching** — if `_extract_taught_knowledge` returns non-`None`, `add_knowledge` is called and a deterministic confirmation string is returned directly, no LLM call at all (same "restate already-computed data in Python" pattern as `_format_opportunities`, for the same reason: confirming a real DB write needs zero natural-language capability, and a fixed string can't hallucinate). Wrapped in a `MistralUnavailableError` catch (`/code-review` bug found and fixed: this write path calls `add_knowledge` → `mistral_client.embed`, and was the only Mistral-dependent branch in this file with no degradation — an outage bubbled all the way to the app's global 503 handler instead of a friendly in-band message) — degrades to "je n'ai pas pu enregistrer... réessaie plus tard" rather than a hard error. **No DeepSeek fallback here**: `embed()` is Mistral-only project-wide (see `mistral_client.py`'s own module docstring — "DeepSeek n'expose pas d'endpoint d'embeddings"), so unlike `complete()` there is no second provider to fall back to for this specific call; the in-band degradation message is the correct behavior, not a stopgap.
- **Learned knowledge feeds back into every other `/chat` answer**, not just questions about the topic it was taught under: `answer_question` now also runs `jane_knowledge.search_jane_knowledge(db, question, limit=3)` unconditionally (same "no relevance threshold, let the prompt decide" approach as `agents/jane.py:ask`) and passes the results as a new `connaissances_apprises` context key, documented in `chat_system.txt` as a note the investor asked George to remember — never presented as an official fact about a company. A failed embedding call (`MistralUnavailableError`) degrades to an empty list, same as every other optional `/chat` context source in this file. Note this adds a Mistral embedding round-trip to every `/chat` call, including ones a recognized tracked security would otherwise have answered with no extra network call — an accepted latency/cost tradeoff for making taught knowledge available everywhere, not gated behind `if not snapshots` like `resultats_web`/`analyse_technique_externe`.
- **Accepted, not fixed: taught content is stored verbatim with no per-user scoping or review**, and is later replayed into the LLM's context as a note it's told it "can use to steer its answer" (`chat_system.txt` rule 6) — functionally a persistent prompt-injection surface, since anyone with `/chat` access can plant text that influences every future answer. Flagged in `/code-review`; not changed because it's inherent to the feature as requested (a personal memory a single user teaches their own assistant), not an incidental bug — narrowing it (e.g. requiring confirmation before storing) would change the deterministic, no-LLM-call design the user asked for.
- **Test-suite gotcha**: `mock_llm`'s `_fake_embed` (`tests/test_api.py`) returns an identical all-zero vector for every text — fine for tests that never populate `jane_knowledge`, but a dedup test needs two *different* contents to land on genuinely different vectors, matching the pattern already established in `tests/test_jane_knowledge.py`'s `_fake_embed_factory`. New teach-intent tests that need real dedup/retrieval behavior override `mistral_client.embed` locally instead of relying on `mock_llm`'s uniform fake.

## Ask Jane (mobile) — floating button on the Univers screen (`agents/jane.py:ask`, `agents/prompts/jane_ask_system.txt`, `api/routers/jane.py`, `mobile/lib/features/univers/widgets/ask_jane_sheet.dart`) — ad hoc, not a roadmap phase

- **A third, distinct role for Jane**, unrelated to `second_opinion` (per-decision contradictory note) or `reformulate_formal` (stylistic pass on George's own explanation): a free-form question against `jane_knowledge` with no decision in scope at all. `agents/jane.py:ask` reuses `jane_knowledge.search_jane_knowledge` exactly like `second_opinion` does, but the RAG query is the user's own question (not `_knowledge_query`'s decision-type/pattern-type string) — the only other change was a new system prompt (`agents/prompts/jane_ask_system.txt`) instructing Jane to say so plainly when nothing relevant is indexed, rather than fall back on generic financial knowledge (the whole point of this screen is to reflect what the knowledge base actually contains, not to be a second chat). No persistence, unlike `second_opinion`'s `jane_second_opinions` table — a free-form question isn't a decision to cross-reference against a future outcome.
- **New router (`api/routers/jane.py`, `POST /jane/ask`)** rather than folding this into `api/routers/chat.py` or `api/routers/decisions.py` — same one-router-per-domain convention as `chat.py` itself, and this endpoint has nothing to do with George's own `/chat` (which answers on tracked securities/decisions, not methodology).
- **Mobile-only** (explicit user request — not built for `web/`): a `FloatingActionButton` positioned via `Stack`/`Positioned` (`right: 16`, vertically centered with `Center` inside a `top: 0, bottom: 0` band) rather than one of Flutter's predefined `FloatingActionButtonLocation`s, none of which offer a vertically-centered right edge; overlaid on `UniversScreen`'s existing `Column` body, which had to be wrapped in a `Stack` for this (previously a bare `Column`). Opens `AskJaneSheet` (`showModalBottomSheet`, `isScrollControlled: true` to rise above the keyboard) — a text field plus a mic button, mirroring `web/`'s existing chat input row (text + send) with voice added on top, not a replacement for typing.
- **First voice-capture feature on mobile** (`package:speech_to_text`, `RECORD_AUDIO` runtime permission requested only at `SpeechToText.initialize()`, never at launch — plus the Android 11+ `<queries>` entry for `android.speech.RecognitionService`, without which `initialize()` fails silently even with the permission granted). `initialize()` failures (denied permission, no recognition service on the device, unsupported platform) are caught and degrade to a disabled mic button rather than crashing the sheet — the text field always works regardless. Auto-submits on `SpeechRecognitionResult.finalResult`, same UX as web's `useVoiceCapture` `onFinal` (no extra tap needed after speaking). iOS Info.plist keys (`NSMicrophoneUsageDescription`/`NSSpeechRecognitionUsageDescription`) added for correctness but **untested** — iOS isn't buildable from this Windows dev machine (see the top of this file).
- **`showResponseDialog` gained a `shareable` parameter** (default `true`, so every existing call site is unaffected) to hide the 📤 email-share icon for this popup specifically — sharing a Jane knowledge-base answer by email doesn't make sense the way sharing a decision explanation with an attached chart does. While touching this shared dialog, its close button was also relabeled from a bare "Fermer" to "❌ Annuler", matching the emoji-labeled button convention already used one screen away in the same file's `_ShareEmailDialog` ("❌ Annuler" / "✅ Envoyer") — a small consistency fix that affects every popup using `showResponseDialog`, not just Ask Jane.
