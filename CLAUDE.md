# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

"George" is a planned agent for technical analysis of financial markets (pattern detection on OHLCV data, per-basket "George Index" scoring, natural-language rationale for trade decisions). The build follows the 8-phase roadmap in `George_Prompts_Claude_Code.md`. So far: **Phase 0** (DB schema + Docker infra), **Phase 1** (pattern-detection engine + price ingestion), **Phase 2** (backtesting, learned XGBoost confidence score, baskets + George Index), **Phase 3** (FastAPI backend + `web/` wired to it via React Query), **Phase 4** (Mistral-backed LLM layer: decision explainer, `/chat`, pgvector-indexed reports, Jane's second opinion — `agents/`), **Phase 6** (risk management: exit-level calculation, the propose→confirm→monitor→confirm-exit decision lifecycle — `engine/exit_levels.py`, `engine/propose_decisions.py`, `engine/monitor_decisions.py`, this section), and a **deliberately scoped-down MVP of Phase 7** (collection orchestrator + validation/quarantine module + 2 manually-triggered sub-agents — `agents/orchestrator/`, `agents/collectors/`, see the Phase 7 section below) are implemented. **Phase 5 (mobile app) was deliberately skipped in its original form** — built out of roadmap order, straight after Phase 4, because the user's immediate need was real buy/sell opportunities surfaced through the existing API/web stack, not a mobile client; nothing about Phase 6 depended on Phase 5 having been built first. A **Flutter V1 MVP** of the mobile app was built later (see "Mobile app (Flutter)" section below), deliberately deviating from the roadmap's own Phase 5 stack (React Native/Expo + FCM + Piper/Coqui TTS) at the user's explicit request for Flutter + Firebase — with Firebase itself deferred to a V2 that tackles push notifications, since V1's scope (3 read/action screens against the existing REST API, no auth, no push) doesn't actually need any Firebase product yet. The full Phase 7 (LangGraph/Celery/Redis/Airflow/Playwright, 4 activation modes, the scraping-based sub-agents, Jane's continuous methodology watch) remains unimplemented — see that section for exactly what was built instead and why.

Root-level reference material (not code to run):
- `George_Prompts_Claude_Code.md` / `George_Prompts_Claude_Pro.md` — the full 8-phase roadmap (Phase 0 DB/Docker foundations → Phase 1 pattern-detection engine → Phase 2 ML scoring & George Index → Phase 3 FastAPI + React web app → Phase 4 LLM layer → Phase 5 mobile app (skipped, see above) → Phase 6 risk management/exit scenarios → Phase 7 geopolitical/press monitoring agents). Read the relevant phase section before implementing the next piece — it specifies exact table schemas, endpoints, and pattern lists.

- `whitelist_journaux.md` / `whitelist_journaux.json` — per-country reference list of national newspapers for the future "pilier 7" geopolitical-events agent (Phase 7). Not wired into any code yet.

## Python backend (`ingestion/`, `infra/`, `tests/`) — Phase 0

### Commands
Run from the repo root:
```
cd infra && docker compose up -d      # Postgres+TimescaleDB, Redis, MinIO, Adminer
python -m venv .venv && .venv\Scripts\activate
pip install -e ".[dev]"
alembic upgrade head                  # apply migrations (needs the db container running)
python -m ingestion.seed              # load the 40 CAC 40 securities (idempotent)
pytest                                # needs a local Docker daemon (testcontainers spins up its own Postgres)
```
`alembic upgrade head --sql` / `alembic downgrade base --sql` print the migration SQL without needing a DB connection — useful to sanity-check a new migration when Docker isn't available.

### Architecture
- **`ingestion/models.py`** is the single SQLAlchemy declarative source of truth for the schema (`Security`, `PriceOHLCV`, `PatternDetected`, `Decision`, `DecisionOutcome`) — the Alembic migration in `ingestion/migrations/versions/0001_initial_schema.py` was written by hand to match it (not autogenerated), including the `create_hypertable('prices_ohlcv', 'ts')` call that makes `prices_ohlcv` a TimescaleDB hypertable. If you change `models.py`, write the matching migration by hand rather than relying on `alembic revision --autogenerate` to get the hypertable call right.
- **`ingestion/db.py`** resolves the connection string from the `DATABASE_URL` env var at call time (`get_database_url()`), falling back to the default local Docker Compose credentials. `alembic.ini` (repo root) does not hardcode a real URL — `ingestion/migrations/env.py` overrides it via `get_database_url()` on every invocation, online or offline. `get_engine()` sets `connect_args={"connect_timeout": 5}` — without it, psycopg trying both the IPv6 and IPv4 loopback addresses against a port nothing is listening on can hang far longer than 5s; this bit the notebook's DB-or-fallback logic (below) before the timeout was added, so keep it if you touch this function.
- **`ingestion/cac40.py`** holds the seed list of 40 `(symbol, name, country, currency, sector)` tuples; `ingestion/cac_mid60.py` adds 62 more (CAC Mid 60 — the current index closest to the historical "second marché", abolished in 2005 and folded into Euronext Paris's single market; compiled from Euronext's own March 2026 factsheet cross-checked against a secondary composition list, so treat it with the same "needs refreshing periodically" caveat already documented in `cac40.py`). `ingestion/seed.py` loads both, tagging `securities.theme` with which universe each symbol came from, and raises loudly if a symbol appears in both lists rather than letting the last upsert silently win. One symbol from the initial compilation (Eurazeo) had the wrong ticker (`RAZ.PA`, corrected to the real `RF.PA`) — caught immediately by `ingestion/ohlcv.py`'s per-symbol soft-failure logging, not by silent bad data, which is the whole point of that design.
- **Tests** (`tests/test_migrations.py`, `tests/test_seed.py`) use `testcontainers.community.postgres.PostgresContainer` (image `timescale/timescaledb:latest-pg16`) to get a disposable database per test session — they require a working local Docker daemon and are independent of whatever is running via `infra/docker-compose.yml`. Each test upgrades to `head` and downgrades back to `base` itself, so tests don't depend on execution order.

## Quant engine (`engine/`) + price ingestion (`ingestion/ohlcv.py`) — Phase 1

### Commands
```
python -m ingestion.ohlcv             # download 2y daily OHLCV via yfinance for every security, upsert into prices_ohlcv (needs network + db)
python -m engine.run_detection        # run all 13 pattern detectors against prices_ohlcv, insert confirmed matches into patterns_detected (needs db)
pytest tests/test_patterns.py         # unit tests on synthetic price series — no DB, no Docker, no network needed
pip install -e ".[dev,notebook]"      # adds mplfinance/jupyter for engine/notebooks/pattern_validation.ipynb
```

### Architecture
- **`engine/patterns/common.py`** holds the shared geometry toolkit and the module-level tolerances every detector reads (`EXTREMA_ORDER`, `LEVEL_TOLERANCE`, `MIN_PATTERN_BARS`, `BREAKOUT_BUFFER`) plus `PatternMatch` (the dataclass every detector returns). Pattern-specific thresholds (e.g. `MIN_PEAK_PROMINENCE`, `MIN_CUP_DEPTH` in `reversal.py`; `MIN_TREND_SLOPE`, `MIN_CONVERGENCE` in `continuation.py`) are documented in each file's module docstring, not centralized — read the docstring before tuning a specific pattern.
- Detectors are split by shape: **`reversal.py`** (Double Top/Bottom, Head & Shoulders + inverse, Cup & Handle — scan the *whole* price history for the most recent qualifying formation, since these can form anywhere in the past and only need a breakout on the latest bar to confirm), **`continuation.py`** (Bull/Bear Flag, Ascending/Descending Triangle, Falling/Rising Wedge — only look at a recent tail window, since these are short-lived), **`breakout.py`** (Breakout/Breakdown — recent tail window, requires a pullback bar immediately before the break so a plain continuous grind doesn't trivially count as a "breakout"). All 13 are registered in `engine/patterns/__init__.py`'s `DETECTORS` dict and re-exported from there.
- **Every detector returns at most one match** (the most recent formation), not every historical occurrence — each one filters/iterates backward and returns on the first (i.e. most recent) qualifying formation. `engine/detect.py:detect_all` just concatenates one call per registered detector.
- **Trendlines are fit through the actual extrema points** (`common.fit_trendline`, `np.polyfit` on `(extrema_index, price)` pairs), not through the whole window — this matters for wedges/triangles/flags. A recurring trap already hit once while building this: computing "does the range narrow / is the channel tight" using the *raw high/low of a window that still includes the breakout bar* silently defeats the check, because the breakout bar's whole purpose is to exceed the channel. Wedge convergence is measured strictly between the first and last **extrema** (`continuation.py:_wedge`), and a flag's channel (`continuation.py:_flag`) is fit only over the consolidation bars, explicitly excluding the final (candidate breakout) bar — apply the same exclusion if you add another breakout-confirmed continuation pattern.
- **`engine/confidence.py`** turns a detector's own `geometry_quality` (0-1, pattern-specific) plus shared `volume_confirmation` and `trend_alignment` (both also 0-1) into the final 0-100 score via fixed weights (0.5/0.25/0.25). `trend_alignment` needs 200 bars of history to judge SMA50/SMA200 alignment and returns a neutral 0.5 below that — expect near-identical confidence scores across patterns when testing on short synthetic series.
- **`ingestion/ohlcv.py`** downloads per-symbol via `yf.Ticker(symbol).history(...)`, retries up to `MAX_RETRIES` with linear backoff, and treats an empty/missing result as a soft failure (logged, symbol skipped, rest of the universe continues) rather than raising.
- **`tests/test_patterns.py`** builds each pattern from hand-placed `ramp()`/`path()` segments (strictly monotonic pieces glued end-to-end so `scipy.signal.argrelextrema` finds extrema exactly where intended) rather than random walks — when adding a test for a new detector, follow that construction style and hand-verify the key indices/levels against the detector's own gates instead of guessing coordinates.
- **`engine/notebooks/pattern_validation.ipynb`** tries the real DB first (via `engine.run_detection.load_prices`) and falls back to a synthetic Double Bottom (same construction as the test above) if it's unreachable or empty — verified executable end-to-end with `jupyter nbconvert --to notebook --execute`. Its `plot_match` helper only sets `hlines=`/`addplot=` on the `mpf.plot(...)` call when those lists are non-empty — mplfinance's kwarg validator rejects `hlines=None` outright rather than treating it as "no lines", which crashed the first version of this cell.

## Learned scoring, baskets & George Index (`engine/`) — Phase 2

### Commands
```
python -m engine.build_training_set   # DB -> engine/data/training_set.parquet (patterns_detected + prices_ohlcv backtested at 5/10/20 sessions)
# then run engine/notebooks/train_confidence_model.ipynb (offline) to train + save engine/models/confidence_xgb_<date>.joblib (+ .meta.json)
python -m engine.compute_george_index # prints each basket's George Index (needs db + baskets/basket_securities populated)
python -m engine.reevaluate_decisions # updates decision_outcomes for existing decisions (needs db)
pytest tests/test_features.py tests/test_backtest.py tests/test_george_index.py tests/test_scoring.py   # no DB, no Docker
```
`engine/models/` and `engine/data/` are gitignored (regenerable binaries/derived data) — running the training notebook with no `engine/data/training_set.parquet` present falls back to a synthetic dataset with a small fabricated signal, so the whole pipeline (train → evaluate → save dated model + metadata → load in `engine.scoring` → override a detector's confidence) is exercisable and was verified end-to-end without Docker.

### Architecture
- **`engine/features.py`** is the single source of the feature contract shared between training and inference: `FEATURE_COLUMNS` (= `CATEGORICAL_FEATURE_COLUMNS` + `NUMERIC_FEATURE_COLUMNS`). Its functions (`relative_volume`, `atr_pct`, `position_vs_moving_averages`) return `None` on insufficient history rather than a placeholder value — that `None` is exactly the signal `engine/scoring.py` uses to trigger the Phase 1 heuristic fallback instead of the learned model.
- **`engine/backtest.py`** is pure (no DB) — `build_sample` turns one detected pattern into a training row (features + `return_{5,10,20}` + `success_{5,10,20}` labels), gated on the pattern being far enough in the past that the longest horizon is observable. `compute_market_trend` is a deliberate proxy for "reference index trend" (cross-sectional average return of whatever price series you hand it) because the schema has no dedicated market-index feed — same limitation called out in `engine/george_index.md`. `engine/build_training_set.py` is the DB-touching script that resolves each `patterns_detected.detected_at` to an integer bar position (`nearest` on the DatetimeIndex) and calls into `backtest.py`. **It skips writing `training_set.parquet` entirely when zero samples are backtestable** (real case: right after a fresh `engine.run_detection` run, every pattern's `detected_at` is today, so none has `TRAINING_HORIZON` sessions of hindsight yet) — writing an empty, columnless DataFrame there would satisfy the training notebook's `os.path.exists(...)` fallback check while still crashing it on `dataset[FEATURE_COLUMNS]` a few cells later; the notebook now also guards with `not dataset.empty` before trusting the file, and falls back to the synthetic dataset otherwise.
- **`engine/scoring.py`** loads the lexicographically-last `engine/models/confidence_xgb_*.joblib` (filenames are ISO dates, so sorted-last == most recent) plus its `.meta.json` (`feature_columns`), caches both for the process, and never raises — any missing model, insufficient per-symbol history, or prediction-time exception falls back to `match.confidence` (the Phase 1 heuristic, already computed by the detector). `predict_confidence`'s `price_frames` param is optional: passing it enables the `market_trend` feature, omitting it just leaves that one feature as `NaN` (imputed by the trained pipeline) rather than blocking inference — only the *other* features (volume/ATR/moving averages) are treated as hard requirements.
- **The saved model artifact is a full scikit-learn `Pipeline`** (`ColumnTransformer(SimpleImputer + OneHotEncoder) → XGBClassifier`), not a bare `XGBClassifier` — this is why `engine/scoring.py` can call `.predict_proba()` directly on a raw one-row DataFrame with string `pattern_type`/`sector` columns without re-implementing the encoding at inference time. If you retrain with a different feature set, update `engine/features.py:FEATURE_COLUMNS` (both training and inference read from there) rather than hardcoding column lists in the notebook or in `scoring.py`.
- **`engine/george_index.py`** implements the formula documented in `engine/george_index.md` — read that file first; the two must stay in sync. Key asymmetry: the confidence part of the score only counts securities with a pattern detected within `ACTIVE_WINDOW_SESSIONS` (5 sessions), but the momentum/volume multipliers are computed over *every* security in the basket with enough price history, active or not — a basket's price-action context isn't limited to its currently-alerted names. Returns `None` (not `0`) when no security in the basket has an active pattern — a silent basket isn't a bad one.
- **`engine/reevaluate_decisions.py`** and **`engine/compute_george_index.py`** are thin DB scripts — `baskets`/`decisions` stay empty unless you run `ingestion/seed_demo.py` (Phase 3) or wait for Phase 6 to generate real decisions; verified here only by import and by unit-testing their pure helper functions (`evaluate_decision`, `george_index.compute_george_index`) directly, not against a live DB.
- **`ingestion/models.py`** gained `Basket`, `BasketSecurity`, `PatternCandidate` in migration `0002` (chained after `0001` via `down_revision`). `pattern_candidates` mirrors `patterns_detected`'s columns exactly — it's a landing/backtesting table for whatever the future Phase 7 methodology-watch agent proposes, nothing promotes rows into it yet.

## API (`api/`) — Phase 3

### Commands
```
uvicorn api.main:app --reload     # dev server on :8000, needs db running (needs Docker)
python -m ingestion.seed_demo     # optional: seeds baskets (one per sector) + a few illustrative decisions/agent_events, so the API isn't just empty lists
pytest tests/test_api.py          # most need Docker (testcontainers); one doesn't (see below)
```
`GET /docs` (Swagger UI) and `/openapi.json` are generated automatically by FastAPI — `app.openapi()` builds successfully with zero DB access (verified by importing `api.main` with no DB running), since routes only touch the DB when actually called.

### Architecture
- **`api/deps.py`** builds the SQLAlchemy `engine`/`SessionLocal` once at import time (not per-request) and exposes both as module attributes — `api/routers/baskets.py` reuses the same engine directly (not the per-request ORM `Session`) to call into `engine.george_index`/`engine.run_detection`, which expect a raw Engine. Tests override `api.deps.engine`/`api.deps.SessionLocal` via `monkeypatch` (see `tests/test_api.py`) since they're bound at import time, before a test DB URL is known. **`baskets.py` does `from api import deps` and reads `deps.engine` at call time — not `from api.deps import engine`.** The latter copies the reference at import time into `baskets.py`'s own namespace; a later `monkeypatch.setattr(deps, "engine", ...)` then silently misses it, and the route keeps querying whatever DB was live at process startup. Caught by running the real Phase 0-3 stack end-to-end (Docker actually available): `test_george_index_for_basket_with_active_pattern` passed against the isolated test container's `SessionLocal`-backed queries but returned `george_index: null` because `load_patterns`/`load_prices` were silently hitting the stale pre-monkeypatch engine instead.
- **`api/schemas.py:Page[T]`** is the one pagination envelope used by every list endpoint (`{"items": [...], "total", "limit", "offset"}`). Routers return a *bare* `Page(items=rows, ...)` (not the parameterized `Page[SecurityOut](...)`) with `rows` being raw ORM objects — this works because FastAPI re-validates the returned object against the route's declared `response_model=Page[SecurityOut]` regardless of how it was constructed, and that re-validation is what triggers `SecurityOut`'s `from_attributes` conversion. Verified with an isolated repro against this exact FastAPI/pydantic version pair before relying on it.
- **`GET /securities/{symbol}/prices`** exists beyond the roadmap prompt's minimum endpoint list — the candlestick chart (task 6 of the Phase 3 prompt) needs real OHLCV, and no endpoint for it was specified. It returns the `limit` most recent bars in chronological order; the frontend must reconstruct each bar's *absolute* index (`total - len(items)` from the same `Page` envelope) to translate a pattern's `context` indices (absolute positions in the full series the detector saw) into positions within this truncated window — see `CandlestickChart.jsx` below.
- **`GET /securities/{symbol}/patterns` orders by `detected_at.desc(), confidence.desc()`, not `detected_at.desc()` alone.** `engine/run_detection.py` typically confirms several pattern types for the same symbol with the exact same `detected_at` (all resolve off the same latest bar) — against a real populated DB, `limit=1` with only `detected_at` ordering returned an effectively arbitrary tied row (observed: consistently the *lowest*-confidence one, e.g. a 19% Double Bottom shown in the watchlist for a symbol that also had a 48% Inverse Head & Shoulders). The confidence tiebreaker makes "the pattern for this symbol" deterministic and picks the most convincing one instead. `tests/test_api.py::test_list_security_patterns_prefers_higher_confidence_on_tie` is the regression test.
- **`api/main.py:database_exception_handler`** is registered for `SQLAlchemyError`, deliberately *not* the bare `Exception` class — Starlette special-cases handlers registered for `Exception` (or status 500) and routes them to `ServerErrorMiddleware`, which sits *above* `CORSMiddleware` in the stack, so its response never gets CORS headers added (the browser then reports a misleading CORS error instead of surfacing the real 503, since with no DB running every list endpoint fails this way). Registering the handler on a specific subclass instead keeps it inside `ExceptionMiddleware`, *below* `CORSMiddleware`, so headers get added correctly. `tests/test_api.py::test_db_unreachable_returns_503_with_cors_headers` is the regression test — it needs no Docker (it points `api.deps.engine` at a deliberately-closed port) and will fail if this handler regresses to catching bare `Exception` again.
- **`ingestion/db.py`'s default `DATABASE_URL` host is `127.0.0.1`, not `localhost`** — `localhost` also resolves to `::1`, and psycopg tries both addresses in sequence on failure, doubling the time before a connection error surfaces (relevant because the API, the notebooks, and every script share this default). Combined with React Query's `retry: 0` (`web/src/main.jsx` — a second client-side attempt would double the already-multi-second server-side failure again), a cold "DB is down" page load now settles in roughly one `CONNECT_TIMEOUT_SECONDS` instead of stacking multiple retries at multiple layers.
- **`ingestion/seed_demo.py`** groups the existing `securities` by their `sector` column into one basket per sector — it doesn't invent a separate taxonomy. Decisions are only inserted for symbols that already have `prices_ohlcv` history (real `entry_price`, computed `take_profit`/`stop_loss` off it); a symbol with no price history is silently skipped rather than seeded with a fabricated entry price. Both the basket-seeding and decision-seeding steps check what already exists before inserting, so the script is safe to re-run.
- **`ingestion/models.py`** gained `AgentEvent` in migration `0003` (chained after `0002`). It backs `GET /agents/activity`; nothing populates it yet outside `seed_demo.py`'s illustrative rows, pending the Phase 7 sub-agents.

## LLM layer (`agents/`) — Phase 4

### Commands
```
alembic upgrade head            # migration 0004: CREATE EXTENSION vector + reports table
export MISTRAL_API_KEY=...      # required at call time, not import time — see below
uvicorn api.main:app --reload   # POST /decisions/{id}/explanation, POST /chat, POST /reports, GET /reports, GET /reports/search
pytest tests/test_agents.py     # pure context-builder tests, no DB, no network
pytest tests/test_api.py        # includes the Phase 4 endpoints, Mistral client monkeypatched — needs Docker (testcontainers), no real API key
```

### Architecture
- **Scoped per the roadmap's own text** (`George_Prompts_Claude_Code.md`, Phase 4 + the Jane paragraph under pilier 7): built here are the explainer, `/chat`, pgvector report indexing, and Jane's **synchronous second opinion** only. Jane's **continuous methodology-watch** role (scraping Investopedia/TradingView/etc. for new pattern candidates) explicitly "ne fonctionne que sur le mode veille continue autonome, en tâche de fond à faible priorité (queue/worker séparé)" — that infrastructure (Celery/Redis worker, Airflow) doesn't exist yet, so it stays deferred to Phase 7 rather than being half-built on top of a synchronous FastAPI request/response cycle.
- **`agents/mistral_client.py`** generalizes the roadmap's reference `mistral_client.py` (repo root) into one client shared by every sub-agent (explainer, Jane, chat, reports) instead of duplicating the retry/backoff logic per module. Deliberate deviation from that reference: the client is instantiated lazily on first real call (`_get_client()`), not at module import — the reference raises `RuntimeError` at import if `MISTRAL_API_KEY` is unset, which would make `agents.*` unimportable (and untestable) in any environment without a key configured, same reasoning as `ingestion/db.py:get_database_url()` resolving at call time rather than import time.
- **`MistralUnavailableError`** (raised for a missing key or after retry exhaustion) is a dedicated subclass of `RuntimeError`, deliberately *not* bare `Exception` — same Starlette trap as `SQLAlchemyError` (see Phase 3 section above): a handler on `Exception` gets pulled into `ServerErrorMiddleware`, *above* `CORSMiddleware`, so the browser sees a misleading CORS error instead of the real 503. `api/main.py:mistral_exception_handler` targets the specific subclass to stay under `CORSMiddleware`. Verified against the real dev DB with no `MISTRAL_API_KEY` set: `POST /chat` returns a clean `503` with the actual missing-key message, not a crash.
- **Every agent module calls `mistral_client.complete(...)`/`.embed(...)` via `from agents import mistral_client` then `mistral_client.xxx(...)`, never `from agents.mistral_client import complete`** — same reasoning as `baskets.py`'s `deps.engine` pattern in Phase 3: it lets tests `monkeypatch.setattr(mistral_client, "complete", fake)` and have every caller see the fake, regardless of which module imported it first.
- **`agents/context.py`** is pure (no DB, no LLM call) — same split as `engine/backtest.py` vs `engine/build_training_set.py`: it takes already-fetched ORM objects and returns a JSON-serializable dict, converting `Numeric` columns (`decimal.Decimal`) to `float` explicitly. This dict is the *entire* user message sent to the LLM; every system prompt in `agents/prompts/` instructs the model to never cite a number absent from it. `tests/test_agents.py` checks these builders directly; `tests/test_api.py` additionally monkeypatches `mistral_client.complete` to echo the received context back verbatim and asserts the real DB values (not fabricated ones) survive into the "response" — the two halves of the anti-hallucination guarantee required by the roadmap's task 6, without a real network call or API key.
- **`agents/explainer.py:find_pattern_for_decision`** prefers `decision.pattern_id` (Phase 6, a real foreign key filled in by `engine.propose_decisions`) when present. Older/illustrative decisions (`ingestion/seed_demo.py`) have no `pattern_id`, so it falls back to the pre-Phase-6 heuristic: the most recent `patterns_detected` row for the same symbol at or before the decision's `created_at` (same confidence-tiebreak rule as `api/routers/securities.py`'s pattern listing, Phase 3). `agents/jane.py` and `agents/chat.py` reuse it (or its `_latest_pattern` sibling in `chat.py` for symbols with no decision yet).
- **`agents/jane.py:second_opinion`** is a genuinely separate LLM call (`mistral-large-latest`, `agents/prompts/jane_second_opinion_system.txt`) from `agents/explainer.py:explain_decision` (`mistral-small-latest`) — not a parameter tweak on the same call. `POST /decisions/{id}/explanation` with `include_second_opinion: true` calls Jane first, then threads her note through `decision_context(..., jane_note=...)` into George's own explanation, which is told to arbitrate rather than defer to her. This implements the roadmap's "Jane relit le dossier complet ... juste avant la génération de l'explication finale par George" — originally wired to a manually-triggerable endpoint rather than an automatic publishing pipeline, and still is: Phase 6 built the propose→confirm decision lifecycle but nothing in it auto-calls Jane or the explainer, by design (an investor might want the explanation before *or* after confirming, not forced into one order).
- **`agents/chat.py:find_relevant_securities`** does plain substring matching (symbol root or lowercased name) against the ~40-security universe — the roadmap explicitly calls for "RAG simple sur les tables SQL, pas besoin de recherche vectorielle complexe à ce stade" for `/chat`; pgvector is reserved for `agents/reports.py` (task 4 is specifically about indexing long reports/notes, not routing chat questions).
- **`agents/reports.py`** reuses `engine.george_index.compute_george_index`/`engine.compute_george_index.load_patterns` directly (Phase 2), taking the SQLAlchemy `Engine` as a parameter rather than importing one — `api/routers/reports.py` passes `deps.engine` read dynamically at call time, avoiding the exact stale-reference bug already hit once in `baskets.py` (Phase 3). A portfolio-wide report (`basket_id=None`) leaves `george_index` as `None` rather than averaging per-basket indices: the George Index is a defined-only-per-basket metric (`engine/george_index.md`), and no methodology for a portfolio-wide aggregate exists yet.
- **`Report.embedding`** is `pgvector.sqlalchemy.Vector(1024)` — `mistral-embed`'s documented output dimension (verified from the installed `mistralai` SDK's own README, not yet against a real embedding call, since no `MISTRAL_API_KEY` has been configured in this environment). If Mistral ever changes that dimension, both `ingestion/models.py:EMBEDDING_DIM` and migration `0004`'s literal `1024` need updating together (a fixed dimension is required for the column type, not just a soft convention).
- **`mistralai` SDK note**: the installed version (2.7.2) imports as `from mistralai.client import Mistral`, *not* `from mistralai import Mistral` as shown in the roadmap's own reference `mistral_client.py` — that top-level shortcut doesn't exist in this version (confirmed by inspecting the installed package: `mistralai/__init__.py` doesn't exist, only `mistralai/client/`, `azure/`, `gcp/`, `extra/` subpackages). Follow `agents/mistral_client.py`'s import if extending this layer, not the root-level reference file's.
- **pgvector is already available in `timescale/timescaledb:latest-pg16`** (the image already in use since Phase 0) — confirmed with `SELECT * FROM pg_available_extensions WHERE name='vector'` against the real container before writing migration `0004`, so no base-image change was needed.

## Risk management & decision lifecycle (`engine/`) — Phase 6

### Commands


### Architecture
- **Not literally what the roadmap's Phase 6 prompt describes**, and deliberately so: the prompt's own "Contexte" line says decisions "sont créées avec entry_price, take_profit, stop_loss déjà en colonnes... mais la logique de calcul... n'existe pas encore" — it assumes decisions already exist and only specifies the *levels* calculation (task 1) and a `propose-levels`/`confirm` pair (tasks 2-3) for an *existing* decision. In reality, before this phase, only `ingestion/seed_demo.py` ever created a `Decision` row, explicitly as illustrative demo data (Phase 3). The user's actual ask ("peux-tu me proposer des opportunités d'achat") needed decisions to be created from real detected patterns in the first place — so `engine/propose_decisions.py` closes that gap: it's the module that turns a real `patterns_detected` row into a real `status="proposee"` Decision, which `propose-levels`/`confirm` then operate on exactly as specified.
- **`decisions.status` lifecycle**: `"proposee"` (created by `propose_decisions`, levels not yet validated) → `"confirmee"` (investor validated, possibly with adjusted levels) → `"sortie_proposee"` (the monitor job detected a TP/SL breach and filled in `exit_scenario`/`exit_volume_confirmed`/`exit_justification`) → `"cloturee"` (exit confirmed, `decision_outcomes` row written). The 3 pre-existing illustrative decisions (`seed_demo.py`) were backfilled to `"confirmee"` by migration `0005`'s `server_default` — they were already presented as definitive before this lifecycle existed, and `status` has no Python-side default (every code path sets it explicitly), so the server default only ever fires for that one historical backfill.
- **`engine/exit_levels.py:propose_levels`** implements task 1 for all 13 pattern types, not just the two the roadmap gives as examples (flag mast, double-bottom amplitude). Reversal patterns (Double/Top/Bottom, Head & Shoulders + inverse, Cup & Handle) compute take-profit/stop-loss entirely from the geometry already stored in `patterns_detected.context`. Continuation patterns (triangles, wedges) and Breakout/Breakdown don't store enough absolute-price geometry in `context` for this (only a slope or a percentage — see `engine/patterns/continuation.py`'s own docstring) — their functions take the already-loaded price `df` as a second input and recompute a recent high/low over the same `WINDOW` the detector itself used (imported directly from `engine/patterns/breakout.py`/`continuation.py`, not redefined), rather than duplicating that geometry into `context` solely for this purpose. Bull/Bear Flag needed one small, additive change to `continuation.py:_flag`'s `context` (added `pole_amplitude`, `flag_low`, `flag_high` — all computed values that already existed as local variables there, just not previously returned) to avoid an approximation; confirmed safe via `tests/test_patterns.py`, which doesn't assert on exact `context` contents for flags.
- **`engine/propose_decisions.py:select_candidates`** picks at most one proposal per symbol — the most confident active pattern (`ACTIVE_WINDOW_SESSIONS`, same 5-session/1.5x-day-margin window as `engine/george_index.py`) above `MIN_PROPOSAL_CONFIDENCE` (50.0) — and skips any symbol that already has an open decision (`status` in `proposee`/`confirmee`/`sortie_proposee`), so re-running it is safe and never stacks contradictory signals on the same title. Real run against the populated dev DB produced 16 proposals from 109 detected patterns; a few (e.g. a Double Bottom on MT.AS with bottoms far below the current price) show intentionally wide levels because the measured-move formula is faithful to whatever geometry the pattern actually has — proposals are meant to be reviewed/adjusted via `propose-levels`/`confirm`, not auto-executed, so this is accepted rather than artificially capped.
- **`engine/exit_scenarios.py:classify_exit`** implements the volume-confirmed-vs-noise distinction the roadmap asks for "dans ce dernier cas" (i.e. only for a stop-loss breach, not a take-profit hit) — reuses `engine.confidence.volume_confirmation` (same metric Phase 1 already uses for detection confidence) rather than a new one, thresholded at `VOLUME_CONFIRMED_THRESHOLD` (0.5, i.e. breach-day volume ≥ 1.25× the 20-session average) to choose `"sortie_totale"` vs `"sortie_partielle"`.
- **`engine/reevaluate_decisions.py:evaluate_decision`** (Phase 2) gained a third return value (`hit_at`, the breach session's timestamp) — its one existing caller (`run()` in the same file) was updated to unpack 3 values; needed so `engine/monitor_decisions.py` can locate the exact session to check volume on.
- **`engine/monitor_decisions.py`** never writes to `decision_outcomes` and never sets `status="cloturee"` itself — it only reaches `"sortie_proposee"` with the scenario/justification already filled in, honoring the roadmap's explicit constraint ("le job de suivi ne doit jamais clôturer une position automatiquement"). Only `POST /decisions/{id}/confirm-exit` writes the `decision_outcomes` row (task 5) and closes the decision — and it *recomputes* the outcome via `evaluate_decision` rather than trusting `exit_scenario` directly, because `"sortie_totale"` is ambiguous on its own (it's produced both by a take-profit hit *and* by a volume-confirmed stop-loss breach) and the real cause (`take_profit_hit`/`stop_loss_hit`) needs to be unambiguous in `decision_outcomes` for any future retraining use.
- **`GET /decisions`'s query param `status` used to mean `decision_type`** ("Achat"/"Renforcer"/"Surveiller"/"Alléger") — confusingly, since Phase 6 needed a *real* lifecycle `status` field on the same table. Renamed the existing param to `decision_type` and gave `status` its new lifecycle meaning; safe because no shipped `web/` code was actually passing a `status` value yet (`useDecisions({status, ...})` in `web/src/api/queries.js` existed but was never called with one) — updated to `useDecisions({decisionType, status, ...})` and the one test that exercised the old param (`tests/test_api.py`) accordingly.
- **`agents/prompts/exit_scenario_system.txt`** + `agents/context.py:exit_scenario_context` + `agents/explainer.py:explain_exit_scenario` are a third George-voice prompt (alongside the decision explainer and `/chat`), reusing the exact same anti-hallucination contract: the scenario/volume-confirmed verdict is already decided by `engine.exit_scenarios` before the LLM ever sees it, the LLM only puts it into words and is told to always restate that nothing is closed without investor confirmation.

## Collection sub-agents (`agents/orchestrator/`, `agents/collectors/`) — Phase 7 (deliberately scoped-down MVP)

### Commands
```
alembic upgrade head              # migration 0008: collected_info_quarantine

pytest tests/test_orchestrator.py tests/test_collectors.py   # pure, no DB, no network
pytest tests/test_api.py -k collect                          # needs Docker
```

### Scope decision
The roadmap's own text calls Phase 7 "l'étape la plus complexe du projet" — an orchestrator (LangGraph/CrewAI), Celery+Redis, Playwright/Scrapy, Airflow, 6 sub-agents, 4 activation modes, and a multi-source validation/quarantine module. Built here, with explicit user sign-off (plan mode) on scaling down to an MVP rather than attempting the full spec in one pass: the orchestrator and validation/quarantine module (tasks 1 and 4 of the roadmap's Phase 7 prompt) for real, plus **2 of the 6 specified sub-agents**, all triggered manually — same precedent as `POST /prices/refresh` — rather than via any scheduler/queue. No Celery, Redis (already provisioned in `infra/docker-compose.yml` but still unused by any Python code), Airflow, Playwright, or LangGraph exist in this codebase. Deferred entirely: regulatory-filing scraping, earnings-calendar scraping, sector-press/sentiment scraping, Jane's continuous methodology watch (the roadmap explicitly restricts that role to a low-priority background queue that doesn't exist yet — see the LLM layer section above for Jane's *synchronous* second-opinion role, which was already built in Phase 4), and 3 of the 4 activation modes (continuous background watch, nightly Airflow batch, reactive-to-a-missing-info-queue).

- **Sub-agent swap, discovered and confirmed with the user mid-implementation**: the roadmap's "fondamentaux d'entreprise" sub-agent (SEC EDGAR) has a real coverage gap for this universe — EDGAR only indexes companies that file with the US SEC. Checked directly against SEC's own `company_tickers.json`: only ~5-6 of the 102 tracked CAC 40/Mid 60 securities have a real CIK (TotalEnergies, Sanofi, Crédit Agricole, Orange, Saint-Gobain, via their ADRs) — `edgar_client.py` (root, still unintegrated, unchanged) would have been accurate but nearly useless at this universe's scale. Replaced with **"synthèse de document"** — one of the roadmap's own 7 listed collection task types (task 1) — which summarizes an existing `Report` (Phase 4, `agents/reports.py`) instead: zero coverage gap, zero new external dependency, reuses data already produced by the anti-hallucination-verified LLM pipeline.
- **`agents/orchestrator/types.py:CollectedItem`** is the one shared shape every collector returns (label, value, unit, source name/URL, observed-at, optional symbol) — pure dataclass, no DB, no network, same tier as `agents/context.py`.
- **`agents/orchestrator/validation.py:validate`** implements the roadmap's task 4 (multi-source cross-referencing, a reliability score, quarantine on unresolved contradiction) as a pure function: 1 source → `validated` at a moderate fixed reliability (`SINGLE_SOURCE_RELIABILITY = 0.6`, no fabricated second source); ≥2 sources → compares numeric values, `validated` (reliability scaling with agreement) if the relative spread is within `tolerance_pct` (1% default), else `quarantine` with both values in `reason`. This is the function the roadmap's task 7 test targets directly (`tests/test_orchestrator.py`) — no DB/network needed to prove contradictory sources never get integrated.
- **`agents/orchestrator/run.py:run_collection_task(db, engine, task_type, collector, scope)`** is the actual orchestrator (task 1): calls the already-resolved `collector` (passed in by the caller, not imported here — see next point), validates each returned group, writes an `AgentEvent` (validated) or `CollectedInfoQuarantine` (quarantined) row, commits, returns both. `engine` is a parameter, never imported at module level — same anti-stale-reference precaution as `agents/reports.py`/`api/routers/portfolios.py`. **`collector` is passed in rather than resolved from a `task_type` string inside this module** specifically to avoid a real circular import hit during development: `agents/collectors/*.py` import `agents.orchestrator.types.CollectedItem`, so having `agents/orchestrator/run.py` import back `from agents.collectors import COLLECTORS` created an import cycle the moment both packages' `__init__.py` files existed. `api/routers/agents.py` (the one caller) resolves `COLLECTORS[task_type]` and passes the callable in.
- **`agents/collectors/__init__.py:COLLECTORS`** is the registry (`{"donnees_macro": ..., "synthese_document": ...}`), same pattern as `engine/patterns/__init__.py:DETECTORS`.
- **`agents/collectors/macro.py`** — FRED (`fredgraph.csv`) and the ECB's Statistical Data Warehouse (`data-api.ecb.europa.eu`), both genuinely keyless public APIs (verified live before writing any code). EUR/USD is fetched from **both** (FRED `DEXUSEU` + ECB `D.USD.EUR.SP00.A`) specifically to exercise `validate()`'s real multi-source path — the two values are close but not identical in practice (e.g. 1.1385 vs 1.1389 on a live run), a genuine independent-source disagreement small enough to validate, not a fabricated demo. The OAT-10-year indicator (`IRLTLT01FRM156N`) stays single-source — no independent keyless alternative was found, so it's `validated` at the single-source reliability rather than pretending a second source exists. **A real bug caught by live validation, not by the test suite**: FRED's CSV header names the value column after the exact series ID (e.g. `observation_date,IRLTLT01FRM156N`), not a generic `DATE`/`VALUE` pair — the first implementation assumed the latter, which parsed successfully in unit tests (whose canned CSV fixtures happened to share the same wrong assumption) but silently found zero observations against the real endpoint. Fixed in `fetch_fred_series`, and the test fixtures corrected to match the real header shape. The dispatch dict inside `collect_donnees_macro` is built freshly on every call (not once at module import) specifically so tests can `monkeypatch.setattr(macro, "fetch_ecb_series", ...)` and have it actually take effect — a module-level dict built once at import time would have captured the original function reference before any monkeypatch could apply.
- **`agents/collectors/synthesis.py`** — `collect_synthese_document(db, engine, scope)` requires `scope["report_id"]` (`ValueError` otherwise, translated to 400/404 by the router); loads the `Report`, calls `mistral_client.complete` with a new `agents/prompts/synthesis_system.txt` (same shape as the other 5 prompts: French, narrow role, anti-hallucination rule 1, explicit empty-input clause) via `mistral-small-latest`. Always a single item from a single source (the report itself) — always `validated` by construction, unless the Mistral call itself fails, in which case `MistralUnavailableError` propagates unchanged and is already handled by `api/main.py`'s existing handler (Phase 4) — nothing new needed there. Verified end-to-end against a real `Report` and a real Mistral call in this environment (a key is in fact configured here): the summary faithfully cited the report's real confidence figures (e.g. "FR.PA... 87,1") without inventing anything, and the test/demo rows created during that check were deleted afterward.
- **`api/routers/agents.py`** gained `POST /collect` (`CollectionTaskRequest{task_type, report_id}` → `CollectionTaskResponse{validated, quarantined_count}`) alongside the pre-existing `GET /activity`. Unknown `task_type` → 400; `synthese_document` without `report_id` → 400 (checked before calling the collector, so this never reaches the `ValueError`-for-missing-report path); unknown `report_id` → 404. Sync `def` route (like `api/routers/prices.py`), since a call is at most a few seconds (2 short HTTP GETs, or one Mistral call), no threadpool concern.
- **`ingestion/models.py:CollectedInfoQuarantine`** (migration `0008`) is deliberately not paired with a new `produced_by_agent` column — `AgentEvent.agent_name` already identifies the producing sub-agent for validated info, and adding a second column with the same meaning would be redundant.
- **`web/`**: one manual trigger only — "🌍 Collecte macro" in `Univers.jsx`'s sidebar (next to "🔄 Mise à jour des prix"), calling `useTriggerCollection()` (`web/src/api/queries.js`). No trigger for `synthese_document`: it needs a `report_id`, and no screen in `web/` lists `Report` rows yet — building one was out of scope for this pass; the endpoint remains callable via API/curl.

## Named portfolios (`api/routers/portfolios.py`, web `Mon Portefeuille`) — ad hoc, not a roadmap phase

Requested directly by the user rather than specified in `George_Prompts_Claude_Code.md` — a way to hand-pick a subset of `decisions` into a named, saved list, separate from the sector-based `baskets`/George Index machinery (Phase 2).

- **`ingestion/models.py:Portfolio`/`PortfolioDecision`** (migration `0006`) — deliberately *not* the same concept as `Report.scope == "portfolio"` (Phase 4), which means the whole tracked universe, not a personal selection; the naming collision is in the domain language only, not in code.
- **First implementation was client-only (`localStorage`)**; the user explicitly asked for it to persist durably instead ("créer une vraie table côté base de données pour que ça persiste durablement"), so it was rebuilt against a real table before ever being committed — no accounts/auth exists yet (Phase 9), so this is a single shared list of portfolios across all API clients, not scoped to an individual user.
- **`api/routers/portfolios.py`** has no ORM `relationship()` between `Portfolio` and `Decision` — consistent with the rest of this codebase (`Basket`/`BasketSecurity` don't use one either): `_portfolio_out` does the join manually and constructs `PortfolioOut` explicitly, relying on the same "FastAPI re-validates the response against `response_model`" mechanism already documented for `Page[T]` (Phase 3) to convert the nested `list[Decision]` into `list[DecisionOut]`.
- **`web/src/views/Paniers.jsx`**: checking a row's checkbox only stages it in local component state (`checkedIds`) — nothing is sent to the API until "Créer un portefeuille" is confirmed with a name in the popup (❌ Annuler / ✅ Enregistrer, per the user's exact spec), calling `POST /portfolios` via `useCreatePortfolio`. The checkbox column sits between Confiance and Créée le, as requested.
- **CORS**: `DELETE` had to be added to `api/main.py`'s `allow_methods` (previously `GET, POST` only) since `DELETE /portfolios/{id}` and `DELETE /portfolios/{id}/decisions/{decision_id}` are real HTTP DELETEs, not POSTs with a delete-like body.
- **The "Décisions" and "Alertes" nav tabs were removed** (they were `Placeholder` stubs since Phase 3, never implemented) at the user's request, alongside adding the new "Mon Portefeuille" tab.
- **`engine/portfolio_allocation.py`** (migration `0007` adds `portfolio_decisions.quantity`) computes a budget split across a portfolio's decisions — weight = confidence × (take-profit distance / stop-loss distance), i.e. more credible *and* better-rewarded-for-risk decisions get a bigger share, truncated to whole shares (no fractional-share trading on these markets). Deliberately **not** an LLM call: the same "small model can't reliably enumerate/compute over many structured entries" lesson from `agents/chat.py`'s opportunities case applies here even more directly, since this one has to be numerically correct (real money math), not just faithfully worded — `format_allocation_summary` builds the human-readable explanation in Python from the already-computed allocations, and `POST /portfolios/{id}/allocate` is a plain deterministic endpoint, no `agents.mistral_client` involved at all.
- **`PortfolioDecisionOut.current_price`/`pnl_pct` and `PortfolioOut.total_pnl_amount`/`total_invested`** are computed on every request (`api/routers/portfolios.py:_current_price_and_pnl`/`_portfolio_out`), not stored columns — `engine.run_detection.load_prices` for the latest close, and the same direction-aware sign convention as `engine.reevaluate_decisions.evaluate_decision` (bullish `{"Achat","Renforcer"}` vs bearish, imported as `BULLISH_DECISIONS` rather than redefined). **Deliberately not a call to `evaluate_decision` itself**: that function's `since = df[df.index >= decision.created_at]` filter exists to bound the history it scans for a TP/SL breach (Phase 6's exit-monitoring use case), and returns `None` whenever no price bar is dated on/after the decision's creation — for a decision proposed off today's close, that left this screen's PnL blank until tomorrow's bar existed, even though today's return (zero) was already knowable from `current_price == entry_price`. `_current_price_and_pnl` instead computes `(current_price - entry) / entry * 100 * direction` directly off the latest close, so `pnl_pct` is only `None` when there's no price history at all. `total_pnl_amount`/`total_invested` only sum over decisions with both a `quantity` (set via "Demander à George" or a future manual edit) and a non-null `pnl_pct` — a portfolio with no quantities yet shows `total_pnl_amount: null`, which `MonPortefeuille.jsx` renders as a "Renseignez des quantités..." prompt instead of a fake `0`. `_current_price_and_pnl` also returns `price_updated_at` (`df.index[-1]`, the last ingested price bar's timestamp) — `PortfolioDecisionOut`'s "Date"/"Heure" columns show *this*, not `DecisionOut.created_at` (when the decision itself was proposed): the two are genuinely different events (a decision from last week vs. this morning's price refresh) and conflating them was a bug caught by the user directly, not something derivable from the code. The portfolio's own `created_at` is shown separately, next to the "🎙 Demander à George" button ("Créé le …").
- **`POST /prices/refresh`** (`api/routers/prices.py`) wraps `ingestion.ohlcv.run` behind a manually-triggered HTTP endpoint — the "🔄 Mise à jour des prix" button under "Univers" in `Univers.jsx`'s sidebar. Defined as a plain `def` (not `async def`) so FastAPI runs it in its default threadpool rather than on the asyncio event loop; still a blocking call from the calling HTTP client's point of view (~a minute for the full CAC 40 + Mid 60 universe including yfinance retries), acceptable for an occasional manual action but not a substitute for real scheduling (Phase 7, not built). `useRefreshPrices()` (`web/src/api/queries.js`) invalidates the *entire* React Query cache on success (not just `["securities"]`) since a price refresh can change patterns, decisions, the George Index, and portfolio PnL, all downstream of `prices_ohlcv`. `SIDEBAR_NAV` in `Univers.jsx` used to list "Paniers"/"Décisions"/"George Index"/"Historique" as static, unclickable decoration (leftover from the original design prototype, never wired to real navigation — the actual view-switching nav is `App.jsx`'s top-level tabs) — trimmed to just "Univers" at the user's request, since those labels duplicated/contradicted the real top nav and the already-removed "Décisions"/"Alertes" tabs. `ResponsePopup.jsx`'s "loading" status text is now overridable via `popup.loadingText` (defaulting to "George réfléchit…") — needed here since this popup isn't an LLM call and "George réfléchit…" would be a misleading label for a price download.
- **"Demander à George" (web, per-portfolio mic button)** reuses the browser speech-to-text already built for Univers.jsx's voice command, extracted into `web/src/hooks/useVoiceCapture.js` (generic: caller supplies `onListening`/`onInterim`/`onError`/`onFinal`, the hook owns only the `SpeechRecognition` plumbing and error messages). `MonPortefeuille.jsx`'s `onFinal` runs a regex (`parseBudgetFromText`) over the transcript to pull out a euro amount ("répartis un budget de 100 000 euros..." → `100000`) and calls the deterministic `/allocate` endpoint — no LLM in this parsing step either, consistent with the point above. Which portfolio triggered the mic (several buttons, one per portfolio) is tracked in a ref set synchronously on click, not a state — a state update from the same click handler wouldn't be visible yet when `voice.start()` reads it in the same tick.

### Stack
Vite + React 19 + Tailwind CSS v4 (via `@tailwindcss/postcss`) + Recharts (donut chart in Paniers) + [`@tanstack/react-query`](https://tanstack.com/query) (all API calls/caching — task 9 of the Phase 3 prompt) + Vitest/React Testing Library/jsdom (dev-only, task 10). No router — view switching is plain `useState` in `App.jsx`. No `lucide-react` any more (dropped with the Paniers rewrite below — check before re-adding an icon library that nothing else needs it).

### Architecture
- **`src/api/client.js`** is a thin `fetch` wrapper (`apiFetch(path, params)`) — throws on any non-OK response so React Query's `isError` fires correctly. **`src/api/queries.js`** has one React Query hook per API endpoint (`useSecurities`, `useSecurityPatterns`, `useSecurityPrices`, `useBaskets`, `useGeorgeIndex`, `useDecisions`, `useAgentActivity`). There's no batch endpoint for "pattern + price history for N securities at once", so `WatchlistRow` and `GeorgeIndexTile` each call their own per-item hook — real N+1 request behavior, acceptable at CAC-40 scale, called out in `queries.js`'s docstring as something to revisit if the tracked universe grows a lot.
- **`src/components/CandlestickChart.jsx`** no longer generates synthetic candles from a seeded PRNG (that whole approach — and `src/lib/ohlc.js` — is gone). It now takes real `candles` (from `/securities/{symbol}/prices`) plus the real `context` dict from `patterns_detected`/`PatternOut.context`, and derives the overlay generically from that context's shape rather than regex-matching the pattern name: a `{index, price}` value becomes a marker (translated by the `indexOffset` prop — see the API section above for why that offset is needed), a `{points, price}` value (a neckline) becomes markers *and* a horizontal line, and a bare number under the key `resistance`/`support` becomes a line with no marker. No context at all (no active pattern) means no overlay at all — it no longer fabricates one from local extrema, unlike the Phase-3-prototype version. `takeProfit`/`stopLoss` are now absolute prices (from `Decision`), not the old `tpPct`/`slPct` percentages off a synthetic last close.
- **`src/views/Univers.jsx`** fetches `useSecurities`, `useDecisions` (built into a `symbol -> most-recent-decision` map client-side — there's no per-symbol decision filter on the endpoint, and the full list is small enough to fetch once), `useBaskets`, `useAgentActivity` at the top level; `WatchlistRow`/`GeorgeIndexTile` (in `src/components/`) own their own per-item queries. The George Index tile grid always renders exactly 2 slots (real tile, or an empty filler `<div>`) plus the macro tile — the grid's `gridTemplateColumns` is the fixed `"150px 150px 1fr"`, so a *variable* number of basket tiles (0, 1, vs. 2) shifts the macro tile into the wrong column; the empty-baskets message instead spans both slots via `col-span-2`. Distinguishes "API unreachable" (`isError`) from "DB reachable but empty" (`data.items.length === 0`) with two different messages — collapsing them into one generic empty state would hide a real connectivity problem.
- **`src/views/Paniers.jsx`** was rewritten from a fictive-portfolio simulator (invented capital, position weights, cash reserve — none of that has a backing table in the schema) into a real-data basket/decision browser: George Index per basket (bars, real), universe breakdown by `sector` (donut, real, computed client-side from the single `/securities` fetch rather than a per-basket count query), and a real `/decisions` table. Same "unreachable vs. empty" distinction as `Univers.jsx` (`apiUnreachable = basketsError || securitiesError || decisionsError`).
- **`src/data.js`** now only holds `macro` (rates/indices/FX tile — no backing table exists in the schema for this, so it stays a labeled placeholder) and the `decisionColor`/`scoreColor` helpers shared by both views. Everything else that used to live here (`positions`, `georgeIndex`, `agentEvents`, `CAPITAL`) is gone now that real data is wired up.
- **Theming** is CSS custom properties defined once in `src/index.css` (`--bg`, `--panel`, `--positive`, `--negative`, etc.), consumed via inline `style={{ color: "var(--x)" }}` or Tailwind arbitrary values rather than a Tailwind theme extension. Keep new components consistent with this pattern instead of introducing hex literals or extending `tailwind.config`.
- **Tests** (`*.test.jsx` next to the files they cover) mock `../api/queries` wholesale with `vi.mock` rather than standing up a `QueryClientProvider` + mocking `fetch` — simpler, and sufficient since the hooks themselves are trivial wrappers with no logic of their own to test. `vi.mock` is keyed by resolved module path, so mocking `"../api/queries"` from e.g. `Univers.test.jsx` also mocks it for `WatchlistRow`/`GeorgeIndexTile` that `Univers` renders, even though those files import it via the same relative specifier resolving to the same file — no separate per-component mock wiring needed.

Any data still explicitly fictive/illustrative (macro tile, `seed_demo.py` output) says so in the UI or in code comments — don't remove those disclaimers or present them as real.

## Mobile app (Flutter) — ad hoc, not a roadmap phase

Requested directly by the user as "Flutter + Firebase" rather than the roadmap's own Phase 5 spec (React Native/Expo + Firebase Cloud Messaging + Piper/Coqui TTS, see `George_Prompts_Claude_Code.md`). Built as a deliberately scoped-down V1 MVP with explicit user sign-off (plan mode) — same precedent as the Phase 7 scale-down: 3 screens mirroring `web/`'s functionality against the existing FastAPI backend, no push notifications, no native TTS/STT, no offline cache, no daily digest, no authentication. `mobile/` was a one-line placeholder README before this; it's now a real `flutter create` scaffold (`--org com.george --project-name george_mobile --platforms=android,ios`).

- **No Firebase in V1, deliberately** — flagged directly to the user rather than added for its own sake: FCM (push) and Firebase Auth are the only two Firebase products that would organically fit this app, and both are explicitly out of scope for V1 (no push infra, no auth anywhere in the backend yet — Phase 9 of the roadmap, not built). Adding Crashlytics/Analytics just to "use Firebase" would be contrived scope with no backend equivalent to match (`web/` has no crash reporting either). Firebase gets wired in during a V2 that actually tackles push notifications.
- **No authentication in V1** — the app calls the API directly, no login screen, matching the backend's current reality: no auth exists anywhere (see the API section above, `api/main.py`'s "Pas d'authentification à ce stade" comment), portfolios are globally shared, not per-user.
- **State management: Riverpod** (`flutter_riverpod`), not BLoC/plain `Provider` — chosen as the closest analogue to `web/`'s React Query pattern: one `FutureProvider.family` per API resource (mirroring one `useX` hook per resource in `queries.js`), with mutations calling `ref.invalidate(...)` on success instead of `queryClient.invalidateQueries(...)`. `lib/data/invalidate_all.dart:invalidateAllData` is the direct analogue of `useRefreshPrices`'s "invalidate everything" comment — `ref.invalidate(provider)` on a `.family` provider invalidates every parameterized instance, not just one. **Riverpod 3.x API gotcha hit while building this**: `AsyncValue.valueOrNull` from Riverpod 2.x is gone — the plain `.value` getter is now nullable and fills that role (`AsyncValue<T>.value` returns `T?`, never throws). Also, `StateProvider` moved to `package:flutter_riverpod/legacy.dart` in 3.x; rather than pull in that import for a single screen-local filter chip (purely UI state, not server state), `UniversScreen` uses a plain `ConsumerStatefulWidget` with local `setState` instead — no Riverpod provider needed for state that isn't shared/server-derived.
- **API client: hand-written, not codegen'd from `/openapi.json`** — `lib/core/api_client.dart` mirrors `web/src/api/client.js`'s 3-verb wrapper (`get`/`post`/`delete`) exactly, and `lib/models/*.dart` are hand-transcribed from `api/schemas.py` field-by-field, same discipline as the web client's implicit JSON destructuring. Chosen over `openapi-generator`/chopper/retrofit because the API is small (~9 resources, one shared `Page[T]` envelope) and has free-form `dict` fields (`PatternOut.context`, `AgentEventOut.context`) that would generate poorly as strict Dart classes anyway. **Naming collision worth knowing about**: the hand-written generic pagination wrapper is named `Page<T>` (mirroring `api/schemas.py:Page[T]`) — this collides with Flutter's own `widgets.dart:Page` class (used by `Navigator`'s Pages API) the moment a file imports both `package:flutter/material.dart` and `models/page.dart` and references `Page<T>` by name (hit in `test/features/paniers_screen_test.dart`); fixed there with `import '.../models/page.dart' as model;` rather than renaming the model class, since no non-test file needs both imports together.
- **Long-running calls get an explicit per-call timeout override, not a longer global default** — `/prices/refresh` (~1 min), `/agents/collect`, `/decisions/{id}/explanation`, and `/chat` pass `receiveTimeout: Duration(seconds: 90-120)` on the specific `ApiClient` call rather than raising the shared `Dio` instance's default (15s connect / 30s receive) — same "surface real errors fast" reasoning as `retry: 0` in `web/src/main.jsx` and `connect_timeout=5` in `ingestion/db.py`.
- **`lib/shared/widgets/response_dialog.dart:showResponseDialog`** is the mobile analogue of `web/src/components/ResponsePopup.jsx` — one dialog (loading/done/error, parameterized `loadingText`) reused for every LLM/long-running action (decision explanation, chat, price refresh, macro collection, budget allocation) instead of a bespoke dialog per screen.
- **`lib/features/univers/widgets/candlestick_chart.dart`** is a direct `CustomPainter` port of `web/src/components/CandlestickChart.jsx`'s hand-rolled SVG chart (there's no off-the-shelf Flutter candlestick chart in `fl_chart`) — same `buildOverlay` logic (markers from `{index/points, price}` context entries, horizontal lines for `resistance`/`support` keys), same generic "derive from `context`'s shape, not the pattern's name" principle called out in the original component's own comment.
- **`lib/features/decision_detail/`** is a pushed screen (`Navigator.push`, not a `go_router` route) rather than `web/`'s 3rd desktop column — mobile has no room for a persistent 3-column layout, and a plain imperative push was simpler than wiring a nested `go_router` route for a single non-deep-linked destination.
- **`DataTable` + horizontal `SingleChildScrollView`** renders each portfolio's decisions table in `lib/features/portefeuille/portefeuille_screen.dart` — same reasoning as `web/`'s `overflow-x-auto` on a `min-width: 840px` table (too many columns for a narrow viewport either way, scroll rather than cram).
- **Budget allocation uses a plain numeric `TextField`, not voice** — `web/`'s `MonPortefeuille.jsx` parses a spoken euro amount via `useVoiceCapture` + a regex (`parseBudgetFromText`); porting that would need a native STT package (`speech_to_text`), explicitly deferred past V1, so the mobile dialog just takes a number directly.
- **Testing**: no dedicated hook tests (this codebase's `web/` doesn't unit-test its React Query hooks either — they're trivial wrappers) — widget tests per screen (`test/widget_test.dart`, `test/features/paniers_screen_test.dart`, `test/features/portefeuille_screen_test.dart`) override the relevant Riverpod providers with fake data instead of letting a real HTTP call fire, same principle as `web/`'s wholesale `vi.mock("../api/queries")`. A provider left un-overridden in a test (e.g. `georgeIndexProvider` in the Paniers test) still resolves safely to its `AsyncValue.error` branch — Flutter's test `HttpClient` returns a fake 400 for any real request rather than hanging, so an un-mocked provider degrades gracefully instead of timing out the test.
- **Networking for local dev**: `mobile/README.md` documents the `--dart-define=API_BASE_URL=...` mechanism (no `flutter_dotenv` — Flutter's native build-time define mechanism already solves this, no extra dependency needed) and the three environments that actually differ (Android emulator needs `10.0.2.2`, not `localhost`; iOS simulator can use `localhost` directly; a physical device needs the host machine's real LAN IP plus `uvicorn --host 0.0.0.0`). CORS (`api/main.py:allow_origins`) is a browser-only mechanism and doesn't apply to native Android/iOS builds at all — only relevant if a Flutter *web* target is ever added.
- **`android/gradle.properties`'s default `org.gradle.jvmargs=-Xmx8G ...`** (from the stock Flutter Android template) crashed the Gradle daemon with an out-of-memory native allocation failure on this dev machine (7 GB total RAM, well under 8 GB) — lowered to `-Xmx2048m -XX:MaxMetaspaceSize=1g -XX:ReservedCodeCacheSize=256m`, which built `flutter build apk --release` successfully. Worth checking first if a release/debug APK build mysteriously fails with "Gradle build daemon disappeared unexpectedly" plus a `hs_err_pid*.log` crash dump in `android/` — that log's own "Out of Memory Error" / "insufficient memory... to continue" message is the tell, not a code problem.
- **Distributing a build for manual testing (e.g. Firebase App Distribution)** needs no Firebase SDK/`google-services.json` in the app itself — the release APK (signed with the debug key by default, see `android/app/build.gradle.kts`'s `signingConfig = signingConfigs.getByName("debug")`, fine for internal testing, not for a Play Store release) is a self-contained artifact; the Firebase project only needs the app registered (package name `com.george.george_mobile`) to accept an upload via the console's drag-and-drop, no CLI/build integration required for a one-off test distribution.
