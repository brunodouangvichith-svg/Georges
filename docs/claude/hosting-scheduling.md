## Hosting (Supabase Postgres + Render) — ad hoc, not a roadmap phase

### Commands
```
export DATABASE_URL=postgresql+psycopg://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
alembic upgrade head                  # applies the full migration history against Supabase's Postgres
python -m ingestion.seed              # (also: ingestion.ohlcv)
python -m engine.run_detection        # then engine.propose_decisions — see the real bug notes below before trusting old data
```

### Scope decision
Requested directly by the user, who wanted the mobile app reachable over the real internet rather than the local LAN (the LAN path needed a Windows Firewall rule and only worked on the same Wi-Fi as the dev machine — see the Mobile section above). The obvious first instinct — deploy George's own Postgres via Render or Railway — hit a real wall: **George's schema depends on the `timescaledb` extension** (`create_hypertable` on `prices_ohlcv`/`fx_prices_ohlcv`, since Phase 0), and neither Render's nor Railway's managed Postgres includes it; getting it would have meant a Docker-based private service with a persistent disk, which needs a paid plan (confirmed live: Render blocks deploying `plan: starter` pserv services without payment info on file).

- **TimescaleDB was dropped entirely, in favor of plain Postgres.** Verified live, not assumed, that Supabase (already in use for the auth portal, Phase 9 above) does *not* offer `timescaledb` on Postgres 17 projects — `CREATE EXTENSION IF NOT EXISTS timescaledb;` in the SQL Editor against the real `george-auth` project failed with `extension "timescaledb" is not available`, matching Supabase's own docs ("deprecated in projects using Postgres 17"). Given George tracks ~100 securities total, TimescaleDB's actual value-add (chunk partitioning, compression) was never load-bearing at this scale — dropping it unblocks a genuinely free, already-owned Postgres host with zero functional loss. `ingestion/migrations/versions/0001_initial_schema.py` and `0009_carry_trade.py` had their `CREATE EXTENSION timescaledb`/`create_hypertable(...)` calls removed directly (editing already-applied migrations rather than writing a new one to reverse them — justified here since this is a single-developer project with no other environment depending on migration history, and the local dev DB is trivially resettable/re-ingestable). `infra/docker-compose.yml` and `tests/conftest.py`'s testcontainers image both moved from `timescale/timescaledb:latest-pg16` to **`pgvector/pgvector:pg17`** (plain Postgres 17 + pgvector, matching Supabase's exact version) — pgvector (migration `0004`, `Report.embedding`) still needs to come from somewhere now that the TimescaleDB image no longer provides it for free; `tests/test_migrations.py`'s hypertable-existence assertion was removed accordingly.
- **George's own Postgres (via `george-auth`, the same Supabase project already used for auth) hosts the actual application data** — a deliberate expansion of that project's role beyond "identity provider only" (the original Auth-phase design explicitly kept these separate). Connection uses Supabase's **Session pooler** (`aws-0-<region>.pooler.supabase.com:5432`), not the direct connection — Supabase's own guidance reserves direct connections for IPv6-capable hosts and recommends the session pooler as "the alternative... when connecting via an IPv4 network," which better matches an external host like Render.
- **Small SQLAlchemy pool (`ingestion/db.py:get_engine`, 2026-10)**: `pool_size=2`, `max_overflow=2`, `pool_timeout=30`, `pool_recycle=300`, `pool_pre_ping=True` — overridable via `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` env vars (invalid values fall back to the defaults). Added after a real incident: the Supabase project (Nano instance) went `Unhealthy` (Advisor: "Database not usable", TCP `CONNECT_TIMEOUT`), taking Auth down with it (Google login "upstream request timeout", API 503s); a project restart fixed it. Root cause not proven from the logs, but SQLAlchemy's default 5 + 10 per process let the API alone hold up to 15 Session-pooler slots during one Univers page load (~200 requests: `prices?limit=20` + `patterns?limit=1` per security), on top of GitHub Actions jobs. `pool_pre_ping` also drops connections killed by a Supabase restart ("Connection reset by peer") instead of failing the next request. Tests are unaffected: `tests/test_api.py` builds its own engine. Pure tests in `tests/test_db_pool.py`. If 503s or slow pages come back, the next step is a batch endpoint for the Univers watchlist rather than a bigger pool.
- **Render (`render.yaml`, repo root)** hosts only `george-api` (`env: python`, **`plan: free`** — no database service needed anymore, since Supabase already hosts the data, which is what makes the free plan viable here). `buildCommand: pip install -e .`; `DATABASE_URL`/`MISTRAL_API_KEY`/`FINNHUB_API_KEY`/`SUPABASE_URL`/`SUPABASE_ANON_KEY` are all `sync: false` (filled in manually via the Render dashboard once the service exists, same convention as Jaz's own `render.yaml` in `MeteoIA`). Migrations/seeding are run manually (via Render's Shell tab or, as done here, directly from a local machine with `DATABASE_URL` pointed at the Supabase connection string) — no CI/CD migration step exists yet.
- **Two real, previously-undiscovered data bugs surfaced only by running the full pipeline against fresh data ingested mid-trading-day** (local dev had never done this — prior ingestion runs happened to land after market close): `engine/run_detection.py:load_prices` and (now-removed, see the Carry Trade removal note below) `engine/compute_carry_index.py:load_fx_prices` both cast the whole price history to `float`/`int64` without ever dropping a trailing row whose `close` is `NaN` — yfinance can return a most-recent bar with real `open`/`high`/`low`/`volume` but a `null` `close` for a session still in progress (the *same* bug class already fixed once in `api/routers/portfolios.py:_current_price_and_pnl`, now hit a second and third time in different modules). Concretely, this produced: (1) `engine/scoring.py:predict_confidence` computing features (`relative_volume`, `atr_pct`, `position_vs_moving_averages`) off a NaN close, writing a `NaN` confidence into `patterns_detected` for every Breakout/Breakdown pattern whose most recent bar was incomplete (160 of 603 rows on the first real run); (2) `engine/propose_decisions.py` then reading `df["close"].iloc[-1]` directly for `entry_price`, producing NaN there too; (3) `engine.propose_decisions` crashing outright with `decimal.InvalidOperation` the moment it tried to compare a `Decimal('NaN')` confidence against `min_confidence` in Postgres. Fixed at the source in both loader functions (`return df[df["close"].notna()]`, filtering the incomplete trailing bar before *any* downstream consumer — detectors, `engine/confidence.py`, `engine/scoring.py` — ever sees it) rather than patching each consumer separately; `engine/confidence.py:volume_confirmation` also gained a defensive `pd.isna` guard on the same principle. Re-running the full pipeline after the fix against the same live Supabase data confirmed zero `NaN` confidences and zero `NaN` entry prices (down from 603 to 263 genuine pattern detections — the drop itself confirms some of the original 603 were spurious "breakouts" against a bad trailing bar, not just NaN-tainted).
- **Verified**: full test suite (197 tests) green after every change above; `alembic upgrade head` applied cleanly against the real Supabase database; `ingestion.seed`/`ingestion.ohlcv`/`engine.run_detection`/`engine.propose_decisions` all run successfully end-to-end against it; the local FastAPI app, pointed at `DATABASE_URL=<supabase connection string>`, served real data (`/securities`, real decisions) through the full Supabase-auth-protected request path. A UTF-8 mojibake scare (`"SantÃ©"` instead of "Santé" in a `curl | python -m json.tool` check) turned out to be a **Windows/git-bash console display artifact only** — a controlled script-file comparison (never passing accented text through a bash `-c` argument, which is the actual corruption vector on this shell) confirmed the stored data was byte-for-byte correct all along; not a real bug, but worth remembering next time raw terminal output looks wrong on this machine before assuming the data is bad.
- **`george-api` is live on Render** at `https://george-api-mmut.onrender.com` (free `env: python` plan, region Oregon). First deploy attempt failed at import time (`api/deps.py` → `ingestion.db.get_engine()` → SQLAlchemy `create_engine`) with `sqlalchemy.exc.ArgumentError: Could not parse SQLAlchemy URL from given URL string`, even though the exact same `DATABASE_URL` string parsed correctly via `sqlalchemy.engine.url.make_url()` in a local test — ruling out the connection string's format itself. A temporary diagnostic (logging the env var's length/start/end/hidden-character flags, without exposing the password) was committed, pushed, and removed again once the very next redeploy succeeded — root cause was therefore on the Render-dashboard-entry side (a mismatch between what was pasted and what got saved), not the code or the string itself. Confirmed working end-to-end with a real Supabase password-grant token: `GET /securities` → `401` with no token, `200` with a valid one, real data (102 securities, accented sector names rendering correctly, e.g. "Santé / Biotechnologie") — the free-tier cold-start caveat (service spins down with inactivity, ~50s to wake) applies here.
- **Real bug found and fixed (2026-09): the price chart appeared empty for every security, on both mobile and web**, reported directly by the user with a screenshot. Root-caused via a live production investigation, not guesswork: a temporary read-only GitHub Actions workflow confirmed `price_history_long` was fully populated (255,785 rows / 102 symbols, 2,587 for the reported title) via the exact `DATABASE_URL` secret the ingestion jobs use; three successive temporary unauthenticated debug endpoints on the live Render service (committed, tested, removed once done) then proved — in order — that the DB connection `api/deps.py` actually uses in production sees the same data, that `list_security_prices` itself returns real rows when called directly, and that FastAPI's own `response_model=Page[PriceBarOut]` serialization succeeds too. With the query/data/serialization layers all cleared, a browser DevTools Network tab check (asked of the user directly, since it needed their own authenticated session) caught the real cause live: every request — including normally-fast ones like `fundamentals` — sat `(pending)` for **84+ seconds** ("Finish: 1.4 min") on a cold Render instance, confirmed resolved by re-testing once the service was warm (curl round-trips back down to 0.5-2s, and the same page then rendered the chart, pattern, and confidence correctly). This exceeded Mobile's already-bumped 60s `receiveTimeout` (itself a fix for an *earlier*, milder version of this same cold-start class — see `mobile/lib/core/api_client.dart`'s docstring) and, on web, exposed an unrelated pre-existing gap: `Univers.jsx`/`CandlestickChart.jsx` only ever looked at `data`, never `isLoading`/`isError`, so a still-loading or genuinely-errored fetch rendered identically to "no history for this title" — the exact same "loading/error conflated with empty" bug independently present in both codebases, mobile's version already partly addressed the day before by giving `decision_detail_screen.dart`'s silent empty box a visible error message.
- **Fixes applied**: `mobile/lib/data/prices_repository.dart:PricesRepository.fetch` now passes an explicit `receiveTimeout: Duration(seconds: 120)` (comfortably above the observed 84s worst case) instead of relying on `ApiClient`'s 60s default; both `decision_detail_screen.dart`'s and `CandlestickChart.jsx`'s empty-state text now explicitly name the real cause ("le serveur met parfois jusqu'à 1-2 minutes à répondre après une pause (plan gratuit)...") instead of implying the title has no data; `Univers.jsx` now passes `useSecurityPrices`'s real `isLoading`/`isError` through to `CandlestickChart`, which renders a distinct loading/error/empty message for each rather than collapsing all three into one. **Not yet applied**: the same `data`-only pattern still exists in `web/src/components/WatchlistRow.jsx`'s smaller sparkline usages of `CandlestickChart` — lower-stakes (a missing row-level sparkline reads as much less alarming than the full detail panel claiming "no history"), left alone rather than growing this fix into a larger unrequested sweep.
- **Process note**: every temporary debug endpoint/workflow from this investigation was added with a `# TEMPORAIRE` comment explaining exactly what it was isolating and why, and removed in the same session once superseded by the next, more precise one — none were left in the deployed API. If this class of bug recurs, `api/deps.py`'s engine, `list_security_prices`, and `response_model` serialization can all now be considered cleared; check cold-start timing (DevTools Network tab, or `time curl .../health`) first.
- **Root cause addressed, not just the symptom**: `.github/workflows/keep_api_warm.yml` (new) pings `GET /health` every 10 minutes via GitHub Actions' own `schedule:` cron — comfortably under Render's 15-minute idle-to-sleep threshold, so `george-api` never actually spins down during the hours this runs, rather than only widening client-side timeouts to tolerate a cold start that still happens. Chosen over an external cron service (e.g. cron-job.org, already used by the sibling `Jaz`/`MeteoIA` project) specifically because it needs no new account — the user asked for the GitHub-native option directly. `/health` was already public/unauthenticated and touches no DB, so this adds zero load of consequence. A 10-minute cadence (not the theoretical 14-minute max) leaves margin for GitHub Actions' own documented scheduling jitter under load.
- **Moved off GitHub Actions (2026-10), then moved back (2026-11)**: that 10-minute cron turned out to be the single biggest GitHub Actions cost in the repo — ~4,300 runs/month, each billed at least 1 minute, i.e. more than the 2,000 free minutes of a Free account on a **private** repo on its own. Real consequence: the monthly quota ran out and **every** workflow (daily collections, veille jobs, PR tests) was blocked with "spending limit needs to be increased" (diagnosed from `gh run view`, jobs failing in 3-5 s with no logs). The ping was moved to **cron-job.org** (free external scheduler, same choice as the sibling Jaz/MeteoIA project) for about a month while the repo stayed private.
- **The repo went public on 2026-11-04** (user's own decision, unrelated to this workflow — see the "Cron Cloudflare" section for the GitHub Actions spending-limit history this interacts with). GitHub Actions minutes on GitHub-hosted runners are **free and effectively unlimited for public repositories** (no monthly budget the way a private repo has) — confirmed in practice the same day: CI runs that had failed instantly (3-5 s, no logs — the spend-limit signature) since 2026-10-13 started actually executing the full pytest suite again (dozens of seconds, real pass/fail counts) immediately after the visibility change, no code change involved. With that cost gone, `keep_api_warm.yml`'s `schedule:` was restored (10-minute cron, same cadence as before) at the user's explicit request, **replacing** the cron-job.org ping rather than running alongside it — no need for a second account/service once GitHub Actions itself is free again. If cold starts come back, check this workflow's own recent runs (Actions tab) first, not cron-job.org (no longer relied on, though the account may still exist). **If the repo is ever made private again, revert this**: re-disable the `schedule:` here (back to `workflow_dispatch` only) before the quota problem repeats — the same reasoning applies to every other `schedule:`-bearing workflow in this repo (the eight jobs covered by `cloudflare-cron/`, see that section) and to `build_mobile_apk.yml` if it's ever run on a cadence instead of manually.

## Cron Cloudflare (remplace les workflows GitHub Actions planifiés) — ad hoc, not a roadmap phase

The repo's GitHub Actions spending limit has been stuck since 2026-10-13: every scheduled workflow run fails instantly (no runner assigned, no logs — the account hit its spending cap, confirmed via `github.com/settings/billing` → Usage flatlining at a fixed dollar amount) and stayed broken for weeks without the user raising the limit. `keep_api_warm.yml`'s own comment already explains the *original* overage cause (a 10-min health ping burning ~4 300 runs/month) and records that it was moved to the free `cron-job.org` — but the account-level spending limit itself stayed hit regardless, blocking every *other* scheduled job (bonds, energy, fundamentals, company/geopolitical veille, confidence-model training, price history + detection) for far longer than that one fix addressed. Requested by the user: a free alternative that doesn't depend on GitHub Actions minutes at all.

- **`cloudflare-cron/`** — a Cloudflare Worker (`wrangler.toml` + `src/index.js`), free tier, no card required at this volume. One Worker, 8 Cron Triggers (one per replaced job, same cron expression as the GitHub Actions `schedule:` it replaces), a single `scheduled(event, env, ctx)` handler dispatching on `event.cron` → `POST` to the matching `/cron/*` route rather than 8 separate Workers. `cloudflare-cron/README.md` has the full step-by-step deployment (`wrangler login`/`deploy`/`secret put`), written for the user to run themselves — this session has no Cloudflare account access.
- **`api/routers/cron.py`** (new router) — one `POST /cron/<job>` per replaced workflow, each firing the same `ingestion.*.run()`/`agents.*.run()`/`engine.*.run()` entry point the GitHub Actions step called, via `BackgroundTasks` (fire-and-forget: the Worker has its own CPU-time budget and isn't meant to wait out a multi-minute job; no `GET .../status` either, since nobody polls a cron job the way the web/mobile UI polls `/prices/refresh`). `/cron/bonds` additionally runs `seed_bond_alert_thresholds()` first, matching the original workflow step order.
- **Three `agents/*.py` modules refactored to expose what their `__main__` block used to do inline, as `run(...)`** — `agents/george_veille.py:run(company=None)`, `agents/geopolitical_veille.py:run(country=None)`, `agents/jane_veille.py:run_web(topic=None)` — called by both the CLI (unchanged behavior/arguments) and the new cron routes. `agents/george_veille.py`'s own module docstring still says "never through the shared reactive HTTP endpoint" (the original Phase-7-MVP design choice) — left in place as the historical record of *why* it was ad hoc-only originally, even though this change supersedes it; the docstring on the new `run()` function says so explicitly rather than silently contradicting the text above it.
- **`api/auth.py:require_cron_secret`** — a **separate** dependency from `require_user`, deliberately: these calls are machine-to-machine (a Worker, not a logged-in person), so forcing a Supabase session would mean inventing/refreshing a fake user account for no isolation benefit (this auth portal doesn't filter by user anyway, see its own module docstring). Shared secret via `X-Cron-Secret`, `hmac.compare_digest` (constant-time, avoids a timing side-channel on the secret), read from `CRON_SECRET` at call time. `cron.router` is therefore the one router in `api/main.py` **not** wrapped with `dependencies=[Depends(require_user)]`.
- **`render.yaml`**: `CRON_SECRET` added as a `sync: false` env var on `george-api`, alongside the other secrets Render prompts for on blueprint sync — must be set to the exact same value as the Worker's `CRON_SECRET` (`wrangler secret put`, see the README), or every `/cron/*` call gets a 401.
- **The 8 replaced workflows' `schedule:` triggers were removed** (not just left alongside the new Worker) — `.github/workflows/{daily_bond_yields,daily_energy_import,daily_fundamentals_import,daily_george_veille,weekly_geopolitical_veille,weekly_confidence_model_training,weekly_jane_veille_web,price_history_and_detection}.yml` keep only `workflow_dispatch` now, as a manual fallback. Found by `/code-review` on the first pass of this change: leaving both active would have fired every job twice (double Tavily/Mistral/yfinance/FRED/Webstat calls, double DB writes) — the exact spending-limit problem this change exists to route around, just doubled instead of fixed.
- **The Cron Trigger times deliberately do NOT copy the replaced workflows' `schedule:` cron strings verbatim** — a second `/code-review` pass caught that doing so would reproduce same-instant collisions (`fundamentals` daily 20:00 UTC landed on the exact same minute as `confidence-model-training` on Sunday, `price-history-and-detection` on Mon/Wed, and `jane-veille-web` on Saturday) that were harmless under GitHub Actions (each job got its own isolated runner) but become real CPU contention on Render's single free-tier `george-api` process, which also serves live web/mobile traffic. `cloudflare-cron/wrangler.toml` now spaces every job at least 30 minutes apart (`fundamentals` 20:00 → `george-veille` 21:00 → the day-specific heavy/light jobs at 21:30 → `geopolitical-veille` at 22:30 on Sundays, after `confidence-model-training` gets a full hour) instead of matching the old GitHub Actions times exactly.
- **One Cron Trigger for all 8 jobs, not one each — found on the user's actual `wrangler deploy` run, not by static review.** The first design (8 separate `crons` entries in `wrangler.toml`, one per job) failed to deploy: Cloudflare's error named one cron string as "invalid" (`30 21 * * 0`, syntactically fine), which turned out to be a misleading symptom of a real limit confirmed on `developers.cloudflare.com/workers/platform/limits` — **5 Cron Triggers per account** on Workers Free, not per Worker, and this account already hosts several other Workers. Fixed by collapsing to a single `"0,30 * * * *"` trigger (fires every 30 min) and moving the per-job schedule entirely into `cloudflare-cron/src/index.js:JOBS` (hour/minute/optional days-of-week, matched in code against `event.scheduledTime`) — scales to any number of jobs without ever touching Cloudflare's trigger quota again. The 30-minute spacing between jobs from the point above still applies (unrelated problem, same fix doesn't touch it).
- **Known gap, accepted as-is**: `weekly_confidence_model_training.yml`'s GitHub Actions version uploads the trained candidate as a downloadable artifact (`actions/upload-artifact`) for manual review before promotion. `POST /cron/confidence-model-training` has no equivalent — Render's free-tier disk isn't guaranteed to persist across deploys, so the candidate file written to `engine/models/candidates/` may not survive to be fetched later. The training report (`train_confidence_model.format_report`) is logged in full to Render's logs instead, so the metrics are at least visible; actually reviewing/promoting a candidate trained this way currently means reading Render's logs rather than downloading the `.joblib` file, same promotion discipline otherwise (`python -m engine.promote_candidate_model`, always manual, never automatic).
- **Tests**: `tests/test_auth.py` (4 new, pure) covers `require_cron_secret`'s 4 outcomes (missing config → 500, missing header → 401, wrong secret → 401, correct secret → passes); `tests/test_cron.py` (new, pure — no DB, no Docker, since the route handlers themselves never touch the DB, only the `BackgroundTasks`-scheduled bodies do, and those are monkeypatched out) covers routing + auth for all 8 `/cron/*` endpoints via `TestClient`, relying on the already-established project fact that `TestClient` runs `BackgroundTasks` synchronously before returning (see `tests/test_api.py`'s `/prices/refresh` test for the precedent comment). Full suite: 591 passed (up from 582), same pre-existing Docker-only error set, zero regressions.
