## Mobile login fixes and additions (`mobile/lib/features/auth/login_screen.dart`, Supabase project `wziegminwqfrhshnrwes`) — ad hoc, not a roadmap phase

- **A real release-build bug, not caught until an actual APK was installed**: `mobile/lib/core/env.dart`'s `supabaseUrl`/`supabaseAnonKey` are `String.fromEnvironment(..., defaultValue: '')` — required via `--dart-define`, with no sensible default (unlike `apiBaseUrl`, which defaults to `localhost:8000`). A `flutter build apk --release` run without those defines baked in empty strings, so "Continuer avec Google" tried to launch a schemeless URL (`/auth/v1/authorize?...`, no `https://project.supabase.co` prefix) — Android's `PlatformException(ACTIVITY_NOT_FOUND, ...)` on a malformed intent, not "no browser installed". Fixed by always passing `--dart-define=API_BASE_URL=...`/`SUPABASE_URL=...`/`SUPABASE_ANON_KEY=...` (the real deployed API + this project's Supabase credentials, the anon key being a public/publishable key by Supabase's own design — safe to embed) when building a distributable APK. **Hit a second time** (a manual `flutter build apk --release` without the defines, same silent empty-string fallback) — fixed for good with `scripts/build-mobile-release.ps1`, which hardcodes all three values so a release build no longer depends on remembering the flags; always prefer that script over calling `flutter build apk --release` directly.
- **"Continuer avec Yahoo" added, then removed** (at the user's direct request): it briefly existed as `_signInWithYahoo`, mirroring `_signInWithGoogle`, registered as a Supabase **Custom OIDC Provider** (Yahoo isn't one of Supabase's 20+ built-in providers, but is OpenID Connect-compliant, confirmed live against `https://api.login.yahoo.com/.well-known/openid-configuration`), identifier `custom:yahoo-oauth`. The button and method are gone from `login_screen.dart`; the Supabase-side custom provider config and the Yahoo Developer app registration were left as-is (external dashboard state this repo doesn't control) — disable the provider in Supabase's Dashboard → Authentication → Providers if it should stop accepting sign-ins entirely, not just lose its button here.
- **Password recovery** (`login_screen.dart:_showForgotPasswordDialog`, `features/auth/reset_password_screen.dart`, `core/auth/auth_providers.dart:isPasswordRecoveryProvider`): "Mot de passe oublié ?" collects just the email and calls `resetPasswordForEmail` — Supabase sends the email itself, nothing to build for that part. The reset link reuses the exact same deep link as Google OAuth (`io.supabase.george://login-callback/`), which opens a Supabase session with `AuthChangeEvent.passwordRecovery` rather than `signedIn`. **A real access-control bug avoided, not an incidental design choice**: `isLoggedInProvider` alone would already be `true` for that recovery session — without `isPasswordRecoveryProvider` forcing `/reset-password` first, `app.dart`'s router would send anyone holding a (possibly old/leaked) recovery link straight into the account on `/univers`, with no prompt to actually set a new password. The provider reads `authStateProvider`'s last event rather than tracking its own state, so it falls back to `false` for free the moment `updateUser(password: ...)` succeeds (Supabase emits `userUpdated`, not `passwordRecovery`, for that call) — no manual reset needed. No self-service "forgotten email" recovery: there's no secondary identifier (username, phone) to look an account up by, so the dialog just points to contacting support instead of pretending a secure lookup exists.
- **Email sign-up confirmation handling**: `_showSignUpDialog` previously assumed `signUp()` always returns an active session and let the router's `redirect:` handle everything. If the project's "Confirm email" setting (Authentication → Sign In/Providers, confirmed already enabled here) is on, `signUp()` returns a `user` but `session: null` until the user clicks the emailed confirmation link — Supabase sends that email itself, nothing to build for the sending side. Fixed by checking `response.session == null` and showing a new "Vérifiez votre boîte mail" dialog instead of silently closing and waiting for a redirect that will never come.
- **Google sign-in needing two attempts**, reported directly by the user: tap "Continuer avec Google", pick an account, land back on the login screen unauthenticated; tap again, pick the account again, and it works the second time. Two fixes, applied in sequence after the first alone didn't resolve it on-device:
  1. **`android/app/src/main/AndroidManifest.xml`**: `MainActivity`'s `launchMode` was still the untouched Flutter template default, `"singleTop"` — never a deliberate choice, never revisited before this bug. `signInWithOAuth` opens the browser on top of `MainActivity`, so by the time Google redirects back via the `io.supabase.george://` deep link, `MainActivity` is no longer at the top of the back stack — `singleTop` only dedupes when the activity *is* at the top, so Android could create a second instance to receive the callback while the original (visible) instance never learns a session was established elsewhere. Changed to `"singleTask"` — confirmed as the right launchMode by checking the sibling `JADE` project, which already uses `"singleTask"` for the exact same `signInWithOAuth`/deep-link setup and documents having hit this precise duplicate-instance symptom itself (there manifesting as the system back button landing on a stale `LoginScreen` instance). **This alone did not fix the bug on-device** (confirmed by the user re-testing a rebuilt APK) — a second, deeper cause remained.
  2. **`login_screen.dart`**: the class docstring's original claim — "no manual navigation needed after a successful sign-in, `redirect:` handles it as soon as `authStateProvider` sees a session" — turned out to be false in practice, the same class of bug already found and fixed once in this exact codebase for the *logout* path (see `profile_screen.dart:_logout`'s comment: `redirect:` only re-evaluates after `authStateProvider` updates asynchronously, and nothing guarantees that update lands before the router re-reads `state.uri` at the moment the deep link arrives). Fixed by mirroring `JADE/mobile/lib/features/auth/login_screen.dart`'s already-production-proven pattern: `LoginScreen` now subscribes directly to `Supabase.instance.client.auth.onAuthStateChange` in `initState` and calls `context.go('/univers')` explicitly the moment a non-recovery session appears, rather than depending entirely on the router's `redirect:` timing. `AuthChangeEvent.passwordRecovery` is explicitly excluded from this listener — that case must still resolve through `isPasswordRecoveryProvider`/`app.dart` to force `/reset-password`, never a direct jump to `/univers` (see that provider's own docstring for the access-control risk this avoids).

  **Both fixes together confirmed working on a real device** by the user, testing a rebuilt release APK: "Continuer avec Google" now succeeds on the first attempt.
- **`.github/workflows/build_mobile_apk.yml`** (manual `workflow_dispatch` only, no scheduled trigger) — added because a Claude Code cloud session has no Flutter/Android SDK installed and this specific sandbox's network policy blocks `dl.google.com` (the Android SDK + Google's Gradle Maven repo host), so `scripts/build-mobile-release.ps1` can't run there at all. The workflow runs on a GitHub-hosted runner instead (not subject to that sandbox's restriction), using `subosito/flutter-action` + `actions/setup-java` (JDK 17, matching `android/app/build.gradle.kts`'s `JavaVersion.VERSION_17`), and reuses the exact same `--dart-define` values as the PowerShell script — the Supabase anon key is hardcoded the same way there and here (public/publishable key by Supabase's own design, already compiled into every distributed APK, not a GitHub Actions secret). Uploads `app-release.apk` as a 30-day build artifact, and also pushes it to **Firebase App Distribution** (Firebase project `worldchecks-c8a93`, Android app `com.george.george_mobile`, app ID `1:364565195267:android:4946b5d273d813c4677c36`) via `wzieba/Firebase-Distribution-Github-Action`, authenticated with the `FIREBASE_SERVICE_ACCOUNT` repo secret (the project's default `firebase-adminsdk-fbsvc@worldchecks-c8a93` service account key, Editor role — not a dedicated "Firebase App Distribution Admin" account, kept simple since this is the only Firebase use in the project so far). No `groups` input is set (no tester group existed when this was wired up), so uploads land in the console without auto-notifying anyone — add `groups: "<name>"` once a tester group exists.
- **First two runs of `build_mobile_apk.yml` (and every other scheduled workflow in this repo) failed instantly with no runner assigned** — traced to the account's GitHub Actions spending limit being hit (metered usage flatlined at exactly $12 from 2026-10-13 onward, visible in `github.com/settings/billing` → Usage), not anything wrong with this workflow or any other. Every job in the repo was silently broken for ~2 days until the user raised the limit. Worth checking first if a workflow run ever shows `runner_id: 0` and no downloadable logs.

## Mobile app (Flutter) — ad hoc, not a roadmap phase

**Decommissioned for now (Nov. 2026), at the user's explicit request** — documentation-only change, nothing technical disabled: `mobile/` keeps its code, `build_mobile_apk.yml` (manual `workflow_dispatch` only, never ran automatically) is left runnable, and no existing Firebase App Distribution upload was revoked. The point of this note is to stop a future session from treating `mobile/` as an actively maintained surface (e.g. porting a new web screen to it, or running the build workflow) without first checking back with the user — nothing here should be read as a decision to delete the app or its code.

Requested directly by the user as "Flutter + Firebase" rather than the roadmap's own Phase 5 spec (React Native/Expo + Firebase Cloud Messaging + Piper/Coqui TTS, see `George_Prompts_Claude_Code.md`). Built as a deliberately scoped-down V1 MVP with explicit user sign-off (plan mode) — same precedent as the Phase 7 scale-down: 3 screens mirroring `web/`'s functionality against the existing FastAPI backend, no push notifications, no native TTS/STT, no offline cache, no daily digest, no authentication. `mobile/` was a one-line placeholder README before this; it's now a real `flutter create` scaffold (`--org com.george --project-name george_mobile --platforms=android,ios`).

- **No Firebase in V1, deliberately** — flagged directly to the user rather than added for its own sake: FCM (push) and Firebase Auth are the only two Firebase products that would organically fit this app, and both are explicitly out of scope for V1 (no push infra, no auth anywhere in the backend yet — Phase 9 of the roadmap, not built). Adding Crashlytics/Analytics just to "use Firebase" would be contrived scope with no backend equivalent to match (`web/` has no crash reporting either). Firebase gets wired in during a V2 that actually tackles push notifications.
- **No authentication in V1** — the app calls the API directly, no login screen, matching the backend's current reality: no auth exists anywhere (see the API section above, `api/main.py`'s "Pas d'authentification à ce stade" comment), portfolios are globally shared, not per-user.
- **State management: Riverpod** (`flutter_riverpod`), not BLoC/plain `Provider` — chosen as the closest analogue to `web/`'s React Query pattern: one `FutureProvider.family` per API resource (mirroring one `useX` hook per resource in `queries.js`), with mutations calling `ref.invalidate(...)` on success instead of `queryClient.invalidateQueries(...)`. `lib/data/invalidate_all.dart:invalidateAllData` is the direct analogue of `useRefreshPrices`'s "invalidate everything" comment — `ref.invalidate(provider)` on a `.family` provider invalidates every parameterized instance, not just one. **Riverpod 3.x API gotcha hit while building this**: `AsyncValue.valueOrNull` from Riverpod 2.x is gone — the plain `.value` getter is now nullable and fills that role (`AsyncValue<T>.value` returns `T?`, never throws). Also, `StateProvider` moved to `package:flutter_riverpod/legacy.dart` in 3.x; rather than pull in that import for a single screen-local filter chip (purely UI state, not server state), `UniversScreen` uses a plain `ConsumerStatefulWidget` with local `setState` instead — no Riverpod provider needed for state that isn't shared/server-derived.
- **API client: hand-written, not codegen'd from `/openapi.json`** — `lib/core/api_client.dart` mirrors `web/src/api/client.js`'s 3-verb wrapper (`get`/`post`/`delete`) exactly, and `lib/models/*.dart` are hand-transcribed from `api/schemas.py` field-by-field, same discipline as the web client's implicit JSON destructuring. Chosen over `openapi-generator`/chopper/retrofit because the API is small (~9 resources, one shared `Page[T]` envelope) and has free-form `dict` fields (`PatternOut.context`, `AgentEventOut.context`) that would generate poorly as strict Dart classes anyway. **Naming collision worth knowing about**: the hand-written generic pagination wrapper is named `Page<T>` (mirroring `api/schemas.py:Page[T]`) — this collides with Flutter's own `widgets.dart:Page` class (used by `Navigator`'s Pages API) the moment a file imports both `package:flutter/material.dart` and `models/page.dart` and references `Page<T>` by name (hit in `test/features/paniers_screen_test.dart`); fixed there with `import '.../models/page.dart' as model;` rather than renaming the model class, since no non-test file needs both imports together.
- **Long-running calls get an explicit per-call timeout override, not a longer global default** — `/agents/collect`, `/decisions/{id}/explanation`, and `/chat` pass `receiveTimeout: Duration(seconds: 90-120)` on the specific `ApiClient` call rather than raising the shared `Dio` instance's default (15s connect / 30s receive) — same "surface real errors fast" reasoning as `retry: 0` in `web/src/main.jsx` and `connect_timeout=5` in `ingestion/db.py`. `/prices/refresh` no longer needs this override: it was made asynchronous (see the "Named portfolios" section below) after its old synchronous, up-to-2-minute call routinely exceeded even this override once the backend was repointed at 10 years of price history — `PricesRefreshRepository.refresh()` now polls a status endpoint instead, bounded by its own `_maxWait`/`_maxConsecutiveErrors` guards rather than a single fixed HTTP timeout.
- **`lib/shared/widgets/response_dialog.dart:showResponseDialog`** is the mobile analogue of `web/src/components/ResponsePopup.jsx` — one dialog (loading/done/error, parameterized `loadingText`) reused for every LLM/long-running action (decision explanation, chat, price refresh, macro collection, budget allocation) instead of a bespoke dialog per screen.
- **`lib/features/univers/widgets/candlestick_chart.dart`** is a direct `CustomPainter` port of `web/src/components/CandlestickChart.jsx`'s hand-rolled SVG chart (there's no off-the-shelf Flutter candlestick chart in `fl_chart`) — same `buildOverlay` logic (markers from `{index/points, price}` context entries, horizontal lines for `resistance`/`support` keys), same generic "derive from `context`'s shape, not the pattern's name" principle called out in the original component's own comment.
- **`lib/features/decision_detail/`** is a pushed screen (`Navigator.push`, not a `go_router` route) rather than `web/`'s 3rd desktop column — mobile has no room for a persistent 3-column layout, and a plain imperative push was simpler than wiring a nested `go_router` route for a single non-deep-linked destination.
- **`DataTable` + horizontal `SingleChildScrollView`** renders each portfolio's decisions table in `lib/features/portefeuille/portefeuille_screen.dart` — same reasoning as `web/`'s `overflow-x-auto` on a `min-width: 840px` table (too many columns for a narrow viewport either way, scroll rather than cram).
- **Budget allocation uses a plain numeric `TextField`, not voice** — `web/`'s `MonPortefeuille.jsx` parses a spoken euro amount via `useVoiceCapture` + a regex (`parseBudgetFromText`); mobile's budget dialog still just takes a number directly, unrelated to the `speech_to_text` package added later for "Ask Jane" (see below) — porting the budget flow to voice too wasn't part of that change and remains unscoped.
- **Testing**: no dedicated hook tests (this codebase's `web/` doesn't unit-test its React Query hooks either — they're trivial wrappers) — widget tests per screen (`test/widget_test.dart`, `test/features/paniers_screen_test.dart`, `test/features/portefeuille_screen_test.dart`) override the relevant Riverpod providers with fake data instead of letting a real HTTP call fire, same principle as `web/`'s wholesale `vi.mock("../api/queries")`. A provider left un-overridden in a test (e.g. `georgeIndexProvider` in the Paniers test) still resolves safely to its `AsyncValue.error` branch — Flutter's test `HttpClient` returns a fake 400 for any real request rather than hanging, so an un-mocked provider degrades gracefully instead of timing out the test.
- **Networking for local dev**: `mobile/README.md` documents the `--dart-define=API_BASE_URL=...` mechanism (no `flutter_dotenv` — Flutter's native build-time define mechanism already solves this, no extra dependency needed) and the three environments that actually differ (Android emulator needs `10.0.2.2`, not `localhost`; iOS simulator can use `localhost` directly; a physical device needs the host machine's real LAN IP plus `uvicorn --host 0.0.0.0`). CORS (`api/main.py:allow_origins`) is a browser-only mechanism and doesn't apply to native Android/iOS builds at all — only relevant if a Flutter *web* target is ever added.
- **`android/gradle.properties`'s default `org.gradle.jvmargs=-Xmx8G ...`** (from the stock Flutter Android template) crashed the Gradle daemon with an out-of-memory native allocation failure on this dev machine (7 GB total RAM, well under 8 GB) — lowered to `-Xmx2048m -XX:MaxMetaspaceSize=1g -XX:ReservedCodeCacheSize=256m`, which built `flutter build apk --release` successfully. Worth checking first if a release/debug APK build mysteriously fails with "Gradle build daemon disappeared unexpectedly" plus a `hs_err_pid*.log` crash dump in `android/` — that log's own "Out of Memory Error" / "insufficient memory... to continue" message is the tell, not a code problem.
- **Trading & Obligataire tabs (Oct. 2026, aligning mobile with `web/`)** — two new `StatefulShellBranch`es (`/trading`, `/obligataire`), 5 bottom-nav tabs in total. Labels shortened to "Portef." / "Oblig." (full names kept in tooltips and screen titles) because 5 destinations at the theme's 14.52 px label size don't fit ~78 px each on a 390 px phone. `features/trading/trading_screen.dart` mirrors `web/src/views/Trading.jsx` but turns the 4 status columns into tabs (+ a "Performance" tab fed by `GET /decisions/performance`, `models/performance.dart`); confirm/recompute/confirm-exit/propose/monitor go through new `DecisionsRepository` methods, and confirm-exit asks for confirmation first (it closes the decision for good — no broker order is ever sent). `features/obligataire/obligataire_screen.dart` mirrors `web/src/views/Obligataire.jsx` (yield cards with red-rise/green-fall variations, OAT-Bund spread, US slope, history chart, bulletin, active alerts, editable thresholds) via `data/bonds_repository.dart`; alert history and collection runs (shown on web) are not ported. Written without a local Flutter SDK (the build session had none) — `flutter analyze`/`flutter test` must be run before trusting it; tests: `test/features/trading_screen_test.dart`, `test/features/obligataire_screen_test.dart`, `test/models/lifecycle_models_test.dart`.
