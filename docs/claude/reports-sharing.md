## Share by email (`notifications/email_client.py`, `agents/email_formatter.py`, `engine/chart_image.py`) — ad hoc, not a roadmap phase

Requested directly by the user: add "copy" and "share" actions to George's response popups (📋 copy text, 📤 share by email with a To/Cancel/Send dialog) — with the email actually sent from the server (not the phone's native share sheet), the body reformulated by Mistral before sending, and the security's 10-year price chart attached whenever the popup is tied to one (e.g. a decision explanation). Two scope points confirmed directly with the user via `AskUserQuestion`: a real transactional email provider (Resend, chosen from a short list) rather than a native OS share sheet, and the copy/share actions living on the shared `ResponseDialog` itself (so every popup gets them — chart attachment only where a `symbol` is actually associated) rather than only the decision-explanation one.

- **No email-sending infrastructure existed anywhere in this project before this pass** — same "new external service" precedent as Mistral/OilPriceAPI/Supabase: the user created a Resend account and provided the API key directly. `notifications/` is a new top-level package (alongside `ingestion/`, `engine/`, `agents/`, `api/`) — `notifications/email_client.py` calls Resend's REST API directly via `httpx` (already a base dependency) rather than adding the official `resend` SDK, since it's a single JSON POST. Follows the exact same contract as `agents/mistral_client.py`/`api/auth.py`: `RESEND_API_KEY` read at call time, not import time; `EmailUnavailableError` is a dedicated `RuntimeError` subclass (not bare `Exception`) with its own `api/main.py` handler, for the same Starlette `ServerErrorMiddleware`-vs-`CORSMiddleware` reason documented for `MistralUnavailableError`/`SupabaseUnavailableError`.
- **Sandbox limitation confirmed live, not assumed**: without a verified sending domain, Resend's default `onboarding@resend.dev` "from" address can only deliver to the Resend account's own registered email — a real send to a different address returned a genuine `403` from Resend's API ("You can only send testing emails to your own email address..."), surfaced as a clean `503` by `EmailUnavailableError` rather than crashing. A second real send to the account's own address succeeded end-to-end (`sent: true, chart_attached: true`). Documented for the user: sending to arbitrary recipients requires verifying a domain on resend.com later; the feature already works today toward the account's own email.
- **`agents/email_formatter.py:format_email_body`** reformulates the raw popup text via a new prompt (`agents/prompts/email_share_system.txt`) before sending — same anti-hallucination contract as every other George-voice prompt (never add a fact/number absent from the input, reformulate presentation only). Falls back to the raw, unreformulated text if Mistral is unavailable (`MistralUnavailableError`) rather than blocking the send — same "a nice-to-have polish step should never block the core action" reasoning as `engine/scoring.py:predict_confidence` falling back to the heuristic score.
- **`engine/chart_image.py:render_candlestick_png`** is the second real consumer of `mplfinance` (the first being `engine/notebooks/pattern_validation.ipynb`) — promoted from the `notebook` extra to `pyproject.toml`'s base dependencies, since it now runs inside the live API, not just offline. **A real bug caught live, not assumed**: rendering inside FastAPI's threadpool (this route is a plain `def`, like `api/routers/prices.py`, so long-running work doesn't block the event loop) crashed with `RuntimeError: main thread is not in main loop` — matplotlib had auto-detected the machine's installed GUI backend (TkAgg), which isn't thread-safe outside the main thread. Fixed with an explicit `matplotlib.use("Agg")` (the standard headless, server-side rendering backend) before importing `mplfinance`/`pyplot` — caught by actually exercising the endpoint through `TestClient` in a test, not just calling the rendering function directly in isolation (which runs on the main thread and never hit the bug).
- **`POST /share/email`** (`api/routers/share.py`) takes `to_email`/`subject`/`text`/optional `symbol`; if `symbol` is given, loads its price history via `engine.run_detection.load_prices` (the same `price_history_long`-backed function the rest of the pipeline uses) and attaches the rendered 10-year PNG — silently omitted (never an error) if the symbol is unknown or has no price history, since the chart is an enrichment, not a precondition for sending. All internal calls go through whole-module imports (`import notifications.email_client as email_client`, etc.), never `from x import y` — the same stale-reference precaution already documented for `agents/mistral_client.py`/`api/routers/baskets.py`.
- **The attached chart surfaces the actual detected pattern, not a bare price history** — requested directly by the user after seeing a first plain chart in a real received email and asking for the breakout/resistance to actually show. `engine/chart_image.py:_build_overlay` is a **fourth** port of the same "derive the overlay from the shape of `patterns_detected.context`, never from the pattern's name" logic already implemented three times over (`web/src/components/CandlestickChart.jsx`, `mobile/lib/features/univers/widgets/candlestick_chart.dart`, `engine/notebooks/pattern_validation.ipynb:plot_match`) — `{index/points, price}` entries become orange scatter markers (`mpf.make_addplot`), `resistance`/`support`/any leveled entry become dashed horizontal lines (`hlines=`, omitted entirely rather than passed as `None` — mplfinance rejects that outright, same trap the notebook already hit once). `api/routers/share.py:_latest_pattern` resolves the most recently detected pattern for the symbol (same `detected_at`-then-`confidence` tiebreak as `api/routers/securities.py`'s pattern listing) and passes its `context` through — no pattern for that symbol means a plain, unannotated chart, never a fabricated one.
- **A real production deploy failure caught immediately, fixed before it could recur**: promoting `mplfinance>=0.12` to a base dependency broke the Render build — `mplfinance` has never published a stable (non-pre-release) version ≥0.12 on PyPI, only alpha/beta builds (`0.12.7a17`, `0.12.10b0`, etc.), and pip's dependency resolution on a genuinely fresh environment excludes pre-releases by default unless the specifier itself contains a pre-release identifier (this had gone unnoticed locally only because `mplfinance` was already installed on this machine from earlier notebook work, so pip never had to resolve it from scratch). Fixed by pinning the lower bound to the actual pre-release version (`mplfinance>=0.12.10b0`) — verified, not assumed, by installing into two brand-new throwaway virtualenvs (one for `mplfinance` alone, one for the whole project via `pip install -e .`), matching exactly what Render's clean build does.
- **Mobile (`response_dialog.dart`)**: `showResponseDialog` gained an optional `symbol` parameter (threaded through only at the one call site that has a real security context — `decision_detail_screen.dart`'s "Demander une analyse à George" button; the other four call sites — price refresh, macro collection, chat, budget allocation — pass none, so their shares stay text-only, exactly per the confirmed scope). 📋/📤 `IconButton`s appear in the dialog's `actions` row only once real text has loaded (not during loading/error). 📤 opens a small email/Annuler/Envoyer dialog (`_ShareEmailDialog`, same ❌/✅ emoji-button convention as the account-creation and portfolio-deletion dialogs elsewhere in this app), then re-invokes `showResponseDialog` itself for the send's own loading/success/error state — reusing the existing widget rather than building a second one.
- **Cup & Handle's rim/handle levels were invisible in the overlay everywhere, not just email — a real, pre-existing gap caught by the user directly on a real received chart.** All three overlay implementations (`web/src/components/CandlestickChart.jsx`, `mobile/lib/features/univers/widgets/candlestick_chart.dart`, `engine/chart_image.py`, plus the notebook) only ever treated keys literally named `resistance`/`support` as horizontal levels — Cup & Handle's `left_rim`/`right_rim`/`handle_low` play the exact same conceptual role under different names, so the pattern rendered as orange markers only, never a line. Fixed by extending the recognized level-key set (now `{"resistance", "support", "left_rim", "right_rim", "handle_low"}`) identically in all four places, keeping the "derive purely from the shape/name of `context` keys, never from `pattern_type`" design principle intact — this widens the *vocabulary* of recognized level names rather than special-casing by pattern type.
- **Take-profit/stop-loss lines added to the emailed chart** — `render_candlestick_png` takes optional `take_profit`/`stop_loss` (green/red dashed lines, same colors as `AppColors.positive`/`negative` elsewhere in this app), combined with the pattern's own blue level lines into one `hlines=` call (mplfinance takes one color per line, not per line-group, so all three sources — pattern levels, TP, SL — are merged into a single list+color-list pair). Threaded end to end: `ShareEmailRequest.take_profit`/`stop_loss` → `api/routers/share.py` → `mobile/lib/data/share_repository.dart:shareByEmail` → `showResponseDialog`'s new `takeProfit`/`stopLoss` params → `decision_detail_screen.dart` passes `decision.takeProfit`/`stopLoss` at its one call site.
- **A real stale-index artifact found (not a rendering bug) while manually verifying the Cup & Handle fix**: rendering an *old* Cup & Handle detection (from before this session's `price_history_long` 10-year backfill fully completed) put its markers near 2016 instead of near its real ~2026 formation — because that row's stored `index` values are absolute positions in whatever (much shorter) price series `load_prices` returned *at detection time*, and the table has since grown much longer. Confirmed by rendering a pattern detected *after* the backfill completed (a fresh Inverse Head & Shoulders) and seeing its markers land correctly at the real, recent formation. Not something to fix in code — the historical portion of `price_history_long` is now stable (new ingestion only appends future bars), so this can't recur for anything detected from now on; it only affected patterns detected during the one-time backfill transition.
- **Verified**: new backend tests (`tests/test_email_client.py`, `tests/test_email_formatter.py`, `tests/test_chart_image.py` — including `_build_overlay`'s marker/hline extraction, the Cup & Handle regression case, a render with TP/SL, and a render with real pattern context, not just a bare chart — plus 6 new cases in `tests/test_api.py` covering chart-attached/no-symbol/unknown-symbol/reformulation/503-with-CORS-headers) — full suite (`pytest -q`, 287 passed) green. New `mobile/test/shared/response_dialog_test.dart` (3 tests: icons hidden while loading then shown, copy writes to the system clipboard, share invokes `ShareRepository` with the right symbol/text) — `flutter analyze` clean, `flutter test` (6 tests) green, `npm run build`/`npm run test` (web, 45 tests) green after the `LEVEL_KEYS` change. Live end-to-end: a real `POST /share/email` call reformulated real text via Mistral, rendered a real 2,559-session ACA.PA chart correctly annotated with its actual Inverse Head & Shoulders neckline/points, and delivered a real email via Resend to the account's own address with the chart attached. The `mplfinance` pin fix separately verified via two clean-room virtualenv installs.

## Rapport stratégique hebdomadaire + portefeuille virtuel (`agents/strategic_report.py`, `engine/virtual_portfolio.py`, `engine/strategic_risk.py`, `api/routers/strategic_reports.py`, web/mobile « Rapport ») — ad hoc, not a roadmap phase

Requested directly by the user, modelled on a report they had obtained from ChatGPT (France macro/budget, OAT/Bund/spread, energy/geopolitics, CAC 40 sector reading, a virtual 100 000 € portfolio, 40-stock decision table, 3-month scenarios, a vert/orange/rouge bond-risk indicator). Scope confirmed via `AskUserQuestion`: generated by George (not imported), web **and** mobile, portfolio tracked over time, on-demand button (no schedule — GitHub Actions quota).

- **Anti-hallucination split, by construction**: everything numeric is computed in Python and stored in `StrategicReport.data` (migration `0020`): bond cards/spread (`engine.compute_bond_yields.build_dashboard_summary`), energy, CAC 40 close via yfinance `^FCHI`, George's latest decision per CAC 40 stock, the virtual portfolio, and numbered Tavily extracts (`sources`, 6 themed queries × 3 results, news of the last 10 days via the new optional `web_search.search(days=…)`). The LLM (`MODEL_LARGE`, `agents/prompts/strategic_report_system.txt`) only writes `narrative_markdown` from that context, must cite web facts as `[n]`, and never computes a number. A Mistral outage yields an explicit fallback text — the numeric report is still saved. Web/mobile render the Markdown with a tiny parser (`web/src/components/markdownBlocks.js`, `mobile/lib/features/rapport/markdown_blocks.dart`), never as HTML.
- **Bond-risk indicator** (`engine/strategic_risk.py`): rouge if OAT > 5,0 % **and** spread > 150 pb; vert if spread < 120 pb **and** OAT < 4,5 %; else orange; `indetermine` without data. Tracking thresholds of this report, not official ones (said in the UI). Note OAT/Bund are monthly FRED/OECD series (weeks old) — the date is always shown.
- **Virtual portfolio** (`engine/virtual_portfolio.py`, pure): 100 000 €, 0.15 % fees per order, whole shares, positions/cash always **replayed from the full trade list** (`virtual_portfolio_trades`), never stored separately; one `virtual_portfolio_snapshots` row per report for report-to-report performance. Rules: sell everything whose latest signal turned bearish; buy bullish CAC 40 signals not held, by confidence, 7 % of total value each, max 12 positions, keeping a cash reserve of 30/45/60 % (vert/orange/rouge). No partial sells, no top-ups.
- **Real bugs caught by an independent review before shipping** (all with regression tests): (1) `engine/monitor_decisions.py` sets `status="sortie_proposee"` but keeps `decision_type="Achat"` — reading only `decision_type` turned an exit into a buy signal; the report now takes each stock's latest decision of **any** status and maps `sortie_proposee`/`cloturee` to the bearish labels "Sortie proposée"/"Clôturée" (`decision_label`). (2) Two overlapping generations (Render deploy overlap, CLI during a web job) could double-buy: the write transaction takes `pg_advisory_xact_lock(PORTFOLIO_LOCK_KEY)` and aborts if the trade count changed since it was read. (3) A held stock with no recent price blocked all buys and skipped the snapshot: held stocks missing from the 20-day window are valued at their last known close (`_last_known_closes`). (4) Mixed-date prices: a close more than `STALE_PRICE_DAYS` (5) older than the universe's latest is flagged `stale` — shown and used for valuation, never as an execution price. The performance "vs previous report" now carries that report's date/id.
- **API**: `POST /strategic-reports/generate` (background job, in-memory state + lock, same pattern as `/prices/refresh`; network calls happen outside any DB session because of the 2+2 pool), `GET /strategic-reports/generate` (poll), `GET /strategic-reports`, `/latest` (`null` before the first report), `/{id}`. CLI: `python -m agents.strategic_report`.
- **Tests**: `tests/test_virtual_portfolio.py`, `tests/test_strategic_risk.py`, `tests/test_strategic_report.py` (pure parts + an end-to-end DB test: two generations don't re-buy, concurrent trade aborts, API serves the latest), `web/src/views/Rapport.test.jsx`, `web/src/components/markdownBlocks.test.js`, `mobile/test/features/rapport_screen_test.dart` (written without a Flutter SDK — run `flutter analyze && flutter test`). The Docker-tier tests were run here against a local Postgres 16 + pgvector instead of testcontainers.
- **First production run failed with `cannot convert float NaN to integer`** (`math.floor` in `plan_trades`): `price_history_long.close` is `Numeric`, which accepts NaN, and `ingestion/price_history.py` wrote yfinance's NaN rows as-is (the `close is None` checks never caught them). Fixed at three levels: the ingestion now drops rows with a NaN open/high/low/close (NaN volume → 0); the report treats any non-finite value as missing (`_f`, a SQL `close != 'NaN'` filter in `_last_known_closes`) and passes `data` through `_json_safe` before the JSONB write (JSONB rejects NaN); `plan_trades`/`positions_value` ignore non-finite prices. NaN rows already in production stay but are now skipped everywhere this report reads them.
- **Second production failure: `QueuePool limit of size 2 overflow 2 reached`** — the job used `deps.SessionLocal`, i.e. the API's 2 + 2 pool, while the web Univers screen fired ~100 `/securities/{symbol}/patterns?limit=1` requests at once and held every connection for > 30 s. Two fixes: the job now runs on its own `NullPool` engine (`api/routers/strategic_reports.py:_job_engine`, built from `deps.engine.url` at call time, disposed after the job — at most one extra Supabase connection, opened only around the two short DB phases); and a new batch endpoint `GET /securities/patterns/latest` (latest pattern per symbol via `row_number()`, same date-then-confidence tiebreak) replaces the per-symbol calls for the Univers radar and watchlist (web `useLatestPatterns`, `WatchlistRow.latestPattern`; mobile `latestPatternsProvider`). The watchlist sparklines still fetch prices per row on web.
- **Pre-existing, unrelated test failures seen while running the Docker tier for the first time in a while** (not fixed here): `tests/test_bond_yields.py::test_run_is_idempotent_and_logs_the_collection_run` (its fake CSV only has a `DGS10` column, so 3 of 4 series find nothing) and 3 bond-alert tests failing with `DetachedInstanceError` (objects read after their session closed — surfaced with SQLAlchemy 2.1).
